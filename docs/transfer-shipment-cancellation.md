# Отмена ошибочной отправки

Решение владельца 06.10.2026: добавить отмену ошибочно отмеченной отправки, когда весь товар физически остался у отправителя. Существующий довоз из исходной поставки уже решает недостачу и не меняется. Исправленные сотрудниками документы повторно не корректируются.

## Правило

В статусе «В пути» снабжение с действующим правом `transfers.cancel` может выбрать «Отменить ошибочную отправку». Обязательны причина длиной 5–500 символов и отдельное подтверждение, что **весь** товар остался на исходном складе. Если товар действительно уехал, этот сценарий неприменим.

Начавшаяся приёмка, включая нулевой принятый факт, проведённый приход и связанные корректировки блокируют отмену. Сервер проверяет отправку в ERP: принадлежность перемещению и компании, проведённый Material Transfer, исходный склад, транзитный склад, товары и количества. Другие активные складские операции по этому перемещению требуют отдельного разбора. Серийные/партионные движения с bundle не отменяются этим инструментом.

После проверок приложение сохраняет намерение отмены в существующем JSON документа Б24. Затем создаёт обратный Material Transfer из тех же транзитных складов в исходные, с теми же товарами, количествами, единицами и состоянием товара. Проведение использует текущую дату ERP. Исходная отправка остаётся проведённой; её история не переписывается. После подтверждения обратного движения перемещение становится «Отменено», история содержит автора, причину и номер обратного документа. Отмена до отправки по-прежнему освобождает резерв без складского движения.

## Сбои и совместимость

Источник документов остаётся `ctv_transfers.DETAIL_TEXT`, складского учёта — Stock Entry ERPNext. Добавлено необязательное `shipmentCancellation` с причиной, автором, временем и номером обратного движения; старые документы читаются без миграции. Для обратного движения используется существующее поле `b24_transfer_phase` со значением `cancel_ship`.

Отмена, отправка, приёмка, проведение и удаление используют общий замок перемещения в одном процессе backend. Перед складской записью сохраняется намерение отмены: после сбоя/перезапуска приёмка заблокирована до завершения отмены. Повтор ищет `cancel_ship`, сверяет его содержание, продолжает черновик или использует уже проведённый документ. Неопределённый результат создания/проведения не вызывает немедленной повторной отправки; ошибка показывается пользователю, следующий запрос сначала читает ERP. Если завершилась ERP-операция, но не сохранился финальный статус Б24, повтор только завершает состояние Б24. Документ с историей отмены нельзя удалить штатной кнопкой удаления.

При ошибке до сохранения намерения документ остаётся доступным для приёмки. Если намерение уже сохранено, требуется завершить отмену повторным действием; при несовместимых данных — разбор администратора. Межпроцессный замок не добавлялся: для нескольких одновременно работающих backend потребуется отдельная распределённая координация.

Регрессии: `packages/backend/src/routes/transfer-shipment-cancellation.test.ts`, `packages/frontend/src/transfer-shipment-cancellation.test.tsx`. Проверяются отказ без прав/подтверждения/причины, начавшаяся приёмка, несовместимая отправка, исходная история, повтор после сбоев ERP/Б24, состояние и единицы товара, общий замок, прежняя отмена черновика, запрет удаления, подтверждение в UI и API. Данные реальных обращений и складские записи в тестах не используются.
