# Заказы интернет-магазина → b24-app

Статус на 18.09.2026: production receiver и постоянный worker b24-app работают.
Сторона магазина включает отправку отдельно. Приёмник v1 принимает необязательные
`order.business` и `order.fulfillment`; `schemaVersion` сохранён, старые события
без этих полей совместимы. Результаты обновлений:
[реквизиты организаций](umniydom-orders-business-deployment-20260918.md) и
[способ получения](umniydom-orders-fulfillment-deployment-20260918.md).

Актуализация 14.09.2026: [совместный тест сайта пройден](contracts/b24-joint-test-20260914.md).
[Перенос подготовлен в отдельной рабочей копии](umniydom-orders-production-prep.md);
разделы ниже описывают исходную реализацию в этой старой ветке.

## Принятые решения

- Уведомления идут в существующий чат **«Заказы интернет магазин»**, `chat19572`.
- Новый лид назначается служебной учётной записи **«Автозадачи», ID 2812**.
  Активность подтверждена через API; одноимённая старая запись 8 отключена.
  Подстановки администратора, сотрудника или автора вебхука нет.
- Несколько совпадений по телефону/email — сообщение «Нужен ручной разбор»
  в тот же чат; новый лид не создаётся.
- Принятие заказа менеджером пока отмечается сотрудниками в чате. Само
  получение сообщения не означает, что заказ взят в работу.

## Устройство

Код: `packages/backend/src/integrations/umniydom/`.

| Файл | Ответственность |
| --- | --- |
| `contract.ts` | Совместимая Zod-схема: структура, контакты, организация, источники и арифметика |
| `config.ts` | Режимы, секрет, sourceId, путь БД, параметры служебной CRM |
| `route.ts` | POST `/api/integrations/umniydom/v1/orders`, raw UTF-8, Bearer, SHA-256, ограничения |
| `store.ts` | SQLite inbox, очередь, квитанции, аренда обработки, журнал частей сообщений |
| `customer.ts` | Нормализация контактов, поиск контактов/компаний/лидов, неоднозначность |
| `crm.ts` | Изолированный mock и адаптер Битрикса с таймаутом и без слепого повтора записи |
| `message.ts` | Текст заказа, безопасная разметка, первый/последний источник, разбиение сообщений |
| `worker.ts` | Стадии обработки, повторы чтения, восстановление и ручной разбор |
| `register.ts`, `cli.ts` | Подключение в backend, отдельный приёмник и команды оператора |

Транзакция `BEGIN IMMEDIATE` одновременно сохраняет снимок, hash, квитанцию и
задание. Только успешный COMMIT позволяет вернуть 202. Повтор точных байтов
возвращает 200 и прежний ACK. Конфликт идентичности/тела — 409. SQL-уникальности:
`(source_id,event_id)` и `(source_id,order_id)`, без обхода регистром UUID.
SQLite использует WAL, `synchronous=FULL`, busy timeout 5 секунд.

Один обработчик на БД владеет арендой на 120 секунд; параллельные процессы
не берут второе задание, пока она действует. Все записи стадий проверяют токен
и срок аренды. Намерение создать лид/сообщение фиксируется **перед** REST-вызовом.
Источник, режим, портал и чат привязаны к БД: нельзя переключить существующую
тестовую базу в production или молча изменить получателя части заказа.

Первоначальный источник существующего лида/контакта не изменяется. Нет вызовов
обновления SOURCE_ID/UTM, комментариев в CRM, резервов, оплат, ERP и Тильды.
Денежный снимок хранится в копейках; неизвестные цены сохраняются как null.
Необязательный `order.business` хранится в исходном снимке и выводится в сообщении
менеджеру. Контактом остаётся человек; автоматического поиска/слияния компаний по
ИНН, создания компании или счёта это расширение не выполняет.

## Локальная проверка

Для интеграции и её тестов нужен **Node.js 24+**. При MODE=off SQLite-модуль
не загружается в основной backend; его прежний режим Node.js 20 сохраняется.

Из корня репозитория:

```powershell
npm -w @b24-app/backend run test:orders
node scripts/smoke-umniydom-orders.mjs
```

Smoke сам создаёт временную БД и случайный тестовый секрет, поднимает loopback
HTTP-сервер, отправляет вымышленный пример 20 раз, перезапускает сервер и запускает
mock worker. Затем останавливает процессы и удаляет временные данные. Секрет
не выводится. Сайт, его SQLite и рабочая CRM не затрагиваются.

## Приёмник для совместного sandbox-теста

Шаблон настроек: `packages/backend/orders.env.example`.
Ниже UUID **только вымышленного примера**; для проверки отправителем магазина
нужно взять фактический sourceId его установки через согласованную настройку.
Не менять identity базы магазина и не подставлять примерный UUID вместо неё.

```powershell
$env:UMNIYDOM_ORDERS_MODE = 'sandbox'
$env:UMNIYDOM_ORDERS_PROCESSOR = 'mock'
$env:UMNIYDOM_ORDERS_SOURCE_ID = '22222222-2222-4222-8222-222222222222'
$env:UMNIYDOM_ORDERS_DB = Join-Path $PWD '.local/orders/sandbox.sqlite'
$env:UMNIYDOM_ORDERS_SECRET = node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"
$env:PORTAL_DOMAIN = 'portal.example.bitrix24.ru'
npm -w @b24-app/backend run orders:serve
```

Приёмник слушает `http://127.0.0.1:3091`; путь POST указан выше. `/health` проверяет
локальный процесс. Секрет передать отправителю защищённым способом, не через
чат, Git или аргументы командной строки. Оба процесса должны использовать одно
значение. В другом терминале передать те же настройки и запустить:

```powershell
npm -w @b24-app/backend run orders:worker
# Или одно готовое задание:
npm -w @b24-app/backend run orders:once
# Последние 100 заданий, без контактных полей и исходного payload:
npm -w @b24-app/backend run orders:admin -- list
```

Mock хранит созданные лиды и сообщения только в `orders_mock_actions` этой БД.
В чат `chat19572` ничего не отправляется. Приёмник принимает только test=true;
production принимает только test=false. Worker — отдельный процесс, автоматически
вместе с HTTP backend не запускается.

## Повторы и ручной разбор

Безопасные сбои чтения CRM повторяются через 1, 5, 15, 60 и 240 минут.
После шести попыток запись остаётся в `manual`. Явный отказ по лимиту запросов
можно повторить; потерянный ответ, таймаут и 5xx записывающей операции не означают,
что операция не выполнилась.

- `lead_sending`: после потери ответа ищем лид по
  `ORIGINATOR_ID=umniydom:<sourceId>` и `ORIGIN_ID=<order.id>`. Одно совпадение
  позволяет продолжить; отсутствие или несколько результатов требуют проверки
  оператором. Не создаём ещё один лид автоматически.
- `notify_sending`: неизвестный результат отправки удерживается в `manual`.
  Оператор ищет в целевом чате квитанцию и номер части. Автоматического поиска
  по нестрогому совпадению текста и повторной отправки нет.
- `review_notified`: сообщение о неоднозначных клиентах доставлено; ждём решения.
- `done`: уведомление доставлено полностью, но это не статус работы менеджера.

После ручной проверки клиент выбирается командой (receipt и ID — фактические):

```powershell
npm -w @b24-app/backend run orders:admin -- resolve-customer inbox-UUID CONTACT 123
```

Допустимы CONTACT, COMPANY, LEAD. Команда предназначена доверенному оператору,
который уже проверил запись в CRM и соответствие покупателю. Она сохраняет
привязку и ставит уведомление на обработку, не создаёт/объединяет сущности.
После неоднозначности в чат придёт сообщение с выбранным клиентом.

Если найдена уже отправленная часть сообщения, зафиксировать её фактический ID:

```powershell
npm -w @b24-app/backend run orders:admin -- resolve-message inbox-UUID 456
```

Продолжатся только оставшиеся части. Все ID частей сохранены в
`orders_message_actions`. Если сообщения нет, оператор вручную доставляет
недостающую часть и затем фиксирует её ID этой командой. Если новый лид после
неопределённого исхода не найден, оператор проверяет CRM, создаёт его вручную
при необходимости и фиксирует через `resolve-customer`. Сброса стадии для
слепой повторной записи намеренно нет.

Исходный заказ содержит контакты. Не публиковать БД, mock-таблицы или payload.
Команда list выводит только технические статусы и идентификаторы CRM.

## Проверка импорта товаров

Прочитан исходник сайта `packages/backend/src/b24-readonly/export.mjs`:
он экспортирует `id: String(p.itemCode)`, а `buildCatalog` сохраняет `id: p.id`.
Следовательно, в этом конкретном пути каталожный ID происходит от ERP item_code.
Это не универсальная гарантия контракта v1 и не проверка существования каждого
товара в текущей ERP. Приёмник сохраняет ID сайта и текстовую позицию; не создаёт
товары и не пересчитывает цены. `manual-*` не сопоставляется по артикулу.

Экспорт сайта ссылается на SQL catalog-mirror рабочего backend. В текущей локальной
ветке b24-app этого модуля нет: перед будущим деплоем нужно совместить этот модуль
заказов с актуальной производственной веткой, а не заменять рабочую версию старой
локальной базой кода.

## До production

1. Совместный тест с фактическим отправителем сайта пройден 14.09.2026:
   2 заказа / 1 mock-лид / 2 mock-уведомления. Реальные права CRM проверяются отдельно.
2. Ответственный согласован и проверен: **Автозадачи, ID 2812, active=true**.
   Значение внесено в example-настройки. Не использовать старую неактивную запись 8.
   `crm.lead.fields` показывает ASSIGNED_BY_ID как необязательный параметр, но
   отсутствие явного назначения не гарантирует, что Битрикс не назначит автора
   вызова. Поэтому live требует явного ID служебной записи. Пользователей не
   создавали и существующих ответственных не меняли.
3. Настроить отдельный вебхук с необходимыми правами CRM и чатов; его владелец
   должен видеть контакты, компании и лиды целиком и иметь доступ к `chat19572`.
   Проверить права менеджеров на открытие и принятие созданных лидов.
4. Подтвердить начальную стадию лида. Чтением портала найден статус `NEW` —
   «Не обработан», но автоматически он не выбран: задать
   `UMNIYDOM_ORDERS_LEAD_STATUS` после проверки правил автоматизации портала.
5. Согласовать HTTPS URL, отдельный секрет, sourceId и постоянный путь SQLite.
   Данные держать на локальном постоянном диске; не на сетевой файловой системе.
   Для резервирования остановить writer либо использовать штатный SQLite backup;
   копирование только основного файла при работающем WAL недостаточно.
6. Сначала production приёмник с PROCESSOR=off; live worker включать отдельным
   согласованным шагом после готовности настроек. Sandbox-БД не переносить в prod.

Dockerfile поддерживает `--build-arg NODE_IMAGE=node:24-alpine`; значение по
умолчанию остаётся прежним. Сама сборка/замена контейнера в этой задаче не выполнялась.
Для основного backend действует AGENTS.md: вывести effective env и `/app/state`
из работающего контейнера, сохранить его как rollback, запускать с
`--network erpnext_frappe_network`, проверить внутренний и внешний `/health`,
read-only доступ к ERP и `docker inspect` на членство в сети. Дополнительно
проверить сохранность inbox при перезапуске и корректность отдельного worker.
Не использовать пути из runbook как готовые production-настройки.

## Проверки реализации

Изолированные тесты покрывают контракт, арифметику, неизвестные поля, raw hash,
токен/source/mode/размер, 20 параллельных POST, несколько процессов, перезапуск,
обрыв после COMMIT, SQL rollback, совпадения клиентов, недоступность CRM,
неопределённый исход создания лида и сообщения, части больших заказов и fencing.
Отдельно проверены отсутствие изменений источника/истории лида и запрет
переключения режима/получателя существующей базы.

Проверка типов и сборка всего приложения прошли. Общий набор существующих тестов
имеет отдельный воспроизводимый сбой `catalog card access is independent from
price access`: в тесте жёстко задан отдел 10, а текущий `SUPPLY_DEPARTMENT_ID` —
другой. Этот тест и права каталога в данной задаче не менялись.

Официальные описания использованных REST-методов:
[поиск дублей](https://apidocs.bitrix24.ru/api-reference/crm/duplicates/crm-duplicate-find-by-comm.html),
[создание лида](https://apidocs.bitrix24.ru/api-reference/crm/leads/crm-lead-add.html),
[отправка сообщения](https://apidocs.bitrix24.ru/api-reference/chats/messages/im-message-add.html).

## Ответ для задачи сайта

Приёмник b24-app v1 реализован: POST `/api/integrations/umniydom/v1/orders`,
Bearer, raw SHA-256, Idempotency-Key, SQL COMMIT перед ACK и стабильная квитанция.
Повторы, рестарт и потеря ответа проверены на изолированной БД. CRM обработка
отдельная, sandbox использует только mock. Рабочий чат согласован: chat19572.
Допустимо необязательное `order.business` с полями `name`, `inn`, `kpp`, `details`;
точные ограничения описаны в `contracts/b24-orders-v1.md`. Поле отсутствует у
частного заказа, email для счёта остаётся в `order.contact.email`, версия равна 1.
Для совместного sandbox-теста нужны фактический sourceId отправителя, согласованный
loopback URL/туннель и общий секрет через защищённую настройку. Сайт и production
не изменялись; отправку магазина автоматически не включали.
