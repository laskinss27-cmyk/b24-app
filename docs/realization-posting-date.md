# Дата проведения реализации

Решение владельца 06.10.2026: при дальнейшем первичном проведении реализации использовать текущую дату, а не дату создания черновика. Ранее черновик Delivery Note сохранял `set_posting_time=1`, и позднее проведение оставляло старую дату движения.

Теперь `submitRealization` перечитывает документ и допускает только непроведённую продажу. Клиент отправляет один PUT с `docstatus=1` и `set_posting_time=0`. ERPNext назначает дату и время по часам и часовому поясу своего сайта в той же транзакции проведения. Часы браузера/backend и дата создания черновика не используются. Успех подтверждается только `docstatus=1` в ответе; ошибка не запускает дополнительное сохранение или повтор.

Контракт проверен по установленному ERPNext v16.22.0: Delivery Note.validate вызывает TransactionBase.validate_posting_time, который при выключенном set_posting_time использует now_datetime(). Отдельного сохранения даты до проведения нет. Существующие проверки прав, принадлежности сделке, количества плана, сериализация операций и ERP-валидация остатков сохраняются.

## История и совместимость

Миграция и изменение уже проведённых документов не выполняются. При исправлении цены, восстановлении продажи или связанного возврата копия сохраняет исходные posting_date/posting_time и явно получает set_posting_time=1. Иначе копирование нового флага 0 могло бы перенести исторические движения на день исправления цены. Обычные вызовы ErpClient.submit для остальных операций не меняют режим даты.

Первичное проведение реализации с ранее явно заданной датой черновика также использует текущую дату согласно новому правилу. Прямое проведение через интерфейс самого ERPNext вне приложения этим изменением не регулируется. Отдельная сверка физического остатка требует данных о подсчёте и движениях; изменение даты будущих реализаций не доказывает исправление прошлых расхождений.

## Проверки

`erp/realization-posting-date.test.ts` проверяет единый запрос для старого черновика, отказ для проведённых/отменённых документов и возвратов, проверку ответа ERP, отсутствие повтора при ошибке и неизменность остальных submit. `erp/operations.test.ts` проверяет сохранение исторических даты/времени при изменении цены продажи и возврата с исходным флагом 0. Маршрутные регрессии `routes/deal-realization-safety.test.ts` сохраняют защиту от повторного проведения и превышения плана. Все входят в обычный автоматически обнаруживаемый набор.

Проверки используют изолированные фикстуры. Реальные складские документы ради тестирования не создаются и не проводятся.
