# Архитектура

## Назначение

`b24-app` — серверное приложение и единый React-интерфейс, встроенный в корпоративный портал Битрикс24. Оно оставляет сотрудников внутри Битрикс24, но выполняет складские операции через ERPNext.

## Компоненты

```text
Браузер сотрудника
        │ iframe Битрикс24
        ▼
https://app.example.com
        │
      nginx
        │ 127.0.0.1:3000
        ▼
b24-backend (Fastify + собранный React)
        ├── REST API Битрикс24
        └── http://frontend:8080
                 ▼
             ERPNext
```

Монорепозиторий:

```text
packages/backend   Fastify, OAuth, placement и /api/*
packages/frontend  React SPA
packages/shared    общие типы
```

Frontend собирается в `packages/frontend/dist`; backend отдаёт эти файлы и подставляет контекст конкретного placement.

## Источники данных

| Данные | Источник |
|---|---|
| сделки, контакты, компании, задачи, файлы | Битрикс24 |
| пользовательские поля и смарт-процессы | Битрикс24 |
| каталог складских позиций, цены, склады и остатки | ERPNext |
| приходы, реализации, списания, перемещения и возвраты | ERPNext |
| названия, модели, статусы и структурированные описания товаров | ERPNext |
| фотографии новых карточек | ERPNext |
| фотографии и резервные метаданные старого каталога | Битрикс24, когда в ERPNext нет значения |
| служебная память отдельных процессов | entity-хранилища Битрикс24 |
| публичный остаток Tilda (будущая односторонняя проекция) | ERPNext; Tilda не становится источником правды |

Точная карта entity stores, `/app/state`, связей ERPNext и поэтапного перехода на отдельную базу приведена в [sql-migration.md](sql-migration.md). На текущем этапе runtime использует `b24_app` только как readiness dependency: ограниченное соединение выполняет `SELECT 1`. Четыре пустые supply identity/graph tables уже созданы ручными migrations, но workflow-чтений, backfill и записей в них нет.

Регулярного зеркалирования остатков из Битрикс24 в ERPNext нет. Старые миграционные скрипты не являются частью рабочего контура.

Карточка товара редактирует справочные данные только в ERPNext. Описание хранится одновременно
в читаемом виде и как защищённая структура характеристик. Названия и типы полей будущих
фильтров нельзя менять или удалять через интерфейс; пользователь редактирует значения, а backend
повторно нормализует их и формирует отображаемый текст. Произвольные новые характеристики
сохраняются как дополнительные и не участвуют в фильтрах до отдельного сопоставления со схемой.

При создании товара приложение сначала получает совместимый числовой `productId` из технической
записи каталога Битрикс24, затем создаёт полную карточку в ERPNext. Характеристики, описание,
статус, цены и новое фото сохраняются в ERPNext; фото перед загрузкой уменьшается клиентом и
повторно проверяется backend.

Редактирование справочных полей карточки и цен проверяется раздельно. Пользователь без ценового
права получает текущие цены только для чтения, а backend игнорирует их в запросе сохранения
карточки. Новое фото готовой карточки загружается в ERPNext тем же защищённым маршрутом, что и
фото при создании товара.

## Входы в приложение

Один frontend выбирает экран по контексту:

- вкладка сделки `Товары 2.0`;
- левое меню `База товаров и услуг`;
- левое меню `Складской учёт`;
- левое меню `Снаб`;
- левое меню `Ремонты`;
- отчёт по продажам;
- мобильный вход `/m` для инвентаризации.

Точные обработчики перечислены в [api.md](api.md).

## Авторизация

Обычный путь:

1. Битрикс24 открывает placement и передаёт контекст пользователя.
2. Frontend получает краткоживущий токен через SDK Битрикс24.
3. Frontend отправляет токен и домен в backend.
4. Backend проверяет домен и вызывает REST API от имени текущего пользователя.

Для `/m` используется OAuth и защищённая cookie. Серверные токены ERPNext и служебные вебхуки во frontend не передаются.

## Безопасность

- Публичен только nginx на HTTPS.
- Backend и ERPNext привязаны к loopback или внутренней Docker-сети.
- Токены редактируются в логах.
- iframe разрешён только для `*.bitrix24.ru`.
- Секреты хранятся только в env-файлах сервера.
- Записывающие действия проверяют пользователя и контекст на backend.

## Развёртывание

На VPS работают:

- `b24-backend` — образ `b24-app:<git-commit>`;
- Docker Compose-проект `erpnext`;
- nginx и Certbot;
- ежедневный скрипт резервного копирования.

Текущий порядок деплоя и отката — в [runbook.md](runbook.md).

## Планируемая база workflow

Отдельная MariaDB-база `b24_app` вводится маленькими обратимыми этапами. ERPNext остаётся единственным источником правды физических остатков и проведённых складских документов, а Битрикс24 — CRM, идентификацией и правами. Прямой SQL к ERPNext запрещён. Отключённая конфигурация, ручной migration runner, metadata backup/restore drill и read-only readiness уже проверены; backfill, shadow reads и переключение модулей выполняются отдельными этапами после повторного backup/restore gate доменной схемы.

Первым проверен домен снаба: production-кардинальности требуют нормализованных документов, строк, типизированных document links и количественных line allocations. Точные наблюдения и граница change set приведены в [read-only аудите снаба](sql-supply-domain-audit-2026-08-20.md). Четыре one-statement DDL migrations применены отдельным ручным runner и независимо сверены при 0 domain rows; текущий workflow не изменён.

Read-only dry-run снаба развёрнут отдельно от workflow runtime. Он собирает полный snapshot через официальные API, строго проверяет внешние ссылки и выдаёт только агрегированный отчёт/hash; SQL-подключение и запись отсутствуют. Первый production run fail-closed остановился на legacy standalone/manual/historical links и line mismatches. Пользовательские экраны продолжают читать Bitrix/ERPNext; mirror apply, shadow comparison и source switch остаются отдельными этапами.

В развёрнутом read-only follow-up автономные закупки/перемещения представлены корнями графа, а ручные заявки на перемещение — отдельными Bitrix `supply_request` с внешним ID записи `ctv_tr_requests` и явным ключом `transfer-request:<id>`. Отображаемое имя не используется как identity. Второй dry-run устранил все 29 ожидаемых standalone/manual blockers без новых issue; пользовательский runtime и SQL source-of-truth не менялись. Исторические удалённые transfer не синтезируются без отдельной проверяемой tombstone-политики.

Первая tombstone-политика развёрнута read-only и не создала документы для пяти historical gaps: официальный ERP API доказал, что все 12 ссылающихся Stock Entry отменены (`docstatus=2`), а не проведены. Это корректный fail-closed результат, SQL domain rows остались нулевыми. Локальное уточнение разрешает evidence-only tombstone отдельно для однородной группы проведённых или однородной группы отменённых Stock Entry старше 24 часов: `source_missing` либо `source_missing_canceled`. Смешанное, draft или свежее evidence остаётся blocker. Политика восстанавливает только document links и не угадывает исходный Bitrix payload, строки или line allocations; отсутствие строки остаётся явным warning.

## Будущая проекция остатков в Tilda

Tilda подключается только отдельным поздним этапом и не входит в текущий SQL foundation. Поток односторонний: backend читает остаток через официальный ERPNext API, соединяет его только с `confirmed`-сопоставлениями из `b24_app` и публикует проекцию в Tilda через ограниченный интеграционный контур. Tilda не пишет остатки обратно и не используется для восстановления ERPNext.

Сопоставление хранится в SQL-таблице `tilda_product_mappings`, не в `/app/state`: уникальные Tilda UID/External ID, SKU, внешние `erp_item_code`/`erp_product_id`, статус `confirmed`/`unresolved`/`ignored`, parent/variant metadata, timestamps и audit source. Экспорт-baseline содержит 177 строк (131 parent, 46 variants), из них 150 stock-bearing SKU; 117 сопоставлены однозначно, 33 требуют ручной сверки. `unresolved` и `ignored` не попадают в публикацию. Реализация таблицы, backfill, Tilda API, ключи, cache/rate limits и расписание синхронизации требуют отдельных разрешённых этапов.
