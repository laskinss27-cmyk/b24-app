# Частичное снятие резерва

Решение пользователя 05.10.2026: разрешить прямое снятие части резерва снабжением и запрос снятия части из сделки.

В форме пользователь задаёт количество по выбранным позициям; пустое поле и ноль оставляют позицию в резерве. Есть явная кнопка выбора всего резерва. Позиция определяется ID строки SQL-резерва, а не товаром: одинаковый товар на разных складах/этапах не объединяется. Причина необязательна. Права создания запроса и прямого снятия остаются прежними.

Новый запрос сохраняет точные позиции и количества. Согласование снимает только их; отказ ничего не снимает. Пока запрос ожидает решения, прямое снятие блокируется: сначала нужно согласовать или отклонить запрос. После частичного снятия можно создать следующий запрос. Срок, привязка сделки, физический остаток ERP и непомеченные позиции не меняются.

Количество проверяется в SQL-транзакции под блокировками, с точностью до 9 десятичных знаков. Отрицательные, нулевые, повторные, чужие строки и превышение текущего активного количества отклоняются. Если после подачи запроса товар использовали/сняли/сократили и запрошенного количества уже нет, согласование отклоняется целиком: запрос остаётся ожидающим, снабжение отклоняет его и менеджер подаёт актуальный. Для истёкшего резерва согласование также запрещено. Повтор с тем же ключом команды не снимает товар повторно; форма сохраняет ключ при повторе неизменённого ввода. Закрывать форму и заново отправлять после неопределённой ошибки не следует без обновления реестра.

Активный остаток продолжает вычисляться штатной SQL-проекцией `reserved_qty - consumed_qty - released_qty - shortfall_qty`. При ненулевом остатке статус резерва сохраняется; `released` ставится только после полного снятия. История содержит выбранные количества и отдельные события по строкам. Каталог продолжает читать те же суммы активного резерва.

## Схема и выпуск

Источник истины не меняется: существующие `stock_reservations`, `stock_reservation_lines`, `stock_reservation_release_requests` в SQL. В последнюю таблицу добавляется nullable JSON `release_lines_json`, содержащий массив `{lineId, quantity}`. Для старых записей NULL означает прежнее снятие всего активного резерва. Новые запросы старого API без `lines` при создании также фиксируют весь текущий состав; явно пустой массив не означает полную отмену.

Перед обычным выпуском выполнить `node scripts/reservation-release-migration.mjs` с выделенной migration identity и подтверждёнными настройками БД (`B24_APP_DB_HOST/PORT/NAME`, `B24_APP_MIGRATION_DB_USER/PASSWORD`). Скрипт идемпотентно добавляет колонку и проверяет её наличие, не меняя резервы. Не передавать секреты аргументами команд или в логи. Runtime DML-пользователю не выдавать DDL.

Миграция совместима с работающей старой версией. **Откат приложения после появления новых ожидающих частичных запросов требует сначала отклонить такие запросы в новой версии:** старая версия не знает их состав и может снять весь резерв при согласовании. Колонку при откате сохранять. Не выполнять отмену или согласование запросов напрямую SQL-командой.
