## Как пользуется менеджер

1. В приложении открыть Telegram → Аккаунты и привязки. Назвать рабочий аккаунт, подтвердить QR в Telegram → Настройки → Устройства. Если включена двухэтапная проверка, ввести пароль в экран приложения.
2. Загрузить список личных диалогов, выбрать клиента и номер сделки. Сервер проверяет существование сделки и права текущего пользователя Битрикс24.
3. При первой привязке загрузить последние 100 сообщений; дальше сервер автоматически сохраняет новые входящие и исходящие. Менеджер продолжает отвечать из обычного Telegram.
4. Читать сообщения во вкладке «Переписка» карточки сделки или через кнопку Telegram внутри приложения. Сообщения хранятся в базе приложения, а не как комментарии стандартной ленты Bitrix24.

Одна собственная пара API ID/API hash используется приложением; каждый из восьми аккаунтов отдельно подтверждает свою сессию. Сбор работает в backend независимо от браузера, пока работает сервер. Закрытие приложения не отключает Telegram. Кнопка отключения останавливает сбор и пытается отозвать только сессию B24 CRM, сохраняя историю сделок. Если отзыв не удался, интерфейс предлагает завершить эту сессию в Telegram → Устройства.

## Источник, хранение и совместимость

Предыдущий источник MSG-01 — отдельный пилот на 5198, авторизация и непроверенные привязки только в памяти процесса. Новый источник MSG-02–04 — MTProto через teleproto 1.229.3 внутри backend, SQLite WAL в B24_STATE_DIR/telegram/telegram.sqlite. Постоянная база содержит аккаунты, проверенные привязки, курсоры и сообщения. Пилот сохранён как историческая проверка; его данные автоматически не импортируются. Из текущего процесса пилота сессия не экспортируется: первый вход в новый сборщик требует отдельного QR. Обе сессии отображаются в Telegram как разные устройства.

Сессии, peer/accessHash и содержимое сообщений шифруются AES-256-GCM с отдельным случайным IV и AAD, привязанными к идентификаторам записей. Названия аккаунтов/диалогов, идентификаторы, номера сделок и временные метки остаются метаданными SQLite. TELEGRAM_SESSION_KEY — отдельный постоянный ключ из 32 случайных байт (64 hex); это не API hash. Потеря/смена ключа делает сохранённые данные нечитаемыми. Нужно хранить защищённые резервные копии базы и ключа; для согласованного файлового переноса сначала остановить сборщик либо использовать SQLite backup. Не копировать только .sqlite при работающем WAL. Никаких значений ключей в Git/документах/логах.

Один процесс backend владеет базой и каждой MTProto-сессией. При переносе локальной базы на сервер сначала остановить локальный постоянный сборщик, затем перенести базу с WAL согласованным способом и исходный ключ. Одновременно использовать одну и ту же сохранённую сессию на двух хостах нельзя. Авторизация и курсоры сохраняются при обычном перезапуске; попытка расшифровки неверным ключом показывает ошибку, не очищая сессию.

## Сбор и ограничения версии

- До восьми профилей на приложение. Отключённые профили сохраняют своё место и свою Telegram-идентичность: повторное подключение — того же аккаунта. Удаление профиля/замена сотрудника и перенос истории между сделками пока не реализованы.
- До 100 явно привязанных личных диалогов на профиль. Для выбора загружаются последние 500 диалогов, исключаются группы, боты, Избранное и удалённые пользователи. Поиск выполняется только в этом списке. Секретные чаты не поддерживаются.
- Первоначально последние 100 сообщений, не полный архив. Затем страницы по 100 сообщений, до десяти страниц за цикл; следующий цикл продолжает с сохранённого курсора. При восстановлении соединения догружаются доступные Telegram сообщения новее курсора. Сообщения, удалённые до получения сборщиком, восстановить нельзя.
- Новые обновления инициируют сбор, резервная проверка — каждые 15 секунд. При ограничениях Telegram выдерживается FLOOD_WAIT, при сетевых сбоях повтор через 60 секунд. Аккаунты работают независимо. Это не обещание фиксированной задержки: она зависит от Telegram, сети и числа диалогов.
- Исправления и удаления обновляют уже сохранённые сообщения; после простоя сверяются по 100 сохранённых ID диалога за цикл с круговым проходом истории. Старые исправления могут появиться с задержкой. Удалённый текст заменяется отметкой удаления. Самоуничтожающиеся сообщения с ttlPeriod не сохраняются. Это синхронизируемая история, не неизменяемый архив.
- Вложения пока обозначаются типом; файлы, фотографии и голосовые не скачиваются. Отправка сообщений, отметка прочтения и импорт контактов отсутствуют.
- Пауза сохраняет историю и прекращает дальнейшие запросы диалога после уже начатого запроса; его запоздалый результат не сохраняется. При возобновлении догружаются доступные сообщения после курсора. Отключение аккаунта сохраняет историю, но очищает его сессию.
- Один диалог одного аккаунта связан с одной сделкой. Автоматического сопоставления по имени/телефону нет. Лиды и MAX в эту реализацию не входят. Отдельная мобильная страница подсчёта /m не получает Telegram: там другой механизм входа; адаптивная вкладка CRM проверена на ширине 360 px.

## Доступ

Все API требуют пользовательскую OAuth-авторизацию разрешённого портала и действующего пользователя. Управлять подключением может создавший его сотрудник либо владелец приложения APP_OWNER_USER_ID. Просмотр истории и привязка требуют deals.view и реального crm.deal.get с токеном текущего читателя; системного webhook fallback в production нет. Имеющий доступ к сделке видит все связанные с ней рабочие переписки. Перед каждым чтением истории CRM-права проверяются заново. Данные между аккаунтами разделены составным ключом account/chat/message.

MTProto-сессия технически имеет широкий доступ ко всему Telegram-аккаунту. Ограничение выбранными клиентскими диалогами реализовано нашим кодом; оно не является ограниченной Telegram OAuth-областью. Библиотека получает обновления аккаунта, список диалогов может содержать последние сообщения, но UI списка показывает только названия; отдельные запросы истории и сохранение выполняются только для явно привязанных чатов. QR, пароль, API hash и сессия не журналируются; пароль используется только во время входа.

## Сетевой сбой и отдельный SOCKS5-транспорт

Сетевая пауза (60 секунд) не является FLOOD_WAIT. UI получает понятную ошибку сетевого соединения; повторная команда подключения во время неё возвращает 503, при подтверждённом ограничении Telegram — 429. После паузы активный профиль восстанавливает сохранённую сессию, не запускает лишний QR и не меняет идентичность аккаунта. Регрессия закреплена service.test.ts.

Файловая конфигурация может дополнительно содержать proxy: объект с ip (адрес/имя SOCKS), port (1–65535), socksType: 5, необязательными username/password. Некорректный объект отклоняется без вывода секретов; config.test.ts проверяет это и отсутствие смешивания источников. При конфигурации через переменные окружения файл целиком игнорируется, включая proxy. Прокси передаётся только TelegramClient: обращения к ERPNext/Bitrix и маршрут хоста не меняются.

Для пользовательской Netzrun-подписки подготовлен отдельный Xray 26.3.27 из официального ghcr.io/xtls/xray-core. Образ закреплён digest sha256:592ec4d11f656db95598d01e76dbcc6e002d67360b96a5436500a938230f52c7. Контейнер b24-telegram-egress в erpnext_frappe_network, SOCKS 1080 только внутри Docker, обязательный случайный пароль, нет опубликованных портов. Запуск без capabilities, read-only, no-new-privileges, uid 65532, лимиты 128 MiB/0.5 CPU. Конфигурация вне Git в /srv/b24-telegram-egress (0700); config.json (0600, uid 65532), proxy.json (0600, root), image.txt содержит закреплённый образ. Эти пути подтверждены при установке на текущем сервере, не являются универсальными значениями для другого развёртывания.

Конфигурация Xray валидна, но связь через него не прошла. Поэтому proxy пока не добавлен в рабочий Telegram config.json. Неработающий транспорт нельзя считать готовым подключением. После исправления сети: проверить TCP/TLS и реальный MTProto через контейнер, сохранить защищённую копию текущего config.json, атомарно добавить proxy без изменения apiId/apiHash/key; включить через штатный релиз/контролируемый перезапуск, проверить автоматическое восстановление и lastSync. Подписка и исходный ключ хранятся отдельно от кода, не публикуются в отчётах. При ротации узлов обновлять защищённую конфигурацию и проверять её перед перезапуском; автоматическое обновление/переключение VPN-узлов пока отсутствует.

## Рабочий альтернативный маршрут: WARP

По предложению владельца проверен Cloudflare WARP в изолированном контейнере. На принятие условий бесплатного сервиса и регистрацию сервера получено отдельное явное согласие. Официальный пакет cloudflare-warp 2026.8.2100.0, APT-репозиторий Cloudflare с проверкой подписи; пакет SHA256 6b0a3e8df24d785c7b218dd5089628e2e153c8838ca077759226352f182512c3. Клиент зарегистрирован один раз; статус Connected/healthy, запрос Cloudflare trace через SOCKS подтвердил warp=on, TLS-запрос к venus.web.telegram.org/apiws прошёл. Прямой маршрут и Netzrun остаются недоступными; WARP — другой проверенный путь. Реальная авторизация/синхронизация MTProto проверяется после штатного выпуска backend с поддержкой SOCKS.

Постоянный сервис собирается из scripts/telegram-egress в чистом опубликованном checkout с label полного SHA. Debian и Xray закреплены digest, WARP — версией. Контейнер b24-telegram-warp на erpnext_frappe_network, без host network, без опубликованных портов и без изменения маршрутов хоста. NET_ADMIN ограничен сетевым namespace контейнера; no-new-privileges, 384 MiB, 0.5 CPU. WARP слушает только 127.0.0.1:40000, Xray от uid 65532 предоставляет SOCKS5 1080 с паролем другим контейнерам. Зависимость только Telegram: рабочий конфиг proxy.ip=b24-telegram-warp; Bitrix/ERP используют прежнюю сеть.

Регистрация WARP хранится в /srv/b24-telegram-warp (0700), монтируется в /var/lib/cloudflare-warp; перед заменой контейнера остановить предыдущий клиент, не запускать две копии одного состояния. Отдельная /srv/b24-telegram-warp-proxy/config.json содержит только настройки прокси, включая пароль, файл 0600 uid 65532; родитель 0700. Секреты и регистрация не входят в образ/Git. Перезагрузка всего VPS и автоматическое восстановление после реального отказа провайдера ещё не проверены.

## Уточнение маршрута и перезапуска

Чистый WARP пропускает HTTPS Telegram, но соединение MTProto к DC2 закрывается: WARP сообщает timeout подключения к upstream. Дополнительная проверка без пользовательской сессии подтвердила рабочее MTProto через цепочку WARP → существующая Netzrun-подписка → Telegram. Xray использует VLESS/TLS узла Netzrun с streamSettings.sockopt.dialerProxy=warp; outbound warp — SOCKS 127.0.0.1:40000. Параметры подписки остаются в защищённом серверном config.json; новая подписка не оформляется. Эксплуатация зависит от обоих сервисов и срока Netzrun. Прежняя конфигурация только WARP сохранена как config-warp-only.json, первоначальная конфигурация backend — config-before-warp-FULL_SHA.json рядом с рабочим файлом.

При проверке перезапуска контейнера обнаружен оставшийся /run/dbus/pid. Entrypoint изменён на dbus-daemon --nopidfile; постоянный контейнер требует tmpfs /run (rw,nosuid,nodev,size=16m), чтобы служебные PID/socket-файлы не переживали перезапуск. Проверка реального restart и автоматического восстановления обязательна для приёмки этой конфигурации.

## Автоматическая привязка по телефону (MSG-05)

Решение пользователя 09.10.2026: при нескольких открытых сделках выбирать самую новую. Новизна определяется **датой создания**, затем ID по убыванию, а не датой изменения. Прежний ручной режим сохранён; требование «сохранять только вручную выбранные диалоги» заменено разрешённой автоматической привязкой для включённого аккаунта.

Менеджер открывает «Переписка» → «Аккаунты и привязки» → «Включить автопривязку» у своего подключённого аккаунта. Приложение получает OAuth refresh grant из BX24 SDK, сразу обменивает его, проверяет портал, реального активного владельца и deals.view. Это одноразовое включение, браузер дальше не требуется. Администратор может выключить чужую настройку, но включить её от чужого имени не может. Отключение всего Telegram-аккаунта также выключает автопривязку. Выключение только автопривязки оставляет текущие связи и сбор сообщений.

Алгоритм использует только phone, который Telegram сам возвращает для собеседника. Не импортирует контакты, не угадывает номер/страну по имени или username. Отдельно ищет CONTACT и LEAD через crm.duplicate.findbycomm; затем crm.item.list по contactIds (включая дополнительный контакт сделки) и leadId с stageSemanticId=P. Каждая выборка отсортирована по createdTime/id DESC; объединяются кандидаты по всем найденным CRM-записям. Нельзя использовать частичный результат при отказе одной выборки. Перед сохранением crm.deal.get повторно проверяет существование, доступ и открытый статус. Сделки/контакты в CRM не создаются и не редактируются: связь и сообщения остаются в SQLite приложения, видны во вкладке сделки.

Текущие границы: 500 недавних личных диалогов, максимум 10 доступных номеров за минутный цикл на аккаунт, общий ограничитель фоновых CRM-вызовов — два в секунду на все аккаунты (при восьми аккаунтах цикл может занять дольше минуты), повтор для ненайденных через пять минут; длительность первого прохода зависит от количества доступных номеров, дубликатов и аккаунтов; при тысячах кандидатов он может занять несколько часов. Старые диалоги вне окна — ручной выбор через существующий ограниченный список/после новой активности; полной индексации архивов нет. До восьми аккаунтов, до 100 связей на каждый; при достижении лимита видна ошибка, история не удаляется. Отказ CRM отложит автопоиск на пять минут, но не остановит существующий сбор Telegram. FLOOD_WAIT обрабатывается существующим транспортом с серверной паузой. Скрытый номер, отсутствие клиента или открытых сделок оставляют диалог непривязанным. Поиск по лидам поддерживается, отображение истории в карточке самого лида и MAX не добавлены.

Миграция совместима и добавляет таблицы telegram_auto_settings, telegram_auto_links, telegram_crm_credentials. Все старые настройки по умолчанию выключены, прежние связи/паузы/история не меняются. Одна пара OAuth-токенов на владельца зашифрована существующим AES-GCM ключом с AAD crm:ownerId. Ротация сериализована между аккаунтами владельца, новый refresh сохраняется до последующих запросов; проверка user.current и политики повторяется для рабочего цикла. Токены не возвращаются через status/accounts и не попадают в обычные frontend-запросы. Refresh grant передаётся только при явном включении. Ошибки пользователю обезличены; системного webhook fallback нет. Неудачная/отозванная CRM-авторизация требует повторного включения из Битрикс24, новый QR Telegram для этого не нужен.

Гонки: после CRM-запросов перепроверяются active, версия настройки и наличие уже созданной связи. Ручная привязка/пауза, отключение или выключение автопривязки побеждают поздний ответ. Первоначальное правило о бессрочной неизменности сделки уточнено пользователем в MSG-06: старая история сохраняется, последующая переписка может перейти в новую сделку после закрытия прежней.

## Повторное обращение и следующая сделка (MSG-06)

Во время реализации пользователь отдельно выбрал: **«Продолжать сохранять в старую до создания новой»**. Нет отдельного буфера/очереди неразобранной переписки. Например: старую сделку закрыли в 10:00, клиент написал в 11:00, новую создали в 12:00 — сообщение 11:00 остаётся в старой, сообщения начиная с 12:00 идут в новую. Поиск по номеру выбирает новейшую открытую сделку, созданную позже текущей (при одинаковом времени — больший ID). Пока текущая ещё открыта, она сохраняет диалог независимо от других открытых сделок.

Граница маршрутизации — max(дата создания новой, MOVED_TIME текущей закрытой сделки, дата включения авто). MOVED_TIME означает время перехода в текущую стадию; если CRM не отдаёт корректные даты, переключение откладывается с ошибкой. Текущая сделка проверяется повторно перед сохранением, её переоткрытие отменяет переключение. Если новая уже существовала до закрытия прежней, сообщения до закрытия сохраняются в прежней. При первом включении/повторном включении после выключения не перераспределяем уже накопленную историю до включения. Это позволяет безопасно мигрировать существующую ручную связь 37974. Автоматическое правило относится ко всем включённым личным диалогам аккаунта; приостановленные связи никогда не возобновляет.

Сервер обнаруживает изменения циклически, а не мгновенно в момент создания сделки. Сообщения после установленной границы, успевшие сохраниться в прежней за время задержки, атомарно получают новую принадлежность. Сообщения между закрытием и созданием остаются в прежней. Новая таблица telegram_deal_routes сохраняет интервалы каждого диалога; курсоры Telegram и исходные message_id не сбрасываются, повторная догрузка/редактирование/удаление учитывают эти интервалы. В SQLite по-прежнему один экземпляр сообщения. История в старой карточке остаётся видимой; historical-связь не раскрывает номер следующей сделки пользователю без проверки доступа к ней. Версия маршрутизации сбрасывает устаревший кэш/пагинацию вкладки, чтобы хвост не отображался в двух сделках.

Миграция добавляет интервалы, привязывая всю текущую историю к прежней сделке, и enabled_at к настройке. Строки сообщений, шифротексты и авторизованная сессия при миграции не изменяются. Первоначальная версия MSG-05 без интервалов не выкладывалась. До первого включения авто старый rollback полностью совместим. После фактического переключения на следующую сделку нельзя считать старый UI до MSG-06 совместимым для просмотра архивных карточек: данные останутся в базе, но старый код не умеет показать историческую связь. Для восстановления после таких переключений нужен совместимый выпуск с интервалами; таблицы/сообщения при откате не удалять и не склеивать.

Если новая сделка успела создаться и закрыться целиком между проверками, поиск только открытых не восстановит её автоматически. Распределение по всей истории стадий CRM, определение темы сообщения (поддержка старого заказа или новая покупка), скрытые номера и MAX остаются вне объёма. Тексты не отправляются клиентам и в ленту CRM; доступны в штатной вкладке приложения.

Уточнение реального OAuth-ответа: поле domain относится к серверу авторизации, не к CRM. Фоновый доступ проверяет client_endpoint: HTTPS, точный hostname настроенного портала, путь /rest/, без userinfo/порта/query/fragment; затем user.current и deals.view. Из client_endpoint не строятся произвольные запросы — используется только заранее настроенный portalDomain. Неверный endpoint не получает токен.
