# Сайт → b24-app: приём заказов v1

Статус: сторона сайта реализована, рабочий b24-app не подключён.
Версия контракта 1, 14 сентября 2026 года.

## Границы ответственности

Сайт сохраняет неизменяемый снимок заявки и событие `order.created` одной
транзакцией SQLite. Он не ищет людей в CRM, не создаёт лиды/задачи в Битриксе,
не меняет ERP/Тильду и не занимается резервом или оплатой.

b24-app принимает событие в свою SQL-входящую очередь, затем независимо
сопоставляет клиента и создаёт задачу/уведомление. Подтверждение HTTP означает
только надёжное сохранение входящего сообщения, НЕ завершение CRM-операций.
Не ждать Битрикс перед ответом: иначе его недоступность сломает надёжный приём.

## HTTP

`POST /api/integrations/umniydom/v1/orders`

- HTTPS для production. Для sandbox сайт разрешает только HTTP loopback:
  127.0.0.1, localhost или ::1. Приёмник для совместной проверки можно поднять
  рядом либо направить через согласованный SSH-туннель; в этом этапе туннель не создавался.
- `Authorization: Bearer <shared-secret>` — отдельный секрет интеграции,
  32–256 символов `[A-Za-z0-9_-]`. Не CRM webhook, не административный токен сайта.
  Секрет генерировать при согласованном подключении, не хранить в Git/промпте.
- `Content-Type: application/json`, `Accept: application/json`.
- `Idempotency-Key` = `eventId` из тела.
- `X-Content-SHA256` = SHA-256 точных байтов UTF-8 тела, lowercase hex.
  Это контроль целостности, НЕ подпись или замена аутентификации.
- Максимальное тело 256 КиБ (262144 байта); передающий таймаут 15 секунд.
- Перенаправления не выполняются, включая 307/308: токен на другой URL не отправляется.

Не логировать Authorization, контактные поля или полное тело. Приёмник должен
проверять собственные ограничения тела, аутентификацию, hash, Idempotency-Key,
версию, структуру и арифметику; не полагаться только на валидацию сайта.
Разрешённые `sourceId` привязать к секрету/настройке отправителя. Не принимать
произвольный sourceId как доверенную организацию только потому, что поле есть в JSON.

## Данные

Полный вымышленный пример: `order-created.v1.example.json` в этом каталоге.
Нормативная исполняемая схема сайта:
`packages/storefront/src/order-delivery/contract.ts` (`deliveryEnvelopeSchema`).
Для контактов/источников она использует `orders/schema.ts`. Никаких неизвестных
полей во внешних объектах принимать не следует. Пример обязан проходить тест схемы.

| Поле | Значение |
| --- | --- |
| `schemaVersion` | Число 1 |
| `eventType` | Только `order.created` |
| `eventId` | UUID события, постоянный при всех повторах |
| `sourceId` | UUID установки сайта из `order_delivery_identity`, сохраняется в резервной копии |
| `occurredAt` | Время создания заявки, ISO 8601 UTC |
| `order.id` | UUID заказа для внешней интеграции, не ID клиента или CRM |
| `order.number` | Читаемый номер `UD-000001`; не использовать как уникальный ключ интеграции |
| `order.channel` | `storefront` или `preview` |
| `order.test` | Тестовый признак; preview всегда true |
| `order.contact` | name, phone, email (может быть пустым), comment (может быть пустым) |
| `order.business` | Необязательный снимок организации: name, inn, kpp, details |
| `order.fulfillment` | Необязательный строгий объект получения: pickup либо delivery с address |
| `order.consent` | true, разрешение связаться по этой заявке; не маркетинговое согласие |
| `order.currency` | RUB |
| `order.items` | От 1 до 50 строк, количество каждой позиции 1–99; productId уникальны у заказов без комплектов |
| `order.bundles` | Необязательные группы комплектов; правила в [расширении](b24-bundles-v1.md) |
| `order.totals` | subtotalMinor, discountMinor, totalMinor, knownSubtotalMinor |
| `order.promo` | null или снимок id, code, kind (`percent`/`fixed`), value |
| `order.attribution` | null или first/last; любой из двух переходов может быть null |
| `order.attributionTrust` | `browser_reported`, это сведения браузера, не подтверждение площадки |
| `order.payment` | `not_requested`; онлайн-оплаты нет |
| `order.reservation` | `not_reserved`; резерв не выполнялся |

Позиция: `productId` (непустая строка до 100), `origin` (`catalog`/`manual`),
`name` (до 1000), `brand` (до 160 или null), `quantity`, `unitPriceMinor`,
`totalMinor`, `availability` (`in_stock`, `on_order`, `unavailable`, `unknown`),
`stockWarning` (до 500). `manual-UUID` обязательно имеет origin=manual.
**productId — идентификатор сайта, не обещание совпадения с ERP item_code или SKU.**
Соответствие каталога проверить по реальному импорту b24-app. Ручные товары
автоматически с ERP по артикулу не объединять; при отсутствии связи передавать
текстовую позицию/на ручную проверку, не создавать фиктивный товар ERP.

Деньги — целые неотрицательные безопасные числа в КОПЕЙКАХ, не рубли.
unitPriceMinor и totalMinor позиции могут быть null (цена по запросу).
У известной цены totalMinor позиции = quantity × unitPriceMinor.
knownSubtotalMinor = сумма только известных позиций, ДО скидки промокода.
У комплектов цены компонентов уже учитывают цену набора; см. [расширение](b24-bundles-v1.md).
Если все цены известны, subtotalMinor равен этой сумме, а totalMinor =
subtotalMinor − discountMinor; скидка не превышает subtotalMinor.
Если есть неизвестные цены: subtotalMinor и totalMinor null, discountMinor=0,
promo=null. Не превращать неизвестную сумму в ноль и не подменять актуальной ERP-ценой.
Для промокода kind=percent value означает процент, kind=fixed — копейки.
Историческая скидка не требует проверки сегодняшнего срока действия промокода.

`business` отсутствует у частного заказа. Если поле передано, объект содержит только
`name`, `inn`, `kpp`, `details`: название после trim — 2–200 символов; ИНН — ровно
10 или 12 цифр; КПП — пустая строка либо ровно 9 цифр; дополнительные реквизиты —
строка до 2000 символов. Email для счёта остаётся в `order.contact.email`.
`schemaVersion` остаётся равным 1: расширение необязательное, поэтому ранее
сохранённые события без `business` принимаются без преобразования и повторной
отправки. Наличие `business` — заявление покупателя, а не подтверждённая компания.

`fulfillment` отсутствует в старых событиях. Если поле передано, допустим только
один из строгих вариантов: `{ "method": "pickup" }` либо
`{ "method": "delivery", "address": "..." }`. У pickup адрес запрещён. У
delivery адрес обязателен, после trim содержит 5–500 символов и не содержит
запрещённых управляющих символов. Дополнительные ключи и другие методы запрещены.
Поле не меняет `schemaVersion: 1`, endpoint, подпись тела или идемпотентность.

Контакты: name 2–100 символов, phone до 40 (7–15 цифр, разрешены ведущий +,
пробелы, скобки, дефисы), email пустой либо корректный до 254, comment до 2000.
Переход: kind (`utm`/`referrer`/`direct`), source, medium, campaign, content,
term (строки до 120), referrerHost (hostname до 253), landingPath (путь до 200,
без query/hash), at (ISO UTC). Пустые метки разрешены. Все тексты — недоверенные
данные; экранировать также разметку Битрикса, не исполнять HTML/BBCode из комментария.

v1 передаёт только первоначальное создание. Последующие изменения статуса,
в том числе отмена до доставки сообщения, не изменяют исходное событие и пока
не синхронизируются. Нужен отдельный будущий контракт для обновления статусов;
нельзя трактовать это сообщение как текущее состояние заказа на сайте.

## Надёжный приём и подтверждение

В SQL приёмника нужны уникальности `(sourceId,eventId)` и `(sourceId,order.id)`.
Квитанция создаётся один раз и сохраняется с hash/телом в одной транзакции.
Параллельный повтор того же события и точного тела возвращает прежнюю квитанцию.
Тот же eventId с другим hash/order.id либо другое событие для того же order.id —
409, не новый заказ. Сравнивать hash сырых байтов: сайт повторяет точную сохранённую
строку, не пересобирает её из актуальных товаров/контактов.

После COMMIT входящей записи вернуть 202 (для повтора допустим 200) и JSON:

```json
{
  "schemaVersion": 1,
  "eventId": "11111111-1111-4111-8111-111111111111",
  "sourceId": "22222222-2222-4222-8222-222222222222",
  "orderId": "33333333-3333-4333-8333-333333333333",
  "status": "accepted",
  "receiptId": "inbox-12345"
}
```

Только эти поля. Content-Type application/json, тело не более 8192 байт.
receiptId — строка `[A-Za-z0-9_-]{1,100}`, стабильная при повторах.
Не возвращать в квитанции контактные поля, произвольные URLs, CRM-токены и
тексты исключений. Три идентификатора должны точно совпадать с запросом.
Просто HTTP 200 без правильного тела **не считается приёмом**.

Ошибки: 400/422 неверный контракт, 401/403 неверный доступ/режим/sourceId,
409 конфликт идемпотентности, 413 слишком большое тело, 429 перегрузка,
5xx временная недоступность. Сайт не сохраняет и не показывает тело ошибки.

Сайт автоматически повторяет NETWORK_ERROR, 408, 429 и 5xx: интервалы 1 мин,
5 мин, 15 мин, 1 ч, 4 ч; после шестой неудачи останавливается в failed.
Остальные HTTP-ответы, redirect, неверная квитанция — failed до ручного повтора.
Ответ, потерянный после COMMIT приёмника, обрабатывается тем же повтором.

## Отдельная обработка b24-app

1. Нормализовать телефон/email. Искать существующие контакты, компании и лиды
   по реальной модели b24-app. Не сопоставлять только по имени, не объединять автоматически.
2. Один однозначный существующий клиент/лид — привязать заказ к нему.
   Конфликт совпадений телефона/email или несколько кандидатов — ручной разбор.
3. Если совпадений нет, создать нового лида. Повтор входящего события не создаёт второго.
4. Создать задачу ИЛИ уведомление со ссылкой на найденного/нового клиента или
   лида, номером/составом/суммой заказа и источником перехода. Выбор механизма,
   ответственного, группы/воронки требует конфигурации, не угадывать.
5. **Не писать источник этого заказа в существующий лид/контакт:** не менять
   SOURCE_ID/UTM, не добавлять специально комментарий/заметку в лид, не переписывать
   его историю. Источник хранится с заказом и отображается в задаче/уведомлении.
6. Сохранять шаги обработки и внешние CRM ID. Повтор после ошибки Битрикса
   не должен повторно создавать лид/задачу. Учесть неопределённый исход запроса:
   перед повтором reconcile по внешнему ключу; если API не позволяет надёжно
   найти результат, ручной разбор, а не слепая повторная запись.

Контактом остаётся человек. Если передан `business`, приёмник сохраняет исходный
снимок вместе с событием и явно показывает название, ИНН, непустой КПП и details
менеджеру в уведомлении. Расширение само не ищет и не объединяет компании по ИНН,
не создаёт компанию или счёт и не прячет реквизиты в комментарии лида.

Яндекс + medium=maps позволяет подписать «Яндекс Карты»; один yandex.ru не
доказывает переход с Карт. Указывать первый и последний источники отдельно;
campaign может различать точки. При пустых данных — «Источник не определён».
Не выдумывать название точки из незнакомой метки.

В production приёмник отклоняет test=true/preview до CRM-операций. В sandbox
приёмник принимает только тестовые события и использует заглушки CRM/изолированные
данные. Нельзя молча превращать тестовую заявку в рабочую.

## Сторона сайта и эксплуатация

- SQL v2: order_delivery_identity и order_delivery в существующей orders.sqlite;
  новые события создаются атомарно с новыми заказами. Старые записи не backfill.
- Стабильные UUID и сериализованный payload сохраняются в резервной копии.
  После восстановления не регенерировать UUID/sourceId; старый код v1 с этой
  базой несовместим. Копирование установки для независимого сайта требует
  отдельной процедуры идентичности, не менять identity у уже поставленных событий.
- SQLite lease 60 с и token fencing защищают конкурирующих workers. После
  аварии expired sending можно забрать снова. HTTP максимум 15 с.
- Статусы доставки pending/sending/retry/accepted/failed независимы от new/
  in_progress/done/cancelled заявки. accepted не означает «обработан менеджером».
- Ручной повтор доступен локальной админке, с токеном и ревизией доставки.
  Он разрешён только из retry/failed, не меняет payload/UUID/статус заявки.
  Сбрасывается счётчик последовательных неудач, общий attempts сохраняется.
- `npm run orders:deliver` — обработать одну готовую запись и выйти.
- `npm run orders:worker` — отдельный цикл; 15 с ожидания при пустой очереди/
  ошибке, 1 с после обработки. Прерывание SIGINT/SIGTERM останавливает цикл.
- Настройки — `config/orders-delivery.env.example`, реальные значения через
  окружение процесса либо packages/storefront/.env. По умолчанию MODE=off.
  Никакого автозапуска worker в текущих серверах/супервизоре не добавлено.
- При MODE=off CLI не открывает базу и не отправляет запросов. При sandbox
  выбираются только test, при production только не-test; preview всегда test.
- Текущие локальные серверы всё ещё создают test=true. Настройка production
  worker сама по себе не включает рабочие заказы. Публичный checkout и шлюз
  также остаются в прежних безопасных границах.
- Резервирование orders.sqlite автоматически включает очередь и identity.

Сейчас рабочие URL/секреты не заданы, автозапуск выключен. После реализации
b24-app сначала выполнить совместный sandbox-тест, затем отдельным этапом
согласовать production URL, TLS, секрет, allowlist sourceId, права и запуск.

## Приёмочные проверки для другой стороны

Тестовый JSON проходит схему и финансовые проверки; 20 параллельных повторов
создают одну входящую SQL-запись и одну квитанцию; рестарт приёмника не теряет
идемпотентность; обрыв после COMMIT возвращает прежнюю квитанцию при повторе.
Изменённое тело/ключи дают 409. Неверный токен/hash/режим/version/размер отвергается.
Без Битрикса HTTP-приём сохраняет запрос, CRM-очередь ждёт восстановления.
Существующий однозначный клиент не дублируется; новый создаётся один раз;
конфликт контактов уходит на ручной разбор. Источник существующего лида не меняется.
Задача/уведомление не дублируется при повторе и восстановлении процесса.

На сайте тесты: `src/order-delivery.test.ts` — атомарность, повторы/рестарт,
lease/fencing, sandbox, HTTP mock с потерянным ответом, ошибки/ACK, миграция,
доступ к ручному повтору. HTTP mock — изолированный тест, не реализация b24-app.
