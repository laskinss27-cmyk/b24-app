## Карта чтения и записи

### Старые реализации

- `deal-order-info.ts:loadDealOrderInfo` читает память складов из `ctv_realize`.
  Сейчас это одиночный `entity.item.get`, а не обход всех страниц; ошибки
  проглатываются, партии возвращаются без названий складов.
- `routes/deal-bitrix-realization-route.ts` создаёт запись `ship_<shipmentId>`
  после создания нативной отгрузки Bitrix. Ошибка памяти сейчас не отменяет
  уже созданную отгрузку.
- `routes/api-deal.ts` регистрирует этот endpoint;
  `routes/deal-supply-routes.ts` тоже вызывает `loadDealOrderInfo`.
- Основной текущий интерфейс реализации вызывает `/api/deal/realize-core`
  через `deal-realization-actions.ts`. Поэтому эти две записи — память старого
  сценария, не две недостающие ERPNext-реализации.

SQL хранит external record ID/name, deal/order/shipment refs и упорядоченные
строки rowId/storeId/storeName. Нативные документы Bitrix и ERPNext не
создаются повторно при backfill. Повтор сохранения памяти привязывается к
исходной отгрузке; ошибка mirror не должна провоцировать новую отгрузку.
Если при свежем чтении появится второй документ с тем же shipment ID,
перенос останавливается для разбора, а не выбирает один молча.

### Договоры и номера

- `deal-contract-numbering.ts:allocatePersistentContractNumber`: файловый
  high-water mark, очередь внутри процесса, `baseline`, `previousKeys` и
  необязательный запрошенный номер.
- `deal-contract-bitrix.ts:allocateContractNumber`: ключ по ИНН, legacy-ключ
  по company ID, минимальный номер и значения `app.option.get`.
- `deal-contract-generator.ts` выдаёт номер, формирует DOCX, сохраняет документ.
- `deal-contract-storage.ts`: список, скачивание и сохранение метаданных и DOCX.
  Обычное чтение может **перезаписать имя файла в метаданных** через
  `migrateStoredContractFilename`. Диагностический read-only список не пишет,
  но скрывает ошибки отдельных файлов; для backfill он непригоден.
- `routes/api-contracts.ts` и `admin/deal-application-documents.ts` — потребители.
- `CONTRACT_DOCUMENTS_PATH` и `CONTRACT_SEQUENCE_PATH` имеют собственные
  overrides и не обязаны следовать `B24_STATE_DIR`. Получать эффективные пути
  у запускаемого backend, как это делает аудитор.

SQL хранит все 14 полей карточки отдельными колонками, относительный путь DOCX,
размер и SHA-256; даты/формат отображения сохраняются без потери исходных строк.
DOCX остаются файлами. Нумерация: отдельный ключ и high-water mark, блокировка
строки в транзакции; учитывается максимум файла, app options, baseline и
связанных legacy-ключей. Автоматически объединять разные юрлица нельзя.
Backfill сохраняет все исходные ключи, даже не используемые текущим кодом.

Выдача номера получает идемпотентный ключ операции; повтор после timeout не
выдаёт новый номер. SQL фиксирует операцию, завершённый DOCX атомарно публикуется
по UUID, затем карточка переводится в ready. Прерывание между файловой и SQL
записью должно быть восстанавливаемым по той же операции. На чтении не запускать
переписывание legacy JSON. При ошибке SQL не возвращаться к файловому allocator:
это создаёт риск двух независимых последовательностей.

### Матрица

- `assortment-matrix-template-store.ts`: `list/save/delete`, очередь процесса,
  проверка `expectedUpdatedAt`, максимум 100 шаблонов и 1000 строк в шаблоне.
- `routes/api-stock-assortment-routes.ts` создаёт store и сохраняет текущую
  проверку пользовательских прав.

Шапка: UUID, название, from/to, salesScope, created/updated actor и timestamps.
Отдельные таблицы упорядоченных складов и строк: productId/category/segment/
toOrderQty/comment. Сохранять порядок, пустые комментарии, дробные количества,
названия сегментов. Изменять шапку/строки одной транзакцией с проверкой версии;
удаление пользовательским действием реализовать tombstone.
SQL хранит шаблон; текущие остатки и расчёт отчёта продолжают обновляться при
открытии существующим механизмом.

### Конструктор отчётов

- `report-builder/store.ts`: по одному файлу на owner ID; `list/save/delete`,
  оптимистическая проверка `expectedUpdatedAt`.
- `report-builder/model.ts`: definition включает dataset, ordered columns,
  groupBy, from/to/store/categoryIds и sort с направлением.
- `routes/api-report-builder.ts` авторизует пользователя и определяет владельца.

В SQL каждое чтение и запись включают owner ID. Шапка и скалярные фильтры отдельно;
колонки, группировки, категории и сортировки — дочерние строки с ordinal.
Различать отсутствующий optional-фильтр и пустой массив. Не хранить definition
как JSON/blob. Пустой production-источник не заменяет тесты двух владельцев,
создания/редактирования/удаления, порядка полей и конфликта версий.

### Журнал

- `operation-log/store.ts` перечитывает и переписывает весь JSONL, держит
  последние 5000 событий; `list` фильтрует area/outcome, затем берёт 1–500 строк.
- `operation-log/service.ts` формирует событие и ловит ошибки логирования;
  отказ журнала не должен превращать успешное бизнес-действие в ошибку.
- `operation-log/register.ts` подключает store; `routes/api-operation-log.ts`
  возвращает журнал.

SQL: событие, упорядоченные документы, типизированные details
(string/number/boolean). Сохранять отсутствие actor/deal/documents/details;
историческое поле deal.title тоже входит в модель. Порядок журнала — порядок
добавления, а не только occurredAt; одинаковые timestamp не меняют порядок.
Backfill сохраняет все доступные события. SQL append не требует физического
удаления; существующий вид последних 5000 можно сохранить границей запроса
до фильтрации. Автоматическую очистку/retention не включать в пакет.

## Один релиз и управляемое переключение

1. Реализовать все адаптеры, строгие source parsers, нормализованные DDL,
   backfill dry-run/apply, parity, recovery и тесты одним локальным change set.
   Каждый модуль имеет собственные read/write flags с default off.
2. Проверить весь пакет на одноразовой MariaDB: apply/replay, транзакционный
   rollback, конкуренция номеров/редактирования, owner isolation, отсутствие
   DDL/DELETE у runtime и сбои mirror/DOCX. Frontend/API контракты сохранить.
3. Перед production переносом создать **один полный комплект резервных копий**:
   `b24_app`, все эффективные файловые пути (включая DOCX), защищённый экспорт
   `ctv_realize` и относящихся к нумерации app options. SQL dump сам по себе
   файловые источники не защищает. Проверить изолированное восстановление всех
   частей и их согласованность. Не запускать retention.
4. Развернуть один общий image с новой схемой и адаптерами. Старый контейнер
   сохранить. Для начала source остаётся legacy; после активации shadow writes
   согласовать свежий снимок/дозагрузку с конкурентными записями. Backfill не
   должен затереть более новую shadow revision. Checkpoint/hash apply строго
   ручной, атомарный и fail-closed. Никаких migrations/backfill при startup.
5. В рамках того же релиза сверить и переключить модули последовательно:
   журнал → матрица → отчёты → память реализаций → договоры и нумерация.
   Это один пакет кода, но config switches могут потребовать пересоздания
   контейнера; обещание одного релиза не означает одного restart.
6. Перед первыми primary writes сверить актуальные источники ещё раз. Для
   нумерации нужен короткий запрет/дренирование только выдачи номеров на момент
   передачи allocator, чтобы старый процесс не успел выдать номер после сверки.
   Защитить этот переход кодом, а не просьбой сотрудникам не нажимать кнопку.
7. Подтвердить реальные новые записи, пустую очередь mirror либо объяснимые
   восстанавливаемые ошибки, read-only parity и стандартные deployment checks.
   Не выдавать тестирование пустого реестра за проверенное production-создание.

Откат после primary — после доставки/сверки compatibility mirror. Для номеров
сначала выровнять legacy high-water mark с SQL. Нельзя просто вернуть старый
контейнер с устаревшими файлами и продолжить выдачу номеров. Сохранённые исходники,
backup, restore schemas, SQL записи и rollback containers не удаляются.

Production migrations/backfill/source switch/deploy требуют явной команды по
правилам `AGENTS.md`. Производственный переход требует отдельного разрешения
на подготовленный пакет.

## Что не требует повторной миграции

- Снабжение: `api-supply-orders-route.ts` уже вызывает `loadTransfers` при
  `transferSqlRead=primary`. Старый supply mirror resolver вызывается только
  вне primary; сам по себе `B24_APP_SUPPLY_SQL_READ=verified` не означает,
  что этот рабочий путь ещё читает Bitrix transfers.
- Перемещения, ручные заявки, ревизии, ремонты — уже перенесённые модули;
  JSON в compatibility adapters не является их SQL source of truth.
- ERPNext документы/остатки и Bitrix CRM, пользователи/права/задачи — внешние
  системы, доступ к которым сохраняется через официальные API.
- OAuth vault — зашифрованный технический секрет; его не переносить в обычные
  бизнес-таблицы. DOCX, изображения и программные assets остаются файлами.
- API JSON, одноразовые Tilda dry-run отчёты, тестовые fixtures и in-memory
  caches не являются оставшимися рабочими JSON-хранилищами этого пакета.

## Повторение аудита

`scripts/sql-remaining-audit.mjs` передаётся в работающий backend по stdin:
`docker exec -i b24-backend node --input-type=module`. Он только читает выбранные
файлы, сверяет повторное чтение и выводит агрегаты. Не вызывает функции
миграции имён договоров.

`scripts/sql-remaining-bitrix-audit.mjs` аналогично использует штатный owner
vault и проверяет точного владельца; читает все страницы `ctv_realize` и только
считает ключи нумерации из app options. Отказ авторизации завершает аудит,
повтор через webhook/placement token не предусмотрен.

Оба скрипта скрывают исходные исключения, которые могут содержать бизнес-данные
или OAuth, и не являются командами backup/backfill.

## Реализованный пакет

Миграции `0084`–`0112` добавляют 29 таблиц. Точная физическая схема закреплена
в SQL-файлах и декларациях `remaining-sql/schema.ts`; названия в первоначальном
проекте выше уточнены при реализации. Все доменные поля — отдельные колонки.
Массивы и вложенные объекты представлены дочерними таблицами с ordinal и FK.
Детали события — единственное типизированное поле со значением одного из
string/number/boolean; произвольный JSON payload не хранится.

`app_state_heads` указывает на текущую неизменяемую версию коллекции.
`app_state_revisions` хранит module, owner, hash и время, без содержимого JSON.
SQL сохраняет историю при изменении/удалении шаблона или личного отчёта.
Для журнала создаётся только версия нового события и identity с порядковым
номером: предыдущие события не копируются при append. Представление последних
5000 событий и существующие API-фильтры сохранены, физической очистки нет.

Недоставленная compatibility-копия определяется различием revision_id и
mirror_revision_id. Запись и доставка сериализуются одним advisory lock;
восстановление может объединить старые pending изменения в последнюю полную
версию коллекции. Ошибка доставки логируется без потери SQL-записи.
Автоматический фоновый retry не добавлен; ниже есть явная recovery-команда.

В договорах key запроса сохраняется фронтендом между неуспешными попытками
в пределах текущей страницы; после успеха следующая генерация получает новый key.
Номер, UUID и время документа закрепляются одной SQL-транзакцией. Новая
генерация после полной перезагрузки страницы остаётся новым запросом.
DOCX сначала записывается во временный файл, затем SQL фиксирует карточку и
manifest со статусом pending; файл переименовывается и manifest становится ready.
Если процесс остановился между этими действиями, повтор использует тот же
UUID и подготовленный файл, сверяет SHA-256 и завершает запись. Непривязанные
временные файлы после сбоя до SQL prepare остаются для отдельной уборки.
Стандартный путь списка/скачивания сохраняет человекочитаемое имя договора;
административный read-only путь не меняет метаданные.

Память реализаций использует shipment ID как стабильный ключ и отдельно
сохраняет Bitrix external ID. После неопределённого результата entity.add
повтор mirror ищет запись по shipment, затем обновляет её без создания дубля.
Само создание нативной Bitrix-отгрузки остаётся внешней операцией: этот пакет
переносит память складов и не делает всю многошаговую операцию Bitrix атомарной.

### Конфигурация и права

Каждый флаг принимает `off|shadow|verified|primary`, default — `off`:

- `B24_APP_MATRIX_STATE_SQL`;
- `B24_APP_REPORTS_STATE_SQL`;
- `B24_APP_LOG_STATE_SQL`;
- `B24_APP_REALIZATIONS_STATE_SQL`;
- `B24_APP_CONTRACTS_STATE_SQL` и `B24_APP_SEQUENCES_STATE_SQL` — одинаковый режим.

`shadow` пишет legacy, затем SQL; `verified` дополнительно возвращает SQL при
совпадении; `primary` читает/пишет SQL и доставляет compatibility-копию.
Новая primary-коллекция другого владельца не читает чужой файл.
Primary не включается до наличия gate соответствующего модуля; /ready проверяет
доступность таблиц включённых модулей. Миграции и backfill при запуске отсутствуют.

Нужны `B24_APP_DB_MODE=readiness`, действующие DB_HOST/PORT/NAME и отдельные
`B24_APP_REMAINING_DB_USER/PASSWORD`. Runtime не принимает root или совпадение
с другим DB_USER из окружения. `remaining-sql/grants.ts` формирует проверяемые
табличные GRANT, не исполняя их: runtime получает SELECT/INSERT на неизменяемые
версии и дочерние строки; UPDATE только для heads, manifests и identity.
Checkpoint runtime недоступен, gates доступны только SELECT. Backfill —
отдельный DML-пользователь, без DDL/DELETE.

```text
npm -w @b24-app/backend run state:backfill -- --compare
npm -w @b24-app/backend run state:backfill -- --apply <точный-planHash>
npm -w @b24-app/backend run state:backfill -- --recover
```

Dry-run дважды читает все источники, не скрывает повреждённые записи и
выводит только hash/количества. Счётчики импортируются с максимумом файлового
значения и старого app.option. Apply снова читает источники дважды под тем же
lock, проверяет hash и переносит весь пакет одной транзакцией. Отличающуюся
существующую SQL-версию он не перезаписывает. CLI разрешает apply только при
shadow/verified для всех модулей пакета; off и primary блокируют перенос.
Полнота DOCX manifests и внешних ID проверяется в обе стороны, включая лишние записи.
Compare выполняет только чтение; recover доставляет pending compatibility
состояние и требует явной операторской команды.

Перед apply все legacy writers этого пакета должны работать в shadow/verified
на одном актуальном backend, чтобы участвовать в lock. На этапе переключения
номеров остановка старого контейнера и проверка завершения его запросов должны
предшествовать последней сверке и запуску primary. Canary с primary нельзя
использовать для пользовательского создания параллельно со старым allocator.
