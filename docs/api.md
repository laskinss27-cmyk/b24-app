# HTTP-маршруты backend

Пример публичной базы: `https://app.example.com`. Рабочий адрес хранится вне репозитория. Большинство маршрутов `/api/*` вызываются только frontend внутри Битрикс24 и принимают контекст текущего пользователя.

## Служебные и OAuth

| Метод и путь | Назначение |
|---|---|
| `GET /health` | состояние процесса backend |
| `GET|POST /app/handler` | основной вход локального приложения |
| `POST /install` | установка и первичная привязка placement |
| `POST /uninstall` | уведомление об удалении приложения |
| `GET /m` | мобильный вход инвентаризации |
| `GET /m/callback` | OAuth callback мобильного входа |

## Placement

Все placement принимают POST Битрикс24 и отдают один собранный frontend с нужным контекстом:

- `/placement/deal-tab`;
- `/placement/task-inventory`;
- `/placement/inventory`;
- `/placement/catalog`;
- `/placement/sales-report`;
- `/placement/repairs`;
- `/placement/stock`;
- `/placement/supply`.

## API по областям

| Префикс | Область |
|---|---|
| `/api/deal/*` | позиции сделки, этапы, варианты, КП в Word/Excel/PDF, товарный чек, заявки и реализации |
| `/api/contracts/*` | контекст и генерация договора |
| `/api/catalog/*` | каталог, карточка товара, цены, остатки, сравнение и Excel-выгрузка выборки маркетплейсов |
| `/api/inventory/*` | инвентаризации и корректирующие документы |
| `/api/stock/*` | складские документы и движение товара |
| `/api/transfer-requests/*` | заявки и заказы на перемещение |
| `/api/transfers/*` | жизненный цикл перемещения |
| `/api/supply/*` | заявки, поставщики, закупки и приёмка |
| `/api/marketplaces/*` | продажи, комплекты и возвраты маркетплейсов |
| `/api/repairs/*` | ремонты, статусы, цены, файлы и поиск |
| `/api/realizations/*` | журнал реализаций |
| `/api/reports/*` | отчёты |
| `/api/quicksale/*` | быстрая продажа |
| `/api/access-control/*` | чтение сотрудников и отделов, загрузка и сохранение правил доступа |

Актуальный перечень конкретных endpoint всегда определяется регистрацией `app.get` и `app.post` в `packages/backend/src/routes/`. При добавлении или удалении группы этот документ обновляется.

Печатные формы сделки используют единые данные `POST /api/deal/kp`. Word-файл создаёт читающий маршрут `POST /api/deal/kp-docx`, Excel — `POST /api/deal/export-xlsx`. PDF-версия КП и товарный чек печатаются frontend через системный диалог печати браузера. Контекст и Word-файл договора обслуживают `/api/contracts/context` и `/api/contracts/generate`. При генерации frontend передаёт шаблон, наше юрлицо, тип клиента, дату, адрес и срок работ; номер договора и НДС backend определяет автоматически.

Связанные строки сделки и снабжения изменяются только через серверные маршруты. `POST /api/deal/replace-plan-product` заменяет необработанный товар одновременно в рабочем составе и открытой заявке снабжения. `POST /api/supply/request-line` позволяет снабжению изменить товар или количество и переносит ту же правку в сделку. Количество нельзя уменьшить ниже уже распределённого, а полностью распределённая позиция зафиксирована. `POST /api/supply/request-store` меняет конечный склад открытой заявки и её строк Material Request; маршрут отклоняет изменение после создания перемещения или проведения прихода.

## Авторизация запросов

Frontend передаёт:

- домен портала;
- access token текущего пользователя;
- идентификаторы контекста: сделка, документ, склад или ремонт.

Backend:

1. принимает только настроенный `PORTAL_DOMAIN`;
2. выполняет вызовы Битрикс24 от имени текущего пользователя;
3. не отдаёт токен ERPNext клиенту;
4. применяет явные правила сотрудника и его отделов к маршрутам приложения;
5. отдаёт приоритет личному правилу сотрудника, а между несколькими отделами — явному запрету;
6. сохраняет прежнюю проверку ролей, если для права нет явной настройки;
7. возвращает JSON-ошибку с понятным сообщением.

Писать прямые вызовы Битрикс24 из React не следует: это усложняет права, таймауты и аудит.

## Правила изменений

- Читающие маршруты не должны создавать документы.
- Записывающий маршрут обязан сообщать, что было создано или изменено.
- Повтор после сетевой ошибки допускается только после проверки отсутствия уже созданного документа.
- Секреты и полные тела с OAuth-токенами не логируются.
