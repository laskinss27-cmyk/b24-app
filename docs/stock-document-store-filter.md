# Фильтр складских документов

Решение пользователя 01.10.2026: сотрудники должны быстро находить документы своей точки в «Складском учёте».

Выбор «Склад» расположен сразу под вкладками документов, по умолчанию «Все склады». Список берётся из прежнего справочника активных складов ERPNext (`/api/stock/form-data`), права не меняются. Выбор сохраняется при переключении журналов в текущем открытом окне, не сохраняется после перезагрузки. Отдельные роли не получают новый доступ или запрет просмотра других складов.

## Область действия

- Заявки ТТ: перемещение участвует по отправителю или получателю; заявка снабжению — только по получателю.
- Перемещения: входящие и исходящие выбранного склада, совместно с прежними фильтрами товара, поиска, статуса и периода.
- Реализации/возвраты: `Delivery Note Item.warehouse`.
- Оприходования: `Purchase Receipt Item.warehouse` и `Stock Entry Detail.t_warehouse` для Material Receipt.
- Списания: `Stock Entry Detail.s_warehouse` для Material Issue.

Склад определяется по строкам, а не по необязательному складу в шапке. Документ с несколькими складами подходит, если выбранный склад участвует в нём; документ открывается целиком, строки не скрываются. При совместном фильтре товара и склада core выбирает строки с этим товаром на этом складе. Склады сравниваются по точному названию, без совпадений по подстроке.

Фильтр складских документов не показан в «Инвентаризации» (там уже есть свой выбор точек) и «Отчёте по движению товара»; их текущие контракты не меняются. Неактивные/исторические склады не добавляются в справочник форм: их документы доступны в общем списке «Все склады».

«Сброс» в журналах движений/перемещений снимает склад, товар и прежние фильтры. Пустой результат сообщает об отсутствии совпадений. Выбор склада заново начинает список движений с первой страницы. Поиск номера/сделки/ответственного и статус всё ещё работают до разбиения на 50 строк. Несколько совпавших дочерних строк не дублируют заголовок.

## Источники и совместимость

Прежде core возвращал полные заголовки только по периоду/товару; теперь тот же API принимает необязательный `store` и применяет warehouse child filter. Название переводится в прежний ERP Warehouse с суффиксом компании через `erpWarehouse`. Старые клиенты без `store` продолжают получать общий список. Источники ERPNext и Bitrix entity, формат сохранённых документов и складские проводки не меняются; миграция не нужна. Заявки и перемещения фильтруются на клиенте после уже полного чтения истории, без нового лимита.

Неверный тип склада или строка длиннее 200 символов дают HTTP 400. Ошибка чтения не показывается как успешный пустой список. Быстрая смена склада не позволяет устаревшему ответу движения заменить текущий результат.

## Проверки 01.10.2026

Регрессии включены в обычные backend/frontend suites: все типы core-документов, оба прихода, >100 заголовков и дедупликация join; HTTP передача/валидация; передача склада вместе с товаром и периодом; оба направления маршрута, старые строки и supply destination.

Read-only проверка production ERPNext для Дунайского: фильтры вернули 69 реализаций, 4 возврата, 15 Purchase Receipt, 5 Material Receipt и 31 Material Issue. Для каждого типа содержимое первых трёх документов подтвердило warehouse в дочерних строках. Это проверка схемы запросов, не отправка нового HTTP-фильтра из production frontend до выпуска. Ни один документ не изменялся.

В реальном браузере на синтетических данных проверены сохранение выбора между вкладками, оба направления перемещений/заявок, >50 совпадений, вторая страница и поиск документа №124, сброс к 125 документам, пустой результат и выбор клавиатурой. Размеры: 1280×720, 768×1024 и 390×844, тёмная тема и крупный текст. Новый селектор полностью помещается в узкий экран; широкие таблицы сохраняют прежнее горизонтальное прокручивание. Screen reader отдельно не проверялся.

Тестовая страница удаляется до сборки/коммита; снимок в ignored outputs является дополнительным примером, этот документ — постоянный контракт. Production выпуск фиксируется отдельно после переключения и стандартных проверок.

Полные suites после реализации: 408 backend + 185 frontend + 6 release = 599 тестов, без пропусков. Typecheck/build и проверка diff прошли; прежнее предупреждение размера Vite chunk сохраняется. Восстановленные правила аудита 29 сентября и прежние проверки пагинации остаются в штатных suites. Автоматический разбор обращений остаётся на паузе по отдельному решению пользователя.
