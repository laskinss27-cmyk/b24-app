# Релиз с подтверждённым Git SHA

Основные команды запускаются из корня **чистого репозитория**, HEAD которого уже отправлен в upstream-ветку. Неотслеживаемые файлы тоже блокируют релиз. Игнорируемые секреты и локальные зависимости в релиз не включаются: контекст берётся только из `git archive HEAD`.

## Сборка и выкладка на сервере

```bash
npm run test:release
node scripts/b24-release.mjs build
SHA=$(git rev-parse HEAD)
node scripts/b24-release.mjs guard "b24-app:git-$SHA" "$SHA"
bash scripts/b24-deploy.sh "b24-app:git-$SHA" "$SHA"
```

Отдельный вызов `guard` удобен для предварительной проверки. Скрипт `b24-deploy.sh` **всегда вызывает его повторно сам** до остановки backend. Путь репозитория, SSH-хост и ключ берутся из закрытой конфигурации. Скрипту нужен доступ к Git upstream, Docker, Node.js, Bash, curl, flock и установленной службе retention. Скрипт рассчитан на обновление существующего `b24-backend`, а не первичную установку.

`build` формирует временную копию коммита, добавляет манифест хешей исходников и передаёт Docker полный SHA и SHA дерева Git. Dockerfile проверяет входной контекст, запускает **обе** тестовые группы (backend и frontend, включая deal-controls), собирает приложение и сохраняет хеши готовых артефактов. Обычная команда `docker build .` без подготовленного манифеста больше не является способом сборки релиза.

Тесты и приложение используют Node 24 в одном образе. Это требуется существующей интеграции заказов с `node:sqlite`; Node 20 не может выполнить её полный набор тестов. Пример контракта заказа также включён в манифест сборки. Обновление Dockerfile само по себе не переключает работающий контейнер и не включает обработчик заказов.

## Подготовка на Windows, сборка на сервере

```powershell
node scripts/b24-release.mjs prepare .tmp/release-context
```

Каталог назначения должен быть новым. Передайте весь созданный контекст на сервер, включая скрытый каталог `.release`. SHA и дерево находятся в `.release/source.json`. На сервере выполните сборку из этого контекста:

```bash
SHA=$(node -p 'require("./.release/source.json").gitSha')
TREE=$(node -p 'require("./.release/source.json").gitTree')
docker build --build-arg RELEASE_SHA="$SHA" --build-arg RELEASE_TREE="$TREE" -t "b24-app:git-$SHA" .
```

Затем **перейдите в чистый Git checkout того же коммита** с настроенной upstream-веткой и запустите guard/deploy. Архив исходников без `.git` достаточен для сборки, но недостаточен для проверки ancestry и опубликованного коммита. Не выдавайте архив за Git checkout.

## Что блокирует pre-deploy guard

- Незакоммиченные, staged и новые неотслеживаемые файлы; HEAD, не совпадающий с опубликованной upstream-веткой.
- Отсутствующий/неполный SHA, несовпадение SHA или Git tree в образе, манифесте и Git.
- Отличия исходного манифеста образа от содержимого коммита.
- Отсутствующие, изменённые или дополнительные файлы исходников/сборки относительно манифеста готового образа.
- Ручные изменения файлов внутри работающего контейнера после сборки.
- Кандидат, который не является потомком работающего релиза. Откат — отдельная аварийная операция.
- Файлы исходников текущего продакшена, отсутствующие в кандидате (`b24-release-source-guard.sh`). Плановое удаление файла требует отдельного разбора и изменения правила, а не флага обхода.
- Неработающий текущий backend или отсутствие `erpnext_frappe_network`.

Скрипт блокирует одновременные выкладки, сохраняет предыдущий контейнер, наследует фактическое окружение и `/app/state`. Сначала создаётся **остановленный** кандидат; его неизменяемый image ID сверяется с результатом guard **до остановки продакшена**. Затем запускается этот точный container ID. Подмена тега не приведёт к запуску чужого образа. Полный Git-тег сохраняется в конфигурации контейнера для совместимости с retention. После запуска обязательны внутренний и публичный `/health` с ожидаемым SHA, Docker network membership и авторизованный read-only запрос к ERPNext. Ошибка вызывает откат на сохранённый контейнер. После успеха запускается установленная служба retention.

## Первый переход со старого образа

Старые образы не содержат метаданных и хешей сборки. Обычный guard их отклоняет. Для единственного перехода передайте **полный, предварительно установленный SHA** текущей старой версии:

```bash
bash scripts/b24-deploy.sh "b24-app:git-$SHA" "$SHA" "$VERIFIED_LEGACY_SHA"
```

Это не отключает проверку: guard сверяет все доступные исходники старого контейнера с указанным коммитом и проверяет ancestry. Учтены известная сборочная замена exports в `packages/shared/package.json` и CRLF/LF в текстовых файлах старых Windows-архивов. Бинарные файлы сверяются побайтно. Отличия содержимого блокируют переход. Новые архивы создаются с `core.autocrlf=false`, а новые образы всегда проверяются побайтно. Проверить исторические скомпилированные файлы старого образа по отсутствующему манифесту невозможно; полноценная проверка артефактов начинается с первого нового релиза. В следующих выкладках дополнительный параметр не нужен.

## Где смотреть версию

`GET /health` сохраняет старые поля и добавляет `gitSha`, `gitTree`, `builtAt`. Они читаются из файла внутри образа, а не из env прошлого контейнера. В локальной разработке без файла значения равны `null`.

```bash
docker inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' b24-backend
docker exec b24-backend cat /app/release.json
```

Это защита от ошибок выкладки и незаметного расхождения исходников. Это не криптографическая подпись сборки и не запрет для владельца root/Docker вручную обойти сценарий. Старые точечные скрипты в `tools/` и локальном `.deploy/` не использовать для production release.

## Сохранность бизнес-правил

Git SHA, хеши и source guard доказывают происхождение/целостность файлов. Они не замечают удалённую ветку условия, изменённую формулу или исчезновение теста внутри сохранившегося файла. Уже утраченную до внедрения guard функцию они тоже не восстанавливают.

Перед выпуском сверять затронутые правила с [реестром](feature-registry.md), включая открытые дефекты [аудита 29.09](audits/2026-09-29-feature-audit.md). Изменения и намеренная отмена правила записываются вместе с кодом; неописанное исчезновение проверки требует разбора. Это обязательная процедура ревью, а не уже реализованный автоматический анализ смысла программы.

Обе workspace test-команды теперь рекурсивно находят все `src/**/*.test.ts(x)` через `packages/shared/scripts/run-workspace-tests.mjs`. Docker вызывает те же команды; новый тест не надо дописывать в package.json. После аудита полный штатный набор — 331 backend + 161 frontend; release tooling отдельно — 6 тестов. Счётчик — ориентир для ревью, не жёсткая константа вместо содержательных проверок.

Четыре диагностических сценария исторических утрат сейчас падают и сохранены отдельно с явным статусом дефекта. Их провал не разрешает выкладку с обходом правил. Для восстановления перенести сценарий в основной набор, исправить поведение и обновить реестр. В рамках документального аудита production не обновлялся.
