# WhatsApp: локальная проверка одного аккаунта

## Запрос и границы

09.10.2026 владелец предложил проверить свой обычный WhatsApp после исследования MAX/WhatsApp. Источник — связанное устройство WhatsApp через неофициальную библиотеку Baileys 7.0.0-rc14. Это отдельный локальный пилот, не новая production-интеграция. Telegram и данные CRM не изменяются. Нет платы библиотеке за каждый аккаунт, но работоспособность не гарантирована WhatsApp; возможны прекращение сессии и ограничения аккаунта.

## Запуск

Из корня проекта: `npm ci --prefix tools/whatsapp-pilot --ignore-scripts`, затем `node tools/whatsapp-pilot/server.mjs`. Адрес: http://127.0.0.1:5201. На экране нажать «Показать QR-код», на телефоне — WhatsApp → Связанные устройства → Привязка устройства. Вход требует действий владельца; полученный QR сам по себе не подтверждает авторизацию.

Локальный сервер слушает только 127.0.0.1, проверяет Host, Origin, Fetch-Site, HttpOnly/SameSite-cookie, специальный заголовок и размер запроса. Нет внешних ресурсов интерфейса, CORS и встраивания в iframe. Сессия, ключи и ограниченный просмотр переписки сохраняются локально в AES-256-GCM контейнере `.local/whatsapp-pilot/session.enc`. Ключ `.secrets/whatsapp-pilot.key` хранится отдельно; оба пути исключены из Git. В журналы не попадают сообщения, телефоны, QR, ключи и URL скачивания истории. Это шифрование файла, не изоляция от пользователя ОС, имеющего доступ к обоим файлам. Зависимости изолированы в tools/whatsapp-pilot/package-lock.json.

## Данные и ограничения

WhatsApp при связывании сам передаёт недавнюю историю и события аккаунта. Выбор двух диалогов ограничивает показ, а не права связанного устройства. Локальная модель и её зашифрованный снимок сохраняют до 120 личных диалогов и до 50 последних сообщений в каждом, текст до 8000 символов. При первом связывании включён расширенный режим `syncFullHistory`, и принимаются FULL-пакеты; объём передачи определяет WhatsApp, полный архив не обещается. Ограничения локального просмотра не ограничивают объём входящих служебных пакетов. Группы, каналы, статусы, собственный чат исключены. Просмотр требует явного выбора, максимум двух диалогов. Медиа только обозначаются, файлы не скачиваются. View-once и сообщения в ephemeral-wrapper не копируются; полная поддержка всех вариантов исчезающих сообщений не заявляется.

Сохраняется направление входящее/исходящее, дата, ID для устранения дублей. LID и номер объединяются только по соответствию, переданному WhatsApp; номер не вычисляется из LID. Конфликтующая смена номера отвергается. Позднее сопоставление сохраняет выбранный диалог и обе части истории. Если номера нет, экран сообщает, что автоматический поиск CRM невозможен. Полученные события удаления очищают локальные сообщения, обычные edits обрабатываются; все варианты протокольных правок требуют реальной проверки.

Программа не вызывает отправку сообщений, отметку прочтения или импорт контактов. Служебные запросы связанного устройства выполняет библиотека. Пилот не включает CRM-поиск, привязку в сделке, полный постоянный архив, восемь аккаунтов или работу на сервере. Старый источник Telegram остаётся прежним; миграции данных нет.

Кнопка «Отключить и очистить пилот» пытается отозвать сессию, очищает память и удаляет зашифрованный снимок. Если WhatsApp не подтвердил отзыв, экран требует завершить сессию на телефоне. Существующая QR-сессия определяется также по `creds.me.id`: `registered` у неё может быть false. Обычный перезапуск сохраняет вход и ограниченную историю; после запуска нажать подключение, новый QR при действующей сессии не нужен. Повреждённый контейнер или отсутствующий ключ вызывают ошибку без автоматического сброса. Повторные соединения ограничены; ошибки блокировки/вытеснения/выхода не запускают автоматический цикл входа.

## Проверки

Регрессии входят в обычную discovery-all команду backend: packages/backend/src/integrations/whatsapp-pilot.test.ts. Проверяют выбор/лимит, отсутствие текста в списке, LID/телефон/направление/дубли, исключённые чаты, границы хранения, удаления, HTTP-защиту, неуспешный отзыв и запоздалые события после отключения.

`node tools/whatsapp-pilot/ui-test.mjs` использует отдельный локальный сервер и подставные данные в headless Edge. Проверены QR, входящие/исходящие, неизвестный номер, отказ третьего выбора и восстановление флажка, XSS как текст, ширины 360/768/1280, увеличенный вдвое текст, клавиатура, очистка и недоступность сервера. Скриншоты в outputs/whatsapp-pilot — дополнительное свидетельство; рабочий контракт сохранён здесь. Screen-reader и полевые показатели производительности не измерялись.

Проверка зависимостей npm при установке: 0 известных уязвимостей; загрузка Baileys под Node 24 успешна. Реальная авторизация, получение переписки и полнота истории требуют подтверждения после сканирования владельцем; тестовый экран не доказывает их.

Затем отдельно перенести правила MSG-05/06 на новый источник, добавить серверное хранение с разграничением доступа и проверить восстановление нескольких аккаунтов. До этого в карточке сделки сообщений WhatsApp нет. Любой production-выпуск — только по штатной процедуре проекта.

## Сетевая проверка 09.10.2026

Прямое разрешение web.whatsapp.com на рабочем компьютере возвращает ошибку DNS. Найден уже работающий локальный Xray на 127.0.0.1:10808; через него публичная страница WhatsApp отвечает 200, а пилот получил настоящий QR (qrReady=true). Настройки ОС/VPN не менялись. Для этого запуска используется WHATSAPP_PILOT_PROXY_PORT=10808: WebSocket через SOCKS5 с разрешением DNS на стороне прокси, загрузка истории через HTTP CONNECT того же локального порта. Оба режима проверены. Адрес прокси всегда loopback, порт проверяется; учётные данные прокси не требуются. Зависимости socks-proxy-agent 8.0.5 и undici 8.11.2 закреплены; итоговый npm audit: 0 известных уязвимостей.

573 backend-теста и backend typecheck прошли. Настоящий QR подтверждает доступность соединения, но ещё не подтверждает вход пользователя или получение сообщений. Экран передан владельцу для сканирования.

## Реальный вход и уточнение истории

Владелец подтвердил вход и список диалогов 09.10.2026. Из живого подключённого аккаунта получены 89 личных диалогов, у 88 есть номер телефона; в 58 диалогах была получена только последняя запись (в сумме 58 сообщений). Это подтверждает авторизацию/идентификацию, но не полную загрузку истории. Владелец также сообщил, что видит лишь одно сообщение.

Добавлена отдельная догрузка: при «Открыть» выбранного диалога или по кнопке «Загрузить историю с телефона» выполняется fetchMessageHistory(50, исходный ключ самой старой полученной записи, messageTimestamp). Ответ приходит асинхронно; телефон должен быть доступен. Не чаще раза в 90 секунд для одного диалога, только после явного выбора, при 50 сообщениях новый запрос не выполняется. Если нет ни одной записи, запросить границу невозможно; это явно показано. Вызов не отправляет клиенту пользовательское сообщение: это служебный запрос истории связанного устройства.

Для обновления memory-only пилота предыдущая сессия успешно отозвана (revoked=true). Получен новый QR. Реальный результат догрузки ожидает повторного входа владельца. Добавлена восьмая регрессия: исходный LID-ключ, требование выбора, лимит повторов, отсутствие внутреннего ключа в ответе UI. Браузерная проверка включает вызов загрузки и подтверждение запроса. Экран не объявляет историю полученной только на основании принятия запроса.

После добавления догрузки: 574 backend-теста, backend typecheck и браузерная проверка пройдены. Повторный реальный вход подтверждён сервером; выбран один диалог с номером, пока получена одна входящая запись. Запрос истории принят библиотекой; получение старых сообщений ещё не подтверждено. Не подменять принятие запроса успешной синхронизацией.


## Исправление загрузки истории 09.10.2026

Предыдущие абзацы о memory-only запуске и ожидании догрузки фиксируют состояние ранней пробы. Правило хранения только в памяти **отменено**: оно требовало повторного QR при исправлениях и теряло уже полученный просмотр. Замена — зашифрованный ограниченный снимок и учётные данные связанного устройства. Старый временный просмотр восстановить после остановки не удалось; сообщения WhatsApp на телефоне не менялись. Миграция CRM или Telegram не выполняется.

Зафиксирована реальная причина отсутствия истории: встроенные уведомления типов 0/1/4 обрабатывались, а загрузка внешних пакетов 5/3/2/6 падала с UND_ERR_INVALID_ARG. Baileys обращается к global fetch; встроенный fetch Node 24 не совместим с протоколом обработчиков установленного ProxyAgent Undici 8.11.2 (invalid onRequestStart method). На публичном URL проверено: встроенный fetch + этот dispatcher воспроизводят ошибку, fetch из того же Undici + dispatcher возвращает HTTP 200. Только standalone-процесс пилота устанавливает global fetch из своего закреплённого Undici; импорт сервера тестами или другими приложениями не меняет global fetch.

Дополнительно включены syncFullHistory и приём всех типов истории. Секунды в fetchMessageHistory оставлены намеренно: название oldestMsgTimestampMs в протоколе вводит в заблуждение; [реализация whatsmeow](https://github.com/tulir/whatsmeow/blob/main/send.go) также использует Timestamp.Unix().

Экран теперь показывает явный тайм-аут через 90 секунд и не выдаёт принятие запроса за доставку. Получение подтверждается новыми сохранёнными сообщениями из history-frame именно выбранного диалога; обычное live-сообщение или история другого чата не подтверждают запрос. Безопасная диагностика хранит только типы/счётчики/коды ошибок. Восстановленный снимок учитывается в статусе загруженной истории.

После исправления и повторного QR владелец подтвердил вход. Реальная диагностика: **6 пакетов истории успешно обработаны, в них 2141 запись до фильтрации; локально сохранены 384 сообщения в 120 личных диалогах, у 119 есть номер, 22 диалога содержат больше одного сообщения**. FULL и RECENT скачались без прежней UND_ERR_INVALID_ARG. Лимит 120 диалогов достигнут, поэтому это не подтверждение полного списка или архива. Чтение зашифрованного снимка отдельным процессом восстановило те же 384 сообщения и 22 диалога с историей. Ранее восстановление действующей учётной сессии после перезапуска отдельно подтверждено без QR. Старую неисправную сессию перед последним входом удалось отозвать (revoked=true).

Регрессии дополнены проверками шифрования/повреждения/отсутствующего ключа, восстановления выбора и исходного LID-ключа запроса, тайм-аута и ложного подтверждения истории, QR-сессии с registered=false. Живые новые входящие/исходящие после подключения и отдельная дальнейшая догрузка выбранного чата остаются следующими проверками; первоначальная расширенная история уже подтверждена.

Итог проверки исправления: 578 backend-тестов (в том числе 12 WhatsApp-регрессий), backend typecheck и браузерная проверка пилота пройдены. Изменения относятся только к локальной пробе; production не обновлялся.


## Неполная старая история: проверка 09.10.2026

Владелец сообщил, что старые диалоги показывают 0–1 сообщение, и подтвердил: на основном телефоне в таком чате видна длинная переписка. Это отдельное ограничение, не исправленная выше ошибка скачивания. На момент проверки: 61 из 120 записей списка без сообщений, 37 с одной записью, 22 с несколькими. Список также пополняется контактами WhatsApp; нулевой счётчик не доказывает ни отсутствие истории на телефоне, ни отдельную сетевую ошибку.

Два запроса ON_DEMAND по выбранным старым диалогам успешно получили пакеты, но число сообщений в них было нулевым. Дополнительно выполнена одна диагностическая попытка для уже выбранного диалога по LID, однозначно сопоставленному WhatsApp с его номером (без выдуманного идентификатора). Подтверждённый ответ: syncType=6, 1 chat, 0 messages, peerDataRequestSessionId совпал с ID запроса. Ошибок соединения/расшифровки не было, сообщений в этом диалоге осталось 1. Изменение адресации не дало историю, поэтому в рабочем запросе сохранён исходный ключ сообщения; эксперимент не включён в приложение.

Пустой ответ теперь завершает только соответствующий запрос статусом «WhatsApp ответил на запрос, но не передал дополнительные сообщения». Учитывается быстрый ответ до возврата ID из fetchMessageHistory; чужой ID не завершает запрос. Новые сообщения последующих пакетов всё ещё могут заменить этот статус на received. Диагностика раскрывает только тип/количество сообщений/количество чатов/наличие ID корреляции, без самого ID. Если исходной записи нет, интерфейс прямо объясняет, что текущий механизм не умеет запросить историю без такой границы; ожидание не представляется решением.

Полная ретроспективная история **не поддержана и не подтверждена этим пилотом**. [WhatsApp официально предупреждает](https://faq.whatsapp.com/653480766448040/), что не все сообщения и чаты синхронизируются на связанные устройства; полный архив следует смотреть на телефоне. Это общее ограничение согласуется с результатом, но конкретная внутренняя причина пустого ответа WhatsApp не установлена. Повторные QR и бесконечные автоматические запросы не используются. Возможный отдельный путь для старого архива — импорт экспорта с телефона; такого импортера пока нет. Живой обмен и привязка WhatsApp к CRM по-прежнему требуют следующего этапа.

Проверки уточнения: 579 backend-тестов (13 WhatsApp), backend typecheck и UI на подставных данных прошли. Обычный сервер восстановил вход без QR, все 384 сообщения и оба выбранных диалога. Production не обновлялся.
