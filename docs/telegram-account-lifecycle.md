# Подключение, имена менеджеров и общий чат (MSG-10–12)

Решения владельца 09.10.2026. Реализованы локально, до следующей согласованной выкладки. WhatsApp остаётся отдельным личным пилотом; ниже описан рабочий Telegram.

## Автоматическая привязка при подключении

Включение телефонного поиска теперь часть `/api/telegram/connect`, отдельная кнопка убрана. Сначала сервер проверяет сохранённый фоновый OAuth владельца; если он недействителен или отсутствует, использует refresh grant текущего владельца из SDK Битрикс24. Только после успешного получения доступа создаёт подключение, включает поиск и запускает QR. Приложение явно сообщает об автоматическом поиске контактов. Токены по-прежнему шифруются, проверяются портал/активность пользователя/права; webhook fallback нет.

После входа сервер ищет единственный контакт по доступному телефону Telegram согласно MSG-08. Нет телефона либо несколько контактов — ручной выбор. Закрывать браузер можно. Пауза конкретного диалога сохраняется, повторное подключение её не отменяет. Изменение настроек/отключение во время OAuth-запроса блокирует запоздалое включение.

Старые аккаунты с включённой автопривязкой продолжают работать. Если поиск раньше был выключен, он включится при следующем действии подключения; база не массово переопределяет прежние настройки. Старый `/auto-binding` сохранён для совместимости кэшированного клиента, но новый интерфейс кнопки не содержит. Историческое требование отдельного согласия MSG-05 заменено данным решением.

## Переименование без переписывания истории

Владелец подключения или владелец приложения может изменить имя менеджера. **Права, owner_id и получатель OAuth не передаются** — пользователь отдельно выбрал «Пока менять только имя». Заголовок диалога показывает текущее имя; исходящие сообщения подписаны именем, действовавшим на дату сообщения. Например, до передачи номера — Вася, после — Петя. Поздно загруженные старые сообщения и их редактирование сохраняют прежнюю подпись.

Добавочная таблица `telegram_manager_names` хранит границы имён. Для существующего аккаунта начальное имя берётся из нынешнего label; ранее неизвестные передачи номера не угадываются. Граница — серверное время сохранения имени, сопоставленное с timestamp Telegram (точность Telegram до секунды). Смена имени не задним числом. Одновременное устаревшее сохранение отклоняется с 409. Шифротекст сообщения, контакт, курсоры, сессии и паузы не переписываются.

Старый бинарник продолжит читать базу, но покажет всем сообщениям текущее имя. Поэтому откат к нему теряет историческое отображение имён, хотя таблица и данные сохраняются. Это учитывать до релиза/отката.

## Уведомления в «Менеджеры Умный дом»

Первоначальное решение о личных уведомлениях владельцу отменено пользователем: уведомления направляются в общий чат. По точному названию read-only вызовом `im.search.chat.list` подтверждён `chat3092` портала `umniydom.bitrix24.ru`. На другом портале этот адрес не используется. Получатель задан сервером, браузер не может заменить его.

Отправитель — владелец приложения (APP_OWNER_USER_ID), его сохранённый обновляемый OAuth с `im`; отправка `im.message.add`. Доступ и scope проверены read-only, тестовых сообщений в рабочий чат не отправляли. Если отправителю недоступен чат или OAuth, очередь сохраняется и в управлении подключением показывается ошибка отправки.

Оповещение содержит мессенджер, текущее имя подключения, ID его владельца и инструкцию входа через «Сообщения» → «Аккаунты и привязки». Клиентские сообщения, токены, телефонные контакты и QR в общий чат не передаются.

Триггер — отзыв/истечение ранее авторизованной сессии Telegram, требующее повторного входа. Ручное отключение, ошибки API-параметров, временная сеть и FLOOD_WAIT не отправляют ложную просьбу войти заново. Сохранённая переписка остаётся доступна. Фоновый цикл обрабатывает уведомления и для уже неактивного аккаунта.

Состояние инцидента хранится в `telegram_connection_alerts`. Повторный опрос и перезапуск не создают новое оповещение для того же сбоя. После успешного входа следующий отзыв — новый инцидент. При подтверждённом отказе CRM повтор через 5 минут. Если ответ на запись потерян либо процесс прервался во время отправки, исход неизвестен: автоматический повтор остановлен, интерфейс просит проверить чат. Это предотвращение дублей, **не гарантия exactly-once**. Смена имени не меняет владельца.

## Проверки

Штатная backend discovery включает `account-lifecycle.test.ts`, `store.test.ts`, `routes.test.ts`, `service.test.ts`: сохранение исторических имён/поздних сообщений/редактирования, миграция и рестарт, отказ чужому пользователю и устаревшему имени, OAuth до QR, конфликт с отключением, точный чат, дубли, сетевой отказ и неопределённая отправка. Frontend `telegram-api.test.ts` проверяет refresh grant только для connect/legacy enrollment. Browser regression проверяет отсутствие авто-кнопки, форму переименования и сохранение прежних сценариев.

Перед production требуется штатная проверка и сборка из чистого pushed SHA по AGENTS.md. Следует сохранить согласованный SQLite backup. Пользователь остановил выкладку до завершения правок; эта документация не утверждает, что новый код уже работает на сервере.

[Отчёт локальной проверки](audits/2026-10-09-telegram-accounts-preview-local.md): 602 backend / 210 frontend, browser regression пройден.
