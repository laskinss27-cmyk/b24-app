# Возврат инвентаризации в работу: сохранение повторного состояния

Исправление от 14.09.2026. Применяется к SQL-primary сохранению инвентаризаций; режимы источников и права не меняются.

## Причина

Ключ `inventory-update:<id>:<stateHash>` использовался для защиты от повторной записи. После отправки отчёта возврат в работу может полностью совпасть с прежним черновиком, включая результат и введённые количества. SQL writer возвращал старую завершённую команду с `alreadyApplied=true`, но `alreadyCurrent=false`. Слой хранения игнорировал второе поле и отвечал успехом. Интерфейс менял статус после ответа, однако повторное чтение SQL показывало «отправлено».

## Новое поведение

- Уже применённое И актуальное состояние не записывается повторно.
- Если совпала историческая команда, но её состояние больше не актуально, слой хранения создаёт отдельную команду с UUID для нового перехода. История прежних команд не переписывается и не удаляется.
- После новой команды недопустим ответ «успешно», если writer вновь сообщает неактуальный исторический результат или возвращает чужой хеш состояния. Ошибка передаётся в существующий интерфейс действий, статус визуально не переключается.
- Семантика явных ключей в низкоуровневом SQL writer не меняется: повтор того же ключа возвращает результат именно той команды. Обработка повторного целевого состояния остаётся в слое `updateInventoryData`.
- Черновик, фактические количества, комментарии, снимок остатков и результат сохраняются. При возврате меняются статус и отметки отправки/акта по прежним правилам. Проведение или исправление складских документов не запускается.

## Проверки

`inventory-reopen-persistence.test.ts` проверяет три цикла отправки и возврата с повторяющимися состояниями, повторное чтение SQL-модели, сохранность количества и снимка, отсутствие лишних записей при повторе актуального состояния, ошибки SQL и запрет ложного успеха. `inventory-storage.test.ts` проверяет неизменность прежнего Bitrix/shadow поведения. Дополнительно перед выкладкой прогоняется сценарий на изолированной тестовой MariaDB, не на production-данных.

Исправление само по себе не возвращает существующие ревизии в работу. После выкладки пользователь повторяет действие и обновляет страницу. Нельзя ради проверки отправлять отчёт или проводить документы настоящей ревизии.

## Результаты проверки релиза

- Проверка типов backend прошла с зависимостями соответствующей исходной версии.
- 64 теста инвентаризации прошли; один общий MariaDB-тест без отдельного opt-in пропущен. Вместо него целевой реальный сценарий проверен отдельно.
- На прежнем production-образе новый регрессионный тест воспроизводит потерю статуса. На исправленном образе все 12 тестов хранения и возврата проходят.
- `scripts/test-inventory-reopen-mariadb.mjs` прошёл на отдельной MariaDB 11.8 в изолированной Docker-сети, без рабочих credentials и без доступа к рабочей Docker-сети. Три цикла отправки/возврата, повтор актуального состояния и чтение новым соединением прошли; ERP-документов создано ноль.
- Тестовый контейнер MariaDB, его временные данные и отдельная тестовая сеть удалены. Рабочие данные не использовались для пробных записей.

Релиз точечный: поверх проверенного действующего образа меняется только исполняемый `routes/inventory-storage.js` и его source map; добавляются тестовые артефакты. Frontend, права, конфигурация источников и схема базы не меняются. Не выполнять полную сборку из этой ветки поверх прода: ветка основана на исходной версии модуля, а другие последующие production-исправления сохраняются за счёт базового образа.
