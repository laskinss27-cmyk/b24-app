# Состояние части складского остатка

## Пользовательский сценарий

В карточке товара: «Остаток по состояниям» → «Изменить состояние части остатка».
Выбрать физический склад, исходное и новое состояние, количество и комментарий.
Например, из 10 обычных мониторов перевести 1 в «Сток»: останется 9 обычных и 1 сток.
Общий остаток и ID товара не меняются. Обратное изменение выполняется той же формой.
Доступ требует обоих разрешений `transfers.create` и `transfers.post`.

При продаже состояние видно вместе с доступным количеством и физическим складом.
В быстрой продаже выбор сохраняется в черновике реализации; списание выполняется
при проведении реализации в сделке. Оплата и касса не изменены. В корзине быстрой
продажи для одного товара выбирается одно состояние; несколько состояний одного
товара в одной корзине пока не поддерживаются.

## Хранение и безопасность

- Одна карточка ERP Item; состояния — отдельные логические Warehouse с названием
  `<физический склад> · Состояние: <состояние>`. Обычный остаток хранится как раньше.
- Изменение — официальный ERPNext API, проведённый `Stock Entry / Material Transfer`.
  Нет прямых SQL-запросов к ERPNext или записи в Bin.
- При первом явном изменении создаются Custom Field для связи логического склада
  с физическим и состояния, UUID операции и данных истории документа. На старте
  приложения и при чтении эти поля не создаются.
- История содержит количество, состояния, склад, комментарий, пользователя и документ.
- UUID сохраняется в sessionStorage до подтверждения: сетевой повтор использует
  тот же документ, а не создаёт повторное перемещение.
- Проверяются ERP Bin, черновики Delivery Note, перемещения и активные SQL-резервы.
  Недоступный источник резервов блокирует изменение. Разные виды резервов считаются
  консервативно: возможное пересечение SQL-резерва и черновика не освобождает товар.
  Колонка «Свободно в ядре» показывает ERP-остаток за вычетом ERP-резервов и черновиков;
  дополнительные резервы приложения проверяются сервером при применении.
- ERPNext запрещает отрицательный остаток и выполняет финальную проверку при проведении.
  Проверка резервов приложения является проверкой актуального снимка, не распределённой
  транзакцией с ERPNext. Существующий протокол SQL-резервирования не изменён.
- Серийные и партионные товары блокируются до реализации выбора серий/партий.
- Состояние сохраняется при перемещении через транзит на другой физический склад.
- Старые общие метки карточек автоматически не распределяются по количествам.
  Их можно удалить; новые физические состояния назначаются только через инструмент.

## Проверки и выпуск

Интеграционная база: текущий production commit `6e1bd92`, изолированная рабочая копия.
Не разворачивать исходную локальную ветку `0162f23`: она старее работающей версии.

Проверено локально с подменой ERP/API, без изменения настоящего склада:

- `npm run typecheck`, `npm run build`;
- `npm -w @b24-app/backend test` — основной набор 440/440;
- `npm -w @b24-app/frontend test` — 137/137;
- `npm -w @b24-app/backend run test:stock-conditions`;
- `npm -w @b24-app/frontend run test:stock-conditions`;
- браузерный тест формы и выбора «Обычный — 9 / Сток — 1» на изолированной странице.

**В production не развёрнуто.** По AGENTS.md требуется отдельная явная команда
пользователя на развёртывание. Не менять режимы SQL/OAuth и не запускать миграции.
При разрешённом выпуске заново сверить текущую production-базу, сохранить работающий
контейнер для отката, унаследовать его реальные environment/state/public URL,
подключить `erpnext_frappe_network`, проверить внутренний и публичный `/health`,
чтение ERPNext из backend и сеть через `docker inspect`.

Первый реальный перевод количества согласовать по конкретному товару и складу:
пример с монитором 5110 проверялся только на тестовых данных.
