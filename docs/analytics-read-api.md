# API чтения для аналитики маркетплейсов

Решение владельца 06.10.2026: Сергею Посягину (Bitrix ID 3712) разрешить его программе получать товары, физические остатки и текущие закупочные цены. Новые виды данных требуют отдельного решения владельца. Это отдельный доступ программы, существующие права сотрудника в ERP и Битрикс24 не меняются.

## Контракт v1

`GET /api/analytics/v1/catalog?limit=200`

Только HTTPS. Заголовок `Authorization: Bearer <индивидуальный ключ>`. Ключ не передаётся в URL, не вставляется в браузерный JavaScript, Git или публичные файлы. Тело запроса не нужно. CORS для сторонних страниц не открыт: запрос выполняет сервер/скрипт сотрудника.

Ответ JSON содержит:

- `apiVersion`, `snapshotId`, `readStartedAt`, `generatedAt`: версия и время чтения данных. Чтение разных справочников не является транзакционной фиксацией всей ERP, время начала и завершения указано явно.
- `currency: RUB`, `priceMeaning: current_catalog_purchase_price`: текущая закупочная цена за складскую единицу, как в каталоге ERP; не историческая FIFO-себестоимость проданных партий. Пустая/техническая цена — `null`.
- `quantityMeaning: physical_stock_including_reserved`: физическое количество, включая резерв и товары с особыми состояниями. Это **не свободное/доступное к продаже количество**. Резервы и брак не вычитаются, минусовые остатки не обрезаются до нуля.
- `warehouses`: идентификатор (`id` — полное ERP-имя склада), название, тип, `disabled`. Включаются все склады нижнего уровня, в том числе транзитные, технические и отключённые, чтобы не терять физические количества. Для аналитики точки выбираются явно.
- `products`: действующие складские товары «Каталог Б24» (без услуг и выведенного из выбора 9254). Поля: `id`, `oldId`, `article`, `name`, `brand`, `model`, `section`, `status`, `unit`, `purchasePrice`, `stocks` (массив `warehouseId` / `physicalQuantity`). Старый ID и артикул — строки с сохранением ведущих нулей. Отсутствующая запись склада у товара означает отсутствие Bin (нулевое физическое количество), а ошибка чтения всего склада даёт 503, не пустую выгрузку.
- `total`, `nextCursor`: общее количество товаров и указатель следующей страницы. Пока `nextCursor` не равен `null`, повторять GET с этим `cursor` и выбранным `limit`.

`limit` от 1 до 500, по умолчанию 200. Иные параметры (произвольные поля, doctype, фильтры ERP и т. п.) отклоняются. Страницы одного cursor используют неизменяемый результат чтения, новые первые страницы могут использовать кэш до 60 секунд. Старый результат доступен до 5 минут или перезапуска сервиса; HTTP 410 означает начать полную загрузку заново и заменить локальный набор только после последней страницы. Одновременные запросы делят одно чтение ERP. Рекомендуемый интервал полной загрузки — от одной минуты.

Ошибки: 400 — неправильные параметры; 401 — отсутствующий/неверный/отозванный ключ; 410 — истёк результат; 429 — более 60 запросов в минуту на ключ (`Retry-After`); 503 — источник/хранилище доступа недоступно. Не подменять ошибки пустыми остатками. POST/PUT/PATCH/DELETE для этого API не реализованы.

## Источник и ограничения доступа

Новый внешний контракт, старого источника/формата для внешней программы не было. Каталог берётся напрямую из Item, физическое количество — Bin, закупка — существующий `fetchCoreCatalogPrices` / `resolvePurchasePrices` (последний приход либо более поздняя ручная цена и прежние fallback). Метаданные Битрикса и внутренние поля документов не экспортируются. Служебный ERP-токен сотруднику не передаётся, общего прокси произвольных методов нет. Read-only обёртка разрешает только list и блокирует любые setup/записи даже при изменении повторно используемого reader.

Индивидуальные ключи сохраняются **только в виде SHA-256** в `/app/state/analytics-access/keys.sqlite`, SQLite WAL. Ключ имеет владельца, метку и фиксированное разрешение `catalog.read.v1`. Отзыв проверяется на каждом запросе даже при попадании в кэш. Ключ не авторизует существующие рабочие маршруты ERP. Создания/редактирования клиентов, сделок, документов, цен, остатков и прав нет. Административного HTTP API ключей нет.

Журнал успешных чтений содержит ID ключа/владельца, snapshot и количество строк, без значения ключа или выгрузки. Authorization маскируется; автоматический request log нового GET подавлен, чтобы ошибочно переданный в URL ключ не попадал в лог приложения. Внешний nginx может логировать URL, поэтому ключ в URL запрещён и в инструкции.

## Управление ключами на сервере

CLI `node packages/backend/dist/analytics-access/cli.js create|list|revoke` внутри текущего b24-backend. Входной JSON через stdin, а не аргументы. create принимает `ownerId`, `label`, абсолютный `output` для нового защищённого JSON-файла. Ключ записывается один раз с режимом 0600; stdout содержит только ID и путь. При ошибке записи ключ отзывается. Файл передаёт владельцу уполномоченный оператор по закрытому каналу, секреты не публикуются. Повторный запуск создаёт новый отдельный ключ, поэтому результат сначала проверяют по list; не плодить ключи при неизвестном исходе команды.

revoke принимает `{ "id": "UUID ключа" }`, list возвращает только метаданные без hash/секрета. Роли Битрикс24, ERP и действующая персональная Excel-выгрузка не меняются. При откате приложения ключи остаются в bind-mounted state; для отзыва скомпрометированного ключа нужно именно revoke, а не откат контейнера.
