# Служебные скрипты

Папка `scripts/` содержит рабочие инструменты, миграции и историю исследований API. Наличие скрипта не означает, что его можно запускать на проде.

## Рабочий контур

| Скрипт | Назначение |
|---|---|
| `sos-status.sh` | чтение состояния backend, ERPNext, nginx, сертификата и бэкапа |
| `core-backup.sh` | ежедневный бэкап ERPNext |
| `core-backup-disk.ts` | отправка дампа БД на Диск Битрикс24 |
| `b24-app-backup.sh` | standalone consistent dump `b24_app`; сам не меняет cron, retention или внешний upload |
| `b24-app-backup-disk.ts` | upload dump/checksum в изолированную папку Bitrix Disk с read-back SHA-256 и retention 14 пар |
| `b24-app-backup-job.sh` | scheduled-цепочка dump → внешний read-back → локальный retention 14 подтверждённых пар |
| `b24-app-restore-drill.sh` | ручное восстановление dump только в новую БД `b24_app_restore_*`; не содержит `DROP DATABASE` |
| `b24-app-drop-restore-db.sh` | guarded удаление только `b24_app_restore_*` с точным confirmation env |
| `smoke-security.ts` | проверка базовых защитных заголовков |

Рабочее расположение бэкап-скриптов задаётся закрытой конфигурацией сервера. Перед изменением нужно сравнить серверную копию с репозиторием.

SQL-скрипты `b24_app` требуют отдельного разрешения на production-запуск. Backup-скрипт использует root-only option file ограниченного dump-пользователя и публикует архив только после gzip/checksum/schema-проверок. Job удаляет локальную старую пару только при наличии `.uploaded`, а Disk uploader работает только внутри папки `b24_app_backups` и строгого шаблона имён. Restore drill использует административный доступ только внутри MariaDB-контейнера, запрещает имя рабочей БД и отказывается перезаписывать уже существующую временную schema. Cleanup требует отдельное точное confirmation-значение.

## Миграции

Скрипты `erp-migrate-*`, `bitrix-to-erpnext-*`, `erp-cleanup-*` и `cleanup-*` изменяют данные либо предназначены для одноразового перехода. Они:

- не запускаются по расписанию;
- требуют свежей выгрузки и бэкапа;
- сначала выполняются в режиме проверки, если такой режим есть;
- запускаются только в согласованное окно;
- сопровождаются отчётом о созданных и изменённых ID.

`sync.sh` и `erp-migrate-catalog.ts --stock` сохранены как история перехода. Они не являются текущей синхронизацией остатков и не должны добавляться в cron.

`erp-bridge.ps1`, `erp-stock-sync.ps1`, `vps-b24-heartbeat.sh`, `vps-erp-core.nginx.conf` и
`pull-core-backup.sh` относятся к закрытому переходному стенду. Они не входят в рабочую
инфраструктуру и не используются в процедурах из `docs/`.

## Разведки и тестовые записи

Префиксы:

- `recon-*` — исследование особенностей REST API;
- `test-*` — точечные проверки, часть из них создаёт или изменяет записи;
- `erp-*-smoke` и `erp-poc-*` — проверки складского ядра.

Перед запуском прочитать исходник целиком. По названию нельзя делать вывод, что скрипт read-only. Переменная `DEV_WEBHOOK` часто даёт широкие права.

## Безопасный порядок

1. Проверить `git status` и версию скрипта.
2. Прочитать, какие сущности и ID он затрагивает.
3. Убедиться, что endpoint и токен относятся к нужному окружению.
4. Для записывающей операции получить подтверждение и сделать бэкап.
5. Запустить на ограниченном наборе.
6. Сверить результат через пользовательский интерфейс и API.

Секреты передаются через env и никогда не вставляются в исходник или команду, попадающую в историю терминала.
