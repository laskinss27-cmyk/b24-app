## Почему подготовлен узкий пакет backend

Контейнер хранит несколько поколений frontend-ресурсов. Его фактический index.html
использует `index-D_WaAyUh.js` и `index-IR8LjGBu.css`, тогда как полная сборка
Git-базы выдаёт `index-D2AoULg1.js` и `index-CAivRRgF.css`. Поэтому заменять
контейнер результатом обычной полной сборки в рамках этого переноса нельзя:
это включило бы не относящиеся к заказам изменения экранов.

Подготовлен `outputs/umniydom-integration-20260914/overlay`:

- Dockerfile наследует точно проверенный текущий образ;
- payload содержит 22 файла: новый app.js с картой и 10 модулей заказов с картами;
- frontend, SQL-каталог, миграции, Тильда, зависимости и остальные приложения
  наследуются из исходного образа без замены;
- MODE и PROCESSOR явно off;
- manifest.json содержит ID исходного образа/контейнера и SHA-256 каждого файла.

Пакет создаётся локально командой `scripts/prepare-orders-overlay.mjs` из уже
собранного worktree, проверяет исходную ревизию и хеши защищённых модулей.
Скрипт не вызывает Docker, SSH, CRM или миграции. Для повторной генерации нужен
новый каталог вывода. Перед будущей сборкой сверить фактический Image ID с
manifest: одинакового имени тега недостаточно. Если production изменился,
перенос и пакет пересобираются от нового состояния.

Узкий пакет намеренно сохраняет Node.js 20 и пригоден только для размещения
**выключенной** интеграции. Включение SQLite-приёмника требует Node.js 24+.
Отдельно подготовленный аргумент NODE_IMAGE в исходном Dockerfile не обновляет
контейнер автоматически и не разрешает заменять его frontend.

  catalog route, SQL ping/close и приёмник в режимах off/sandbox. Внешний HTTP

Старый сбой теста прав каталога из корневой ветки на актуальной базе не
воспроизводится. В этой подготовке не исправляли и не меняли права каталога.
Предупреждение Vite о размере frontend bundle остаётся предупреждением.
Тестов с production MariaDB, ERP-записями или реальным вебхуком не запускали.

  клиента/лида не меняются.
- Начальная публикация, если будет отдельно разрешена, — с выключенной отправкой;
  активация live worker требует отдельного разрешения.

## Настройки и решения перед следующим этапом

| Пункт | Что осталось |
| --- | --- |
| Среда Node.js 24 | Выбрать и проверить отдельный приёмник/worker на Node 24 либо отдельное обновление runtime backend с сохранением действующего frontend. До этого MODE=off |
| HTTP URL | Подтвердить HTTPS-маршрут `/api/integrations/umniydom/v1/orders` через существующий публичный вход и его маршрутизацию. Для отдельного приёмника потребуется явно настроить bind/прокси |
| Отправитель | Перенести фактический sourceId существующей установки сайта в защищённую конфигурацию. UUID примера не подходит, identity не регенерировать |
| Общий секрет | Сгенерировать новый секрет и передать обеим сторонам защищённым способом. Секрет совместного теста удалён |
| Постоянная SQLite | Подтвердить отдельный путь внутри постоянного state-volume, владельца и доступ обоих процессов. Путь state-volume прочитан из контейнера, а не взят из runbook |
| Резервирование | Включить SQLite inbox и очередь в backup, сохранить WAL корректно и провести восстановление. Нынешний backup MariaDB/ERP сам по себе их не покрывает |
| Вебхук | Выделенный серверный доступ с crm/im и достаточной видимостью контактов, компаний, лидов; проверить чтением права и членство отправителя в чате. Секреты не включены в пакет |
| Начальная стадия | Подтвердить `NEW` («Не обработан») и связанные автоматизации/обязательные поля. Этот статус найден чтением портала, но пока не задан |
| Работа менеджеров | Проверить права на открытие и принятие лидов, назначенных «Автозадачи». Участие всех менеджеров в чате заказов и права ещё нужно проверить. Свободные менеджеры сами разбирают уведомления, включая неоднозначных клиентов; порядок согласован. Технический контроль зависших заданий настраивается отдельно |
| Worker | Настроить отдельный процесс, запуск/остановку и контроль очереди. HTTP приёмник сам worker не запускает |

Шаблон добавочных настроек: [deploy/orders-preparation.env.example](../deploy/orders-preparation.env.example).
Он не содержит переменных SQL, ERP, Tilda или PUBLIC_BASE_URL, чтобы их случайно
не затереть. Не заменять действующий env общим example-файлом: при будущем
обновлении сначала получить защищённый снимок фактического окружения контейнера
и добавить только настройки заказов. В частности, не переключать работающий
SQL-каталог с primary/readiness на off.

Порядок будущих разрешённых шагов: повторно подтвердить исходный образ →
разместить выключенный код → подготовить Node 24 и постоянное хранилище →
включить production-приём с PROCESSOR=off → отдельно разрешить live worker.
Тестовые базы не переносить в production. Действующие правила rollback,
`erpnext_frappe_network`, внутренний/внешний health и read-only ERP обязательны
при будущем деплое; их выполнение в этом этапе не имитировалось.
