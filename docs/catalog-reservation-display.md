# Резервы в остатках каталога

02.10.2026: таблица «Остатки» и карточка товара ранее показывали только физическое количество ERPNext. Наличие SQL-резерва никак не обозначалось, хотя резерв участвовал в ограничении выдачи и публикации доступности.

Теперь `/api/catalog/browse` дополняет каждую строку `reservedByStore`: свежая сумма `active_qty` по товару и складу из `stock_reservations`/`stock_reservation_lines`, только active/shortfall и неистёкшие резервы. Запрос выполняется при каждом чтении каталога вне кэша метаданных; никаких expire/reconcile/проводок не выполняет. Склады сопоставляются через штатное имя ERP с суффиксом компании и ID магазина каталога. При выключенном или shadow-режиме поле отсутствует. При сбое чтения оно равно null, интерфейс показывает недоступность данных.

В таблице и карточке возле склада показывается «в резерве: N». Физические числа, фильтр наличия, сумма закупочной стоимости, корзины и правила проведения сохраняют прежний смысл. Полностью зарезервированный товар остаётся в физическом остатке. Резерв при нулевом остатке не скрывается из списка складов видимой строки; общий фильтр «остаток > 0» по-прежнему работает по физическому количеству. Свободное количество не вычисляется простым вычитанием: другие обязательства учитывает отдельная серверная проверка выдачи.

Миграция данных не нужна. Новое поле необязательно для старых клиентов. Каталог и складской учёт не меняют данные резервов, проведённые документы или внешние приложения отчётности.

Регрессии: `backend/src/routes/catalog-reservations.test.ts` проверяет свежесть, SELECT-only, состояния/срок SQL-предиката, отсутствие изменений исходной строки и обработку ошибки; `frontend/src/catalog-reservations.test.tsx` проверяет реальную разметку таблицы/карточки, физическое количество, дефицит, ограничение складов и недоступные данные. Тест предиката не подменяет интеграционную проверку реальной БД.
