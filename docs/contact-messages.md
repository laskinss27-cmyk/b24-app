# Сообщения контакта во всех сделках (MSG-08)

Решение владельца 09.10.2026: диалог принадлежит клиенту, то есть **контакту CRM**, а не конкретной сделке. Один клиент может одновременно общаться с несколькими менеджерами и в нескольких мессенджерах. В любой сделке контакта открывается одна и та же история каждого диалога.

## Экран

Нативная карточка сделки → вкладка **«Сообщения»** рядом с остальными вкладками приложения. «Товары 2.0» и её регистрация не меняются. Обработчик прежней вкладки `/placement/telegram` сохраняется для совместимости; при открытии приложения его название обновляется с «Переписка» на «Сообщения». При ошибке переименования восстанавливается прежняя регистрация, другие обработчики не снимаются.

При нескольких контактах сделки пользователь выбирает контакт. Далее выбирает мессенджер и отдельный диалог рабочего аккаунта менеджера. Диалоги Сергея и Ивана не объединяются в одну ленту. Название берётся из подписи рабочего аккаунта; владелец подключения и права управления остаются прежними. При одном менеджере его диалог тоже выбирается явно. Менеджер отвечает из обычного мессенджера; отправка из CRM не добавляется.

В текущем выпуске рабочий источник — Telegram. WhatsApp и MAX имеют честное состояние «ещё не подключён к CRM». Личный WhatsApp пилота не переносится на сервер и не связывается с клиентами. Импорт старых архивов отклонён владельцем; отдельного импортера нет.

## Связь и права

Ключ связи: портал приложения + контакт CRM + мессенджер + рабочий аккаунт + идентификатор диалога. В текущем однопортальном backend портал определяется конфигурацией, мессенджер — Telegram-модулем. Новая таблица `telegram_contact_links` связывает `(account_id, chat_id)` с `contact_id`; сообщения остаются в существующем зашифрованном хранилище с прежними уникальными ключами. Новый транспорт или новая независимая база не создаются.

Автопривязка: доступный международный телефон → **единственный CONTACT** в `crm.duplicate.findbycomm` → проверка `crm.contact.get`. Наличие открытой сделки не требуется. Несколько совпавших контактов, только лид, отсутствие номера или совпадения — ручной выбор контакта; номер по суффиксу не угадывается. Существующая связь с контактом автоматически не меняется при изменении телефона, закрытии сделки или передаче клиента. Пауза остаётся паузой. Ручная перепривязка к другому контакту запрещена, чтобы случайно не открыть ему чужую историю; для исправления ошибочной связи нужен отдельный согласованный перенос.

Каждое чтение: действующий сотрудник портала + `deals.view` + `crm.deal.get` текущей сделки + её действующий состав `crm.deal.contact.items.get` + доступ к выбранному `crm.contact.get`. Затем проверяется принадлежность выбранной пары аккаунт/диалог этому контакту. История другой сделки доступна через текущий контакт намеренно — это новое правило владельца, а не обход проверки старой сделки. Произвольный контакт или чужой диалог подставить нельзя. Отзыв доступа очищает показанный текст. Поздние ответы запросов после переключения менеджера/контакта/мессенджера не должны подмешивать сообщения.

Управление аккаунтом и ручная привязка разрешены только его владельцу или владельцу приложения, как раньше; включение фонового OAuth — только владельцем аккаунта. Нет webhook fallback. OAuth-ротация и общий лимит CRM 2/с сохранены.

## Замена MSG-05/06 и миграция

Прежние правила «самая новая открытая сделка» и «до новой сделки писать в старую, потом разделять по дате» **отменены**. Причина: контекст клиента должен проходить сквозь все сделки, а сообщения разных менеджеров должны оставаться раздельными. Старые правила и низкоуровневые регрессии сохранены как описание формата и проверка восстановления прежней базы; production больше не запускает `TelegramAutoBinder`, используется `ContactAutoBinder`.

Миграция добавочная: старые `telegram_bindings`, `telegram_messages`, `telegram_deal_routes`, шифротексты, сессии, курсоры, паузы и OAuth не удаляются и не переписываются. Для каждой старой пары аккаунт/диалог проверяются все сделки из сохранённых маршрутов и сообщений. Автоматическое добавление contact-link допустимо только если у каждой сделки ровно один и тот же доступный контакт. Неоднозначность, недоступная сделка или разные клиенты оставляют данные нетронутыми и связь нерешённой. Ручной выбор допускает один из нескольких контактов только если он есть во всех старых сделках. Нельзя автоматически объединять дубли контактов по одинаковому телефону.

Миграция выполняется фоном для включённой владельцем автопривязки, либо при открытии контекста старой сделки самим владельцем подключения/владельцем приложения. До разрешения связи старый сбор продолжает сохранять записи в прежнем формате; новая вкладка предупреждает о нерешённой привязке. После contact-link старые сообщения из всех прежних сделок читаются по аккаунту/диалогу без копирования; новые строки используют `deal_id=0` только как совместимый служебный столбец. Прикладная принадлежность определяется contact-link, а не этим столбцом.

**Совместимость отката:** старый бинарник не понимает contact-link и не покажет новые строки с `deal_id=0`; поэтому сохранённый старый контейнер — технический rollback, но не полный функциональный откат после начала нового сбора. Перед релизом обязательна SQLite backup вместе с WAL-согласованным снимком. Нельзя возвращать старый backup поверх новых сообщений. При необходимости отката сохранить текущую базу и отдельно согласовать возврат модели; данные не удалять.

Старые API `/api/telegram/history` и `/bind` требуют обновить вкладку (409) после проверки запроса. Новые `/client-context`, `/client-history`, `/bind-contact` используют контактную модель; сервер не возвращает прежнюю смешанную ленту кэшированному интерфейсу.

## Проверки

`contact.test.ts`: два менеджера, одна история каждого через 20 открытых/закрытых сделок; сохранение старого шифротекста; неоднозначность/недоступность миграции; запрет смены клиента; пагинация без примеси другой переписки; отказ после отзыва доступа; отключение/пауза во время фонового запроса; переименование только собственной вкладки и восстановление при сбое. Все тесты входят в обычную backend discovery.

`tools/telegram-pilot/persistent-ui-test.mjs` теперь запускает актуальный `contact-ui-test.mjs`; прежний сценарий разделения сделок сохранён в `legacy-deal-ui-test.mjs` как исторический и не представляет действующий контракт. Реальная собранная страница проверяется с подставными ответами CRM: разные менеджеры, задержанный ответ, несколько контактов, выбор мессенджера, QR/пароль, ручная привязка, отзыв доступа, XSS как текст, 360/768/1280, увеличенный текст и клавиатура. Screen reader и полевые показатели производительности отдельно не измерялись.
