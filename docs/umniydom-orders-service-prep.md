## Выбранное размещение

Основной `b24-backend` остаётся в текущем образе на Node.js 20 со своими
SQL-каталогом, Тильдой, frontend и окружением. Новый образ содержит только
модули заказов и отдельный lock-файл для Fastify, Zod и dotenv. В нём нет
основного приложения, MariaDB-клиента, ERP-кода и frontend.

Это текущий вариант запуска вместо ранее подготовленного overlay основного
backend. Старый overlay сохранён как исторический артефакт, для отдельного
сервиса применять его не требуется.

Приёмник и worker — два процесса одного образа с общей отдельной SQLite.
Приёмник публикует порт только на `127.0.0.1:3091` хоста, worker портов не имеет.
Основной backend сохраняет `erpnext_frappe_network`. Сервис заказов использует
собственную сеть: связь с ERP ему не нужна, worker обращается к Битриксу по HTTPS.

Повторная проверка сервера чтением: исходный Image ID backend не изменился,
контейнер работает в `erpnext_frappe_network`, nginx активен, порт 3091 свободен.
Существующий state-каталог подтверждён из работающего контейнера. Для заказов
предлагается отдельный подкаталог `umniydom-orders` в этом хранилище; он ещё
не создан. Менять владельца или права общего state-каталога нельзя.

## Резервное копирование и контроль

Административные команды не обращаются к CRM. `status`/`verify` открывают только
существующую БД в режиме чтения, не создают отсутствующую очередь и не забирают
задания на обработку. Они не печатают контакты, payload или секреты.

```sh
# В окружении процесса задан UMNIYDOM_ORDERS_DB.
node app/admin.js status
node app/admin.js backup /app/state/backups/<новый-каталог>
node app/admin.js verify
```

Родительский каталог backups должен существовать. Новый каталог снимка создаётся
командой; существующий снимок не перезаписывается. SQLite online backup включает
зафиксированные записи WAL. Копировать один файл активной БД обычным cp нельзя.
Архив снимка с manifest необходимо затем переносить в проверенное внешнее
резервное хранилище: копия на том же диске не защищает от потери диска.
Расписание, срок хранения и внешний перенос пока не включены.

Восстановление в production: остановить приёмник и worker, сохранить исходную БД
со всеми WAL/SHM для разбора, проверить снимок в новом каталоге и привязку
mode/sourceId/portal/chat. Начать с PROCESSOR=off. Сверить с сайтом заказы после
момента снимка и с CRM внешние действия после этого момента. Старая копия могла
потерять журнал уже отправленного сообщения, поэтому автоматическое включение
worker после восстановления недопустимо до сверки. Тест восстановления покрывает
состояние на момент снимка, а не произвольную потерю более поздних данных.

`status` выдаёт число записей, состояния, возраст старейшего незавершённого заказа
и число истёкших блокировок worker. При ожидаемо включённом worker контролировать
повторяющиеся сбои процесса, рост очереди, возраст и истёкшие блокировки.
Порог первого технического сигнала предлагается 5 минут на двух последовательных
проверках. Во время согласованного PROCESSOR=off ожидание в очереди нормально.
Бизнес-разбор неоднозначного клиента в чате сам по себе не является аварией.
Неизвестный результат отправки/создания требует технической сверки; нельзя
сбрасывать такое задание для слепой повторной отправки.

## Что требуется до запуска

| Настройка | Состояние |
| --- | --- |
| Чат и ответственный | Решено: «Заказы интернет магазин», chat19572; «Автозадачи», 2812. Свободные менеджеры сами берут лиды и разбирают неоднозначные уведомления |
| Node.js 24 | Отдельный образ собран и локально проверен |
| HTTPS | Предлагается существующий публичный вход + `/api/integrations/umniydom/v1/orders`. Маршрут nginx подготовлен, но не применён; endpoint ещё не считается готовым |
| sourceId | Нужен фактический UUID существующей установки сайта, без генерации нового и без копирования базы заказов |
| Общий секрет | Создать новый секрет при защищённой настройке обеих сторон. Значения и тестовые секреты в пакет не включены |
| Вебхук | Выделенный серверный вебхук пока не настроен. Требуются CRM/im, участие отправителя в чате и достаточная видимость клиентов/лидов. Проверка должна идти именно под будущим отправителем |
| Стадия | Предложена NEW («Не обработан»); окончательно проверить обязательные поля и автоматизации портала до live |
| Права менеджеров | Проверить состав чата заказов и возможность менеджеров открывать и забирать лиды с ответственного «Автозадачи» |
| Хранилище | Создать только отдельный подкаталог заказов, UID/GID 1000, права 0700; конфигурацию Compose связать с проверенным абсолютным путём. Не менять общий state |
| Секретные файлы | Файл окружения доступен оператору запуска; смонтированные secret-файлы должны читаться UID 1000, монтироваться read-only. Родительские каталоги защитить от остальных пользователей |
| Backup и наблюдение | Подключить внешнее резервирование и технический контроль очереди после согласования запуска; локальный restore drill пройден |

Проверка вебхука использует [im.dialog.get](https://apidocs.bitrix24.ru/api-reference/chats/im-dialog-get.html),
[im.user.get](https://apidocs.bitrix24.ru/api-reference/chats/users/im-user-get.html)
и методы чтения CRM. Успешное чтение не доказывает полную видимость всех клиентов,
право переназначения у каждого менеджера или отсутствие побочных автоматизаций.
Скрипт явно оставляет эти признаки непроверенными и не выполняет пробных записей.

Следующий этап требует отдельного разрешения на размещение сервиса и маршрута.
Сначала приём production с PROCESSOR=off, затем после проверок — отдельно live
worker и контрольный заказ. Основной b24-backend заменять для этого не требуется.
