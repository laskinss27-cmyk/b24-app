# Названия этапов в документах снабжения

Запрос 02.10.2026: в документах сделки показать в названии поставки этап,
из которого заказали оборудование; при нескольких этапах показать все. Те же
сведения должны быть видны в складском учёте.

## Поведение

Новый заказ сохраняет список исходных этапов: стабильный ID и название на момент
создания. Основной состав подписывается «Основная сделка». Пустое имя дополнительного
этапа получает такое же «Этап N», как в таблице сделки. Названия определяет сервер
по выбранным строкам, а не по тексту, присланному браузером. Несуществующий этап
или товар, отсутствующий в указанном этапе, блокирует создание до записи заявки.

Пример: `MAT-MR-2026-00123 — Дунайский · Этапы заказа: Черновой монтаж, Чистовой монтаж`.
Названия одного этапа не повторяются для каждого товара. Одинаковый товар в двух
этапах не заставляет угадывать источник: клиент передаёт stageId отдельно для
каждой выбранной строки. Количества и правила повторного заказа не изменяются.

Список виден в названии поставки среди документов сделки, в названиях заявки и
дочерних документов снабжения, в списках и карточках перемещений и приходов склада.
Поиск снабжения/склада учитывает названия. Дочерняя закупка/приход/перемещение
показывает **этапы исходного заказа целиком**, даже если исполняет только часть
заказа; надпись «Этапы заказа» не утверждает построчное распределение этой части.

## Хранение и совместимость

Раньше /api/supply/request получал только productId, имя и количество; источник
этапа не сохранялся. Теперь stageId передаётся из EnrichedRow, имена разрешаются
через текущие DealStage. Снимок сохраняется в отдельном Long Text custom field
`b24_supply_source_stages` у Material Request, затем копируется в Purchase Order и
Purchase Receipt. Метаданные перемещения хранят sourceStages в существующем JSON
entity; сохраняются при чтении, изменениях статуса и создании корректировки.
Служебные поля создаются штатным ensure-механизмом. Для списка приходов поле
Purchase Receipt обеспечивается до запроса заголовков; дополнительных запросов
сделки или каждой строки журнала нет.

Имена/номера документов ERP (`name`), requestKey и связи не переименовываются.
Названия — отображаемый текст, не новые идентификаторы. Общий комментарий заявки
остаётся отдельным полем. Переименование/удаление этапа впоследствии не переписывает
историю заказа. Исправление прихода сохраняет снимок через существующее копирование
custom fields.

**Старые документы и запросы старого клиента без stageId остаются без названий
этапов.** По совпадению товаров история не восстанавливается: один товар может
принадлежать нескольким этапам. Старые документы, остатки, цены и нативные карточки
смарт-процесса Битрикса массово не меняются. Не переопределять stageId статуса
снабжения: это другое поле, не ID этапа комплектации.

## Проверки

- Backend supply-source-stages.test.ts: одинаковые товары в разных этапах,
  выбор части этапов, несколько этапов плюс основной состав, повторения,
  удалённый этап/чужой товар, старые клиенты, независимый снимок перемещения,
  чтение списка/карточки прихода без обращения к текущей сделке.
- Backend operations.test.ts: снимок заявки при создании/чтении/изменении склада
  и комментария; сохранение в закупке и перенос в приход с прежними ограничениями
  количества и защитой неуспешного проведения.
- Frontend deal-supply-source-stages.test.tsx: фактический запрос из действия
  заказа для двух одинаковых товаров в разных разделах; отображение нескольких
  имён и экранирование HTML; поиск прихода по этапу за первой страницей.
