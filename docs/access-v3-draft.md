# Права отделов и личные исключения — этап 1

Статус: редактор черновиков и проверочный серверный пилот. Развёртывание проверять
по журналу релиза; этот документ описывает возможности исходного кода.
Сохранение и откат меняют только черновик. Узкий пилот владельца теперь можно
включить отдельно явным подтверждением; по умолчанию он выключен.
Старый редактор v2 и enforcement остаются выключенными.

## Пользовательский сценарий

Раздел «Снабжение» → «Права отделов · черновик» доступен в меню руководству
(существующие ID 1, 986, 1858). Сервер на каждом запросе заново проверяет
`user.current`: эти ID или настоящий ADMIN портала. Разрешение в черновике
не даёт доступ к редактору. Для прочих ADMIN пункт меню пока не добавлен.

1. Выбрать отдел и действие, установить «Разрешить» или «Запретить».
2. При необходимости выбрать сотрудника и задать личное исключение.
3. «Как у отдела» удаляет исключение. «Текущая база» удаляет правило отдела.
4. «Проверить изменения» показывает сотрудников и изменения расчётного доступа.
5. «Сохранить только черновик» создаёт новую версию. История позволяет посмотреть
   и сохранить обратное изменение. Хранятся последние 20 предыдущих версий.

Личное правило сильнее правил отделов. При явно противоречащих правилах нескольких
отделов действует запрет; интерфейс показывает конфликт. Без новых правил остаётся
снимок проверенных старых правил. Известные личные исключения вынесены отдельно,
а не распространены на весь отдел. Их удаление возвращает базу отдела.

Допуск к складу — отдельное измерение (просмотр, реализация, приход, списание).
Он не заменяет право операции. В первом этапе эти настройки только моделируются.

## Границы достоверности

- Базу строим из существующего кода, не из предположения «менеджеру можно всё».
- Составные, объектные, CRM- и складские проверки имеют значение «Нужна проверка».
  Это не запрет и не подтверждение доступа. Изменение такого пункта в черновике
  также не означает, что действие уже разрешено сервером.
- База является снимком. При изменении справочника показывается предупреждение;
  автоматического пересоздания базы или применения прав нет. Смена отдела,
  увольнение, новое право и новая версия legacy-кода требуют сверки перед пилотом.
- Редактор не изменяет роли Битрикса и не обходит доступ к сделкам.
- Отчёт влияния сравнивает только модель черновиков, не выполняет операции
  от имени сотрудников. Показывает первые 100 изменений и общее число.

## Хранение и защита

API: POST `/api/access-control/v3/load`, `/preview`, `/save`.
Bitrix-справочники читаются постранично, склады — официальным ERP API.
Дубликаты, обрыв страниц, ошибки и отсутствующие отделы не принимаются за пустую базу.
Проверяются revision и fingerprint свежего справочника; previewToken связан
с конкретными правилами и версией. Это контроль устаревшего просмотра, не отдельная
авторизация: полномочия всегда проверяются через `user.current`.

Хранилище: `${B24_STATE_DIR:-/app/state}/access-v3-drafts/<sha256-domain>.json`.
Путь `/app/state` при deployment обязательно сверить с действующим контейнером.
Отдельный файл портала, эксклюзивная блокировка, сравнение revision под блокировкой,
временный файл + fsync + rename. Токены не сохраняются. Ошибочный файл не сбрасывается
автоматически. Зависшая после аварии `.lock` требует проверки отсутствия писателя
перед ручным восстановлением; автоматического удаления блокировки нет.
Это локальный файловый store, не механизм нескольких независимых backend-реплик.
Нужны backup state-volume и отдельное проектирование HA до многорепличного запуска.

## Локальная проверка

Vite `http://127.0.0.1:4173/?supply`, затем «Права отделов · черновик».
Это искусственные сотрудники и склады. Демо-версии живут только в памяти страницы.
Проверены браузером: отдел → личный запрет → preview → сохранение → откат к версии 0.
API-тесты используют временные файлы и имитации Bitrix, без production-записей.

## Проверочный пилот (этап 2)

Пользователь согласовал пилот только своего аккаунта #1858 и просмотра закупки.
`registerAccessV3Shadow` после обычного access hook наблюдает только три маршрута:

| Проверка | Где наблюдаем | Что сравниваем |
|---|---|---|
| Каталог | `/api/catalog/browse` | `catalog.view_purchase_prices` |
| Окно остатков | `/api/catalog/erp-stocks` | то же право |
| Подборка маркетплейса | `/api/catalog/export-marketplace-selection` | то же право |

Во всех трёх местах исходная роль для этого флага — `true`; существующая функция
`appPermission` дополнительно учитывает прежние правила. Наблюдатель получает именно
её фактический результат и всегда возвращается исходный результат, даже при ошибке
наблюдателя. Проверка не распространяется автоматически на цены/маржу в составе
сделки, отчёты, обычную сверку каталога или иной маршрут с похожим названием.

Применяемый и редакторский расчёт явных исключений используют общий resolver.
Runtime-наследование использует живую проверку маршрута, не замороженный baseline.
Для участника дополнительно читается свежий `user.current` и состав отделов;
ID из тела запроса не принимается. Без подтверждения участника нет наблюдения.
Служебное чтение ограничено 1500 мс; ошибка не меняет ответ бизнес-маршрута.

`POST /api/access-control/v3/shadow` доступен только через ту же точную проверку
администратора, что редактор. Показывает число наблюдений, расхождений, пропусков,
последние 200 проверок (версия черновика, источник, HTTP-код). Обновление результатов
не сбрасывает несохранённые изменения редактора. Статистика в памяти процесса,
очищается при рестарте и не является долговечным журналом аудита. Цены, товары,
сделки и токены не записываются. Отсутствие наблюдений или пропущенная проверка
не означает совпадение. Совпадение флага не подтверждает успешность бизнес-операции,
CRM-доступ, корректность документа или закупочных цен. Даже HTTP 200 может содержать
ошибку приложения. Запрещающие бизнес-проверки не заменяются разрешением черновика.

Проверены: обе стороны расхождения с неизменным ответом настоящего маршрута остатков,
приоритеты исключений, свежая смена отдела, чужой/подставной ID, ошибки и timeout,
ограничение памяти и защита отчёта. Отдельная выкладка требуется для реальных наблюдений.

## Публикация узкого пилота (этап 3)

Управление — блок «Действующая версия пилота». Только точный `user.current` #1858
может preview/activate/disable; администраторам доступен status. Нельзя получить
это полномочие переключателем в черновике или переданным с клиента ID.

Сохранить явное правило «Каталог → Видеть закупочные цены» для владельца (личное
либо правило его отдела), затем проверить включение и отдельно подтвердить.
Неоднозначное наследование и конфликт отделов блокируют включение. Публикуется
только вычисленное значение для #1858 и одного permission, независимо от остальных
изменений в черновике. Разрешение не обходит прежний запрет; это пилот ограничения
видимости, не расширения доступа. Область — те же три маршрута из таблицы выше.
Остальные пути получения цен, включая состав сделки, не входят в пилот, поэтому
он не является полной защитой закупочных цен во всей программе.

Публикация (`pilot`) и последние 20 предыдущих состояний (`pilotHistory`) хранятся
в том же файле портала, отдельно от current/history черновика. Единая файловая
блокировка сериализует сохранение и публикацию. Активная версия, ревизия исходного
черновика, время и ID автора сохраняются атомарно. Изменение/откат черновика
сохраняет активную версию; перезапуск её не сбрасывает. Preview привязан к ревизиям
черновика, публикации и свежим отделам владельца. Повтор устаревшего preview запрещён.
Смена отделов после публикации не меняет уже вычисленное значение: нужна перепубликация.

Маршруты POST `/api/access-control/v3/pilot/{status,preview,activate,disable}`.
Ни загрузка страницы, ни сохранение черновика, ни deployment не включают пилот.
Disable отключает последнюю текущую версию под блокировкой независимо от старого
номера в браузере; несохранённые изменения редактора этому не мешают.
Отключение возвращает прежнюю проверку на следующих запросах. Уже показанные
в других вкладках цены не стираются: после смены пилота обновить каталог.

При включённом пилоте неизвестная/сбойная аутентификация не позволяет обойти
ограничение: для области пилота запрос завершается 403/503. Проверка владельца
не полагается исключительно на старый appAccess cache. Файловые ошибки/повреждённое
состояние блокируют соответствующие запросы; при повреждении файла/зависшем lock
может требоваться ручное восстановление из backup или проверенный откат контейнера.
Отсутствующий файл/старый файл без pilot — первоначально выключенный режим, поэтому
удалять state или восстанавливать старый backup без сверки активной версии нельзя.

Персональное право Владимира #1 редактировать закупочные и розничные цены сохранено;
новый пилот его не затрагивает. Флаги v2 по-прежнему выключены.

## Следующий этап (не выполнен)

Сверить реальные baseline-права с маршрутами и representative-сценариями,
разделить составные разрешения, определить пересоздание базы при кадровых изменениях.
Расширить покрытие проверочного режима, разделить общие флаги между маршрутами
и протестировать все способы выдачи цен до расширения активной политики.
Включение прав, развёртывание и расширение на сотрудников согласовать
отдельно. Нельзя просто включить старый `ACCESS_POLICY_ENFORCEMENT_ENABLED`:
он относится к несовместимой модели v2.
