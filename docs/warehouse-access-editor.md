## Форма

В «Складском учёте» у администратора есть кнопка **Права сотрудников**. Сначала
выбирают отдел или человека, затем базовую роль. «Настроить отдельные действия»
раскрывает группы разрешений. Настройки сохраняются одной операцией; видны список
изменённых субъектов, результат сохранения и история. Выход с несохранёнными
изменениями запрашивает подтверждение их отмены. Конфликт версий сохраняет локальные
правки до явного перечитывания актуальных прав.

- **Прежние права / По отделу** — наследование, без массовой смены доступа.
- **Менеджер** — просмотр склада, реализации и удаление их черновиков, свои заявки,
  сборка/отправка/приёмка перемещений, просмотр инвентаризаций и пересчёт.
- **Снабжение** — складские документы, перемещения и инвентаризации; просмотр и
  отмена реализаций. Создание/проведение реализаций можно добавить отдельно.
- **Руководитель** — все настраиваемые складские действия, без редактора прав.
- **Администратор** — настраиваемые складские действия и управление обычными
  назначениями. Назначается только персонально; выдача отделу запрещена сервером.

Смена базовой роли снимает её прежние исключения после подтверждения. Отмена
персональной настройки возвращает правила отделов, отмена настройки отдела —
прежние правила. Примечание не задаёт срок действия разрешений.

## Приоритет и границы

Персональное исключение → персональная базовая роль → прямые отделы сотрудника →
прежние проверки. Между несколькими отделами запрет приоритетнее разрешения.
Роль отдела распространяется на новых прямых участников; дочерние отделы не
наследуются автоматически. Состав отделов берётся из Bitrix24, кеш пользователя
живёт не дольше 30 секунд. Сохранённая политика обновляется в текущем процессе
сразу; уже открытый интерфейс сотруднику нужно обновить.

Проверенный набор задаёт `WAREHOUSE_PERMISSION_IDS`: складские документы,
перемещения, товарные реализации, инвентаризация. Остальные права ERP этот редактор
не меняет. Исторический полный каталог разрешений оставлен для совместимости;
неподключённые настройки в форме не показываются и не применяются как запреты
новых складских ролей. Право удаления перемещений остаётся отдельным прежним
ограничением Сергея; оно не включено в редактируемый набор. Прямые возвраты
из сделки по-прежнему запрещены: используется заявка согласующему. Проверки
состояния документа, остатков, резервов и ограничения Битрикс24/ERP сохраняются.

Просмотр реализаций не требует создания/проведения; разные действия
`realize-core` проверяются отдельно. Запрет просмотра реализаций учитывается и в
складском журнале/карточке документа. Право отменять свою заявку не отменяет
проверку её автора. Пересчёт инвентаризации не даёт права повторно открывать
отправленную точку или оформлять её акт. Автор обновления определяется по
проверенному `user.current`, а не по присланному `userId`.

## Хранилище и переход

Старая отключённая схема читала `app.option.get` → `ud_access_control_draft_v1`.
Оба выключателя в `access-policy.ts` были отключены с `f64fe3e` от 30.07.2026.
Её сохранённые настройки не следует считать действовавшими правами пользователей.

Новая политика хранится **только на backend**: `${B24_STATE_DIR:-/app/state}/access-control/<sha256(normalized-domain)>.json`.
Это состояние в штатном постоянном `/app/state`, которое следует включать в
резервное копирование вместе с остальным состоянием приложения. OAuth клиента и
прямое изменение app options не меняют авторитетную политику. Старый ключ не
читается, не удаляется и не мигрирует автоматически, включая старую роль «Сервис».
Новый файл до первого сохранения не создаётся; два закреплённых администратора
добавляются при чтении. Все остальные сотрудники сохраняют прежние рабочие права
до назначения новой роли им или их отделу.

Сохранение сериализовано по порталу в одном backend-процессе, сверяет `revision`,
записывает временный файл с правами `0600`, затем атомарно заменяет основной.
Два запроса с одной ревизией дают один успех и один HTTP 409. При масштабировании
на несколько backend-процессов потребуется межпроцессная транзакционная блокировка;
текущий выпуск рассчитан на действующий один контейнер.

Ошибка чтения политики/проверки пользователя блокирует защищённое действие с 503,
а не обходит запрет через старые права. Отсутствующий файл при первом запуске
означает отсутствие новых назначений. Повреждённый существующий файл не считается
пустой политикой. Откат приложения на версию с отключённым редактором вернёт
прежние проверки, то есть новые ограничения перестанут применяться; новый файл
при этом остаётся в `/app/state`. Это нужно учитывать при откате.
