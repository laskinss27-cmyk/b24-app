# Локальная проба Telegram без бота

Запрос владельца 08.10.2026: подключить свой рабочий Telegram и попробовать две клиентские переписки. Первый этап — локальное чтение и пробная связь с номером лида/сделки, без изменений production.

## Запуск и вход

Из корня проекта:

```
npm install --prefix tools/telegram-pilot --ignore-scripts
node tools/telegram-pilot/server.mjs
```

Открыть http://127.0.0.1:5198. Кнопка «Пробный вход без API ID» использует официальные TEST ONLY параметры Telegram Desktop для одной локальной пробы. Собственные параметры можно ввести в раскрываемом разделе. На https://my.telegram.org/apps владелец создаёт своё Telegram-приложение (Desktop), вводит api_id/api_hash только в локальный экран, затем сканирует QR через Telegram → Настройки → Устройства → Подключить устройство. Пароль двухэтапной проверки, если запрошен, вводится в тот же экран. Секреты, QR и коды входа не передавать в чат и не записывать в Git.

## Источники и границы

Ранее приложение не собирало переписку личных Telegram-аккаунтов. Новый источник — пользовательская MTProto-сессия через teleproto 1.229.3; не Bot API и не внешний агрегатор. Локальная отдельная зависимость не меняет рабочие backend/frontend сборки.

Сервер слушает только 127.0.0.1. Cookie HttpOnly/SameSite, проверки Host/Origin/Fetch-Site и пользовательского заголовка, запрет iframe и ограничение тела защищают локальные запросы. Переписка и авторизация не пишутся на диск и не журналируются. MTProto-сессия технически имеет широкий доступ к аккаунту: список диалогов Telegram сам содержит последние сообщения, библиотека получает обновления аккаунта; UI не показывает эти сообщения без явного выбора. Это программное ограничение пилота, а не ограничение прав Telegram.

По кнопке загружаются названия личных диалогов из 200 последних чатов, без ботов/групп/«Избранного». Выбираются максимум два; только для выбранного открытого диалога отдельно запрашиваются последние 100 сообщений. Обновление раз в 15 секунд, пока вкладка видна. Это обновляемый просмотр, не полный архив и не гарантия непрерывной доставки всех сообщений. Вложения обозначаются, пока не скачиваются. Секретные чаты не поддерживаются. Прямые методы отправки, отметки прочтения, импорта контактов и изменения CRM отсутствуют.

Пробная привязка хранит Telegram account/chat ID и введённые kind + ID, действует в памяти одного аккаунта. Номер CRM не проверяется; интерфейс явно сообщает, что реальная карточка не изменена. После отключения или перезапуска связи исчезают. При открытии новой вкладки нужно заново загрузить список; серверная авторизация действует до отключения/остановки.

Кнопка «Отключить Telegram» прерывает QR-вход, проверяет авторизацию и отзывает сессию через auth.logOut, после чего очищает память. При сетевом отказе экран предлагает завершить сессию «B24 local pilot» через настройки Telegram. При аварийном завершении процесса также завершить её вручную: отсутствие сохранённого ключа на диске не означает отзыв сессии на сервере Telegram.

## Проверка и продолжение

Регрессионные проверки — packages/backend/src/integrations/telegram-pilot.test.ts в обычном discover-all backend suite: доступ только после выбора, лимит двух, повторный выбор сохраняет связь, снятие выбора во время запроса не выдаёт сообщения, отключение очищает состояние, локальные HTTP-защиты. Браузерная проверка — tools/telegram-pilot/ui-test.mjs, только подставные клиентские данные и без реального входа.

Вход в рабочий аккаунт и получение реальной переписки подтверждает владелец. Пока не прошёл QR-вход, считать проверенным можно только локальный экран и проверки с подменами. Следующий этап после пробы: определить реальные карточки и доступ менеджера, добавить проверку CRM, устойчивое защищённое хранение, непрерывную синхронизацию и показывать переписку в рабочей карточке. Для production требуется обычная процедура релиза; этот экран сам по себе её не выполняет.

Проверки 08.10.2026: 510 backend и 207 frontend тестов прошли; браузер проверен на 360/768/1280 px, при увеличенном тексте, с клавиатурой и состоянием недоступного сервера. QR и пароль проверены только с подменами, вход в реальный аккаунт ожидает владельца. npm audit зависимостей пилота: 0 известных уязвимостей. Полная проверка WCAG с экранным диктором и полевые показатели производительности не выполнялись.

## Официальный тестовый режим (08.10.2026)

Создание собственного приложения не удалось на рабочем и личном номерах владельца; точная причина ERROR со стороны my.telegram.org не установлена. После ограничения числа попыток новые регистрации не инициируются.

Telegram разрешает опубликованные TEST ONLY параметры для тестирования: https://core.telegram.org/api/obtaining_api_id и https://github.com/telegramdesktop/tdesktop/blob/dev/docs/api_credentials.md. Параметры публичны по назначению, не являются сессией пользователя и не дают доступа к его аккаунту без подтверждения входа. Они ограничены Telegram; API_ID_PUBLISHED_FLOOD, FLOOD_WAIT и другие отказы могут помешать даже этой пробе. Их нельзя использовать для постоянной работы, публикации приложения или подключения 25 менеджеров. Отправка сообщений и изменения CRM в пилоте по-прежнему отсутствуют.

Режим включается только кнопкой владельца (/api/connect-test) и явно обозначен на экране во время подключения/просмотра. Обычный /api/connect продолжает требовать собственные параметры. Не используются чужие рабочие API-ключи, платные агрегаторы, параметры официального production-клиента или импорт готовых сессий. Для постоянного решения требуется зарегистрированная пара API-параметров нашего приложения — одна общая для всех отдельно авторизуемых менеджеров.
Проверка официального TEST ONLY режима 08.10.2026: Telegram выдал настоящий login QR (qrReady=true), авторизация аккаунта не выполнялась (accountAuthorized=false). Код QR и MTProto-ключи не выводились и не сохранялись. Проверка завершила свою временную сессию; локальный экран ожидает отдельного нажатия владельцем кнопки входа. Браузерная проверка нового пути прошла с подменами; 8 регрессионных тестов пилота и backend typecheck прошли.

Владелец подтвердил QR-вход 08.10.2026. Локальный /api/status проверен: state=ready, account присутствует, testOnly=true, ошибок нет. Список диалогов загружен (dialogsLoaded=true), владелец подтвердил, что видит его. На момент проверки выбранных диалогов нет; получение клиентской истории и привязка к конкретной карточке пока не проверены. Идентификаторы аккаунта и сессионные ключи в отчёт не записывались.

Продолжение проверки 08.10.2026: владелец выбрал один диалог и указал сделку 37974, контакт 17422. Чтение через существующий DEV_WEBHOOK подтвердило сделку «37974_СВН», контакт «Сергей» и их связь (crm.deal.get, crm.contact.get, crm.deal.contact.items.get). GET /api/messages выбранного диалога вернул 4 исходящих сообщения и 0 входящих; текст сообщений в отчёт не выводился. POST /api/bind сохранил в памяти kind=deal, id=37974; повторный /api/status подтвердил связь. Это по-прежнему пробная привязка: verified=false в контракте пилота, реальные карточки и приложение production не изменены. Внешняя разовая проверка CRM не добавляет проверку произвольных номеров в код пилота. Входящие сообщения и повторный вход после отключения ещё требуют полевой проверки.

Собственные API-параметры получены 08.10.2026: владелец показал успешно созданное приложение B24app и разрешил взять пару со скриншота. Значения проверены по формату и сохранены только в игнорируемом .secrets/telegram-api.env, в документацию и исходники не включены. На момент переключения локальный сервер пилота уже не работал; прежняя авторизация и пробная привязка в памяти отсутствовали. Пилот заново запущен и POST /api/connect инициирован с собственными параметрами. Проверка /api/status: state=qr, testOnly=false, qrReady=true, account отсутствует, ошибок нет. Это подтверждает получение QR, а не вход в аккаунт: владелец ещё должен подтвердить рабочий Telegram и при необходимости ввести пароль локально. Предыдущая реальная проверка истории и связи со сделкой 37974 относится к прошлой временной сессии. Постоянное хранение сессий, восемь аккаунтов и просмотр переписки в production-карточке ещё не реализованы.

Владелец подтвердил новый вход 08.10.2026. Проверка /api/status: state=ready, testOnly=false, account присутствует, ошибок нет; dialogsLoaded=false, выбранных диалогов 0. Таким образом, вход с собственной парой API-параметров подтверждён на реальном аккаунте. Данные аккаунта, ключи и сессия в отчёт не включены. Сохранение авторизации после перезапуска, автоматическая синхронизация восьми аккаунтов и отображение переписки в карточке CRM остаются следующим этапом, а не результатом этой проверки.
