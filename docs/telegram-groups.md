# Группы Telegram — MSG-14

Решение владельца 09.10.2026: добавить групповые клиентские переписки во вкладку «Сообщения». Существующие личные диалоги менеджеров остаются раздельными; группа имеет одну общую ленту с авторами участников и доступна во всех сделках выбранного контакта.

## Привязка и источник

«Сообщения» → «Аккаунты и привязки» → рабочий аккаунт → «Выбрать диалог» → строка «Группа · название» → контакт → «Привязать к контакту». Поддерживаются обычные группы и супергруппы Telegram; broadcast-каналы не предлагаются. Список по-прежнему ограничен 500 последними диалогами аккаунта, включая группы. Сохранённые связи за пределами списка продолжают собираться. Лимит 100 связей на аккаунт включает группы.

Группы **никогда не привязываются по телефонам участников**. Первый ручной выбор фиксирует контакт и аккаунт-сборщик. Один групповой ключ имеет только одну связь во всём однопортальном хранилище (уникальный частичный SQLite index). Повторный выбор через другой аккаунт не копирует историю, не меняет peer/курсор/владельца и не возобновляет чужую паузу. Другой контакт отклоняется 409. Список другого менеджера показывает только факт существующей связи, без чужого contact ID; читать ленту можно при действующем доступе к этому контакту через сделку.

Один сборщик выбран намеренно: у обычных групп message ID относится к аккаунту читателя, поэтому одинаковые сообщения разных аккаунтов нельзя надёжно объединять по ID. Сравнение текста и времени также не доказывает, что сообщения одинаковые. Основание: [официальная модель Telegram](https://core.telegram.org/api/channel). Не делаем недоказанный cross-account dedup и автоматическое переключение сборщика. Если он отключился, восстановить то же подключение по QR; если потерял участие в группе — вернуть доступ. История остаётся читаемой. Ошибки доступа к одной группе показаны у неё и не останавливают остальные диалоги аккаунта. Смена сборщика требует отдельного решения, в текущем UI её нет.

## Сообщения и участники

Сохраняются новые/изменённые сообщения обычных групп и супергрупп, включая каналовые update-типы; системные события вступления/выхода и список участников не импортируются. Первое подключение, как у личного чата, получает последние 100 доступных сообщений; далее push и контрольная догрузка. Полный старый архив не обещается. Повторный пакет обновляет тот же ключ, не создавая дубль. Push не продвигает курсор контрольного чтения.

Автор берётся из from_id и уже полученных сущностей Telegram, без запроса на каждого участника. ID/имя хранятся внутри зашифрованного payload. Подключённый менеджер определяется по его Telegram ID; отображается имя, действовавшее на дату сообщения (MSG-11), в том числе для менеджера, отличного от сборщика. Неизвестный человек обозначается доступным именем либо «Участник ID»; анонимное сообщение не приписывается менеджеру. Если compact edit не передал сущность, известное имя того же отправителя сохраняется. Личные диалоги продолжают использовать прежнюю подпись.

Удаления супергруппы ограничиваются её ключом: одинаковый message ID в другом канале или личном чате не удаляется. Обычные UpdateDeleteMessages относятся только к общему пространству private/basic, исключая супергруппы. Контрольная сверка всегда ограничена конкретным диалогом. Фото/голосовые/PDF используют MSG-09 с дополнительной проверкой точного типа и ID peer; файл не сохраняется на диск. channels.GetMessages входит в ту же очередь 3,5 с, FLOOD-паузы сохраняются как раньше.

## Данные и совместимость

Источник прежний: Telegram MTProto через подключённый рабочий аккаунт, существующий TelegramStore SQLite и AES-GCM. Нового брокера, базы, бота или WhatsApp-сборщика нет. Личные chat_id остаются десятичными строками; новые group keys — g:<chatId> и s:<channelId>. Peer зашифрован: старый {userId,accessHash} читается без изменений; новые варианты {kind:group,chatId} / {kind:supergroup,channelId,accessHash}. Добавляется только уникальный индекс, старые сообщения/сессии/паузы/contact links не переписываются.

При преобразовании basic-группы в супергруппу Telegram меняет идентичность и пространство ID: старую историю не объединяем автоматически. Прежняя лента сохраняется, новую супергруппу выбирают вручную для того же контакта. Форумные темы пока показываются в одной групповой ленте, без отдельной навигации по темам. Отправка сообщений из CRM не добавлена.

**Rollback:** после появления групп старый бинарник не понимает новый peer/key и может прервать сбор аккаунта при обходе группы. Нужен исправленный релиз вперёд либо отдельный план приостановки групп перед откатом; нельзя считать прежний контейнер полностью совместимым по поведению. Не восстанавливать backup поверх поступивших сообщений. Перед первым выпуском делается согласованный SQLite backup, после — проверка сохранности прежних ключей и расшифровки.

## Проверки

Штатная discovery: groups.test.ts покрывает типы/коллизии ID, исключение каналов/мигрировавших групп, один сборщик/повтор/паузу/конфликт контакта, авторов/имена/anonymous/compact edit, scoped deletes, media peer, запрет phone auto, потерю участия без остановки private, push cursor, второй аккаунт, рестарт/ciphertexts, ACL и одну ленту через разные сделки. Прежние suites сохраняются.

Browser regression contact-ui-test.mjs проверяет собранный интерфейс с синтетическими ответами: отдельная группа, три автора, ручная привязка, отсутствие повторных управляющих кнопок через другой аккаунт, 360/1280px, существующие private/media/rename/ACL сценарии. Реальная клиентская группа не выбирается автоматически для полевой проверки: её должен осознанно связать с контактом менеджер.
