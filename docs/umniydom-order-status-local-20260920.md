# Обратный статус заказов: локальная реализация и совместная проверка

Обновление: production включён 20.09.2026 со стороны задачи магазина.
Актуальное состояние: [production-отчёт](umniydom-order-status-production-20260920.md).
Ниже сохранён исходный отчёт до включения.

Дата проверки: 20 сентября 2026 года. Production не изменялся: новый маршрут не
опубликован, режим статусов выключен, `orders.sqlite` на сервере осталась схемы 1.
В production выполнялись только запросы чтения к SQLite и Bitrix24; лиды, сделки,
задачи, комментарии и исходные события заказов не создавались и не менялись.

## Endpoint и включение

- Метод и путь: `POST /api/integrations/umniydom/v1/orders/status`.
- Локальный адрес отдельного receiver: `http://127.0.0.1:3091/api/integrations/umniydom/v1/orders/status`.
- Планируемый production URL при публикации существующим входом:
  `https://201.51.12.57.sslip.io/api/integrations/umniydom/v1/orders/status`.
  Сейчас этот URL для status не считается включённым.
- Флаг b24-app: `UMNIYDOM_ORDER_STATUS_MODE=off|sandbox|production`, по умолчанию
  `off`. Он обязан совпадать с `UMNIYDOM_ORDERS_MODE`.
- Авторизация: `Authorization: Bearer …`; секрет 32–256 символов из
  `UMNIYDOM_ORDER_STATUS_SECRET` либо `UMNIYDOM_ORDER_STATUS_SECRET_FILE`.
  Значение секрета в код, тесты и отчёт не помещается. Настройка отдельная;
  одинаковое значение с прежним секретом возможно только явной конфигурацией.
- Токен применяется только вместе с настроенным `sourceId` и режимом test.
  Авторизация проверяется до поиска заказа. Затем проверяется полный кортеж
  `sourceId + orderId + eventId + receiptId`; телефон, email, ФИО, номер заказа и
  последняя сделка клиента не используются.
- Обязательные заголовки `Content-Type: application/json` и
  `Accept: application/json`. Ответы содержат `Cache-Control: no-store`, размер
  ограничен 16 KiB, общий таймаут проверки 14,5 секунды, редиректов нет.

Receiver выполняет только методы чтения `crm.lead.list`, `crm.deal.list`,
`crm.status.list` и `user.get`. Механизм назначения менеджеров, CRM-поля,
автоматические задачи и создание заказов не менялись.

## Связь заказа

Первичный точный ключ лида или сделки — `ORIGINATOR_ID=umniydom:<sourceId>` и
`ORIGIN_ID=<order UUID>`. Для принятого заказа также используется сохранённый
`customer=LEAD` из его job и штатная связь сделки `LEAD_ID`. Сделка по `LEAD_ID`
принимается только при единственной допустимой связи. Если один старый лид записан
у нескольких заказов и у конкретного заказа нет собственного external key,
результат — `unresolved/ambiguous`.

Допустимые воронки задаются явно переменной
`UMNIYDOM_ORDER_STATUS_DEAL_CATEGORIES`. Для совместного теста выбраны `0,6`:
«Основная» и «Быстрая продажа». Воронки 2 «Клиентская база» и 4 «Партнерская
база» не считаются выполнением заказа. Перед production это значение нужно
подтвердить с владельцем процесса; текущие девять заказов ещё не содержат
связанной сделки, поэтому фактический выбор менеджерами нельзя подтвердить по ним.

При конвертации лида внешний ключ сделки может не копироваться. Связь всё равно
сохраняется через точный лид заказа и `deal.LEAD_ID`. Если лид уже недоступен, но
по его сохранённому ID находится единственная сделка допустимой воронки, сделка
также определяется. Несколько допустимых сделок дают `unresolved/ambiguous`.
Read-only проверка 50 последних существующих сделок с лидом подтвердила: у всех
50 сохранён положительный `LEAD_ID`, во всех четырёх воронках. Собственная внешняя
идентичность была только у 2 из 50, поэтому опора на `LEAD_ID` после конвертации
необходима. Это общая проверка механизма Bitrix24: среди девяти заказов магазина
конвертированных лидов пока нет.

## Реальный lifecycle Bitrix24

Справочники прочитаны из production 20 сентября 2026 года. Для лидов:

| Стадия | Семантика Bitrix24 | Ответ endpoint |
| --- | --- | --- |
| `NEW` «Не обработан» | активная | `awaiting_assignment`, пока ответственный 2812; иначе `lead_active` |
| `IN_PROCESS` «В работе» | активная | `lead_active` или `awaiting_assignment` по ответственному |
| `PROCESSED` «Обработан» | активная | `lead_active` или `awaiting_assignment`; заказ не завершён |
| `CONVERTED` «Качественный лид» | успешное завершение лида | состояние связанной сделки; без подтверждённой сделки `unresolved/linkage_pending` |
| `JUNK` «Некачественный лид» | отрицательное завершение | `lead_rejected`, причина «Некачественный лид» |

Для допустимых сделок endpoint читает системную семантику текущей стадии, а не
угадывает её по названию:

| Воронка | Успешные | Отрицательные | Остальные стадии |
| --- | --- | --- | --- |
| 0 «Основная» | `WON` «Сделка успешна» | `LOSE` «Сделка провалена», `APOLOGY` «Анализ причины провала» | `deal_active` |
| 6 «Быстрая продажа» | `C6:WON` «Закрытие» | `C6:LOSE` «Сделка провалена» | `deal_active` |

Успешная стадия даёт `deal_won`, отрицательная — `deal_lost`. Причина
отрицательного закрытия равна точному безопасному названию текущей отрицательной
стадии. Ответственный читается по `ASSIGNED_BY_ID`; имя, стадия и причина очищаются
до plain text и ограничиваются длинами контракта.

Системная проверка также подтвердила семантику исключённых воронок: в категории 2
`C2:WON` успешная, `C2:LOSE` и `C2:UC_ZR09ET` отрицательные; в категории 4
`C4:WON` успешная, `C4:LOSE` отрицательная. Эти стадии не влияют на заказ при
настройке допустимых категорий `0,6`.

## Состояние девяти production-заказов

Аудит выводил только короткие SHA-256-идентификаторы, счётчики и признаки, без
контактов, payload, CRM ID и секретов.

- 4 заказа имеют ровно один лид с точным external key. Все четыре находятся в
  `NEW`, назначены служебному ответственному 2812, сделок по `LEAD_ID` нет. После
  включения они вернут `awaiting_assignment`.
- 5 старых заказов ссылаются на отсутствующие лиды; exact key и сделки по
  сохранённому `LEAD_ID` не найдены. Три уникальные старые связи вернут
  `unresolved/not_found`.
- У двух из этих старых заказов один и тот же сохранённый lead ID. Оба вернут
  `unresolved/ambiguous`; статус одного заказа не будет применён ко второму.
- Точных сделок с external key среди девяти заказов сейчас нет.

## SQL и свежесть

При первом запуске receiver с включённым status база b24-app транзакционно
переходит со схемы 1 на схему 2. Добавляются:

- `orders_status_links` — подтверждённая связь и её источник;
- `orders_status_current` — текущая версия, `updated_at`, `checked_at` и state;
- `orders_status_history` — по одной записи на каждую версию состояния.

Любое изменение публичного state увеличивает версию. Повтор того же state меняет
только `checkedAt`; `version` и `updatedAt` сохраняются. Ошибка или таймаут CRM
возвращают 503 до SQL-записи, поэтому stale-состояние не выдаётся как свежее.
Новые процессы worker понимают схемы 1 и 2; старый production-образ после миграции
схему 2 не откроет. Поэтому receiver и worker нужно обновлять согласованно после
резервной копии, а старый образ нельзя запускать вслепую как rollback.

## Совместимость и следующий шаг

Контракт v1 соблюдён: строгие request/response, положительные CRM ID до 19 цифр,
все обязательные nullable-поля, plain text, версии, свежесть, `unresolved`, лимит
ответа и отсутствие cache. `schemaVersion: 1`, существующий receiver создания,
`sourceId`, его секрет и идемпотентность не менялись.

Production остаётся выключенным. Для следующего согласованного этапа нужны:
подтверждение категорий `0,6`, резервная копия общей SQLite, новый совместимый
образ receiver/worker, CRM webhook в receiver только для перечисленных методов
чтения, отдельный status secret, точный nginx location и sandbox-запуск worker
магазина. Лишь после этой проверки отдельно включаются production endpoint и
постоянный `orders:status-worker` сайта; старые `order.created` не переигрываются.
