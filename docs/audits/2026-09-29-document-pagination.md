# Доступ к документам за пределами первой страницы

## Симптом и подтверждение

Пользователь сообщил, что в «Реализациях» нельзя увидеть документы после первых 50, и поиск их не находит. Контрольный документ — `MAT-DN-2026-00763`. Проверены также соседние журналы склада, заявки, инвентаризации, ремонты и маркетплейсы.

29.09.2026 выполнено только чтение из ERPNext через работающий `b24-backend`: документ существует, проведён (`docstatus=1`), дата `2026-09-04`, сделка `36058`, `is_return=0`. Среди 1011 неотменённых реализаций он занимает позицию 317 при сортировке `posting_date desc, name desc`. Данные документа не восстанавливались и не изменялись. Production остаётся на `0efe4e736fdb9a2e9d867403f05ca1e0bad18cca`; это исправление пока не развёрнуто.

Причина: `listCoreMovements` возвращал максимум 50 заголовков без фильтров, максимум 1000 при фильтре периода/товара. Интерфейс искал только в полученном массиве, не имел продолжения списка. В приходах дополнительно обрезался объединённый список Purchase Receipt и Material Receipt. Связь по времени с конкретной прошлой выкладкой не устанавливалась.

## Изменения и совместимость

| Раздел | Результат проверки и исправление |
|---|---|
| Реализации, возвраты, приходы, списания | Убраны пределы 50/1000. Загружаются все заголовки выбранного периода/товара, затем интерфейс применяет поиск/статус и показывает по 50 строк. Навигация сверху и снизу; при смене фильтра возврат на первую страницу; при сокращении списка номер ограничен последней страницей. |
| Заявки на перемещение и отдельные заявки снабжению | Вместо одного `entity.item.get` используется общий `listAllEntityItems`, следующий по серверному `next`. |
| Инвентаризации | Список читает все страницы. Чтение точки и обновление документа запрашивают конкретный `FILTER.ID`, а не ищут ID в первой странице общего списка. Заморозка количеств, запреты редактирования и расчёты не менялись. |
| Ремонты | Прежний цикл с молчаливым пределом 40 страниц заменён общим читателем с проверкой курсора и ошибкой при повторении страницы. |
| Перемещения | Уже используют общий читатель всех страниц; поиск выполняется по полному массиву. Изменения не потребовались. |
| Снабжение из ERPNext | Material Request и дочерние закупки/приходы читаются без ограничения 50; связанные перемещения — через общий читатель. Исправление первой страницы относится к отдельному хранилищу заявок на перемещение/снабжение, а не к Material Request. |
| Маркетплейсы | Найден отдельный предел 200 на тип и на объединённый результат. Убран по умолчанию, включая запросы с периодом. Явный внутренний `limit` сохранён для совместимости. |

Источник данных остаётся прежним: складские документы и маркетплейсы — ERPNext, заявки/инвентаризации/ремонты — соответствующие entity Б24. JSON-контракт API не изменился. Миграция, перепроведение и пересчёт остатков не нужны.

Для складских журналов загружаются только заголовки, детализация — при открытии документа. Поиск по ответственному сохранён благодаря существующему пакетному разрешению имён с кэшем. Первичная загрузка теперь зависит от размера полной истории, зато поиск и переходы страниц не повторяют запросы. Для маркетплейсов сохранено прежнее чтение деталей; нагрузочный тест больших архивов не выполнен. Дальнейшая серверная пагинация должна сохранять поиск по всему результату и не возвращать молчаливую обрезку.
