# Исправление ссылки из ответа на обращение

01.10.2026 пользователь сообщил об экране Битрикс24 «Ошибка при показе приложения» после перехода из личного ответа на обращение. На production `a49aab035004fea0895317cf1b0d59b502012ba1` уведомления ошибочно использовали `APP_SECTION_URL=https://umniydom.bitrix24.ru/devops/placement/502/`. Read-only `placement.get` через OAuth установленного приложения подтвердил отсутствие привязки 502. `app.info` подтвердил установленное приложение и совпадение его CODE с APP_CLIENT_ID; действующий REST_APP_URI зарегистрирован на `/placement/repairs`.

Новый адрес формируется через постоянный код приложения: `/marketplace/view/APP_CLIENT_ID/?params[supportTicket]=ID`, согласно [контракту REST_APP_URI Битрикс24](https://apidocs.bitrix24.ru/api-reference/widgets/universal/app-url.html). Числовой ID привязки больше не является источником ссылки. Старое правило использования APP_SECTION_URL для поддержки отменено; эта настройка инвентаризации не меняется. При отсутствующем APP_CLIENT_ID остаётся инструкция открыть форму без непроверенной запасной ссылки.

Существующий обработчик REST_APP_URI передаёт положительный целый ID обращения в контекст, показывает базу товаров и открывает модальное окно истории. Старые ссылки на ремонт, заявку, перемещение и согласование возврата сохраняют прежние ветви. Новый ID — только указание, что читать: OAuth user.current и проверка автора/владельца выполняются прежним support API; URL не содержит токенов или скриншотов. Переход не отправляет сообщения, не меняет статус и не занимает lease. Очередь, складские данные и права не мигрируются.

Регрессии входят в штатные наборы: уведомление не содержит удалённый placement 502, адрес содержит код и ID обращения, без кода ссылка не выдумывается; действующий обработчик выдаёт support-контекст/BX24 SDK, отбрасывает неверный ID и чужой портал, сохраняет ветви ремонтов/снабжения; форма начинает с истории. Полные проверки: 410 backend + 186 frontend + 6 release = 602 теста, без пропусков; typecheck/build.

Реальный браузер на локальных синтетических данных: автоматическое открытие истории, поля ответа и статуса владельца, поле уточнения и снимки менеджера, закрытие/повторное открытие, понятный отказ при недоступном обращении. Проверен React StrictMode: событие close от пробной очистки эффекта не закрывает повторно открытый диалог. Это проверка UI, а не вход в авторизованный браузер production. Производственный переход требует обычной действующей сессии Битрикс24.

Выпуск выполняется стандартными build/guard/deploy из чистого опубликованного коммита с обеими health-проверками, read-only доступом к ERPNext, проверкой Docker network и retention. Итог выкладки записывается после фактического завершения.
