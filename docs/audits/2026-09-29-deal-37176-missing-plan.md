[Сценарий точечного восстановления](../../scripts/recover-deal-37176.mjs) сначала прошёл dry-run, затем был сохранён и опубликован в Git (`6c37374`) и применён из этого коммита. **Восстановление завершено 29.09.2026 в 15:08 МСК.** Код приложения и production-релиз не менялись.

Проверенный production SHA: `0efe4e736fdb9a2e9d867403f05ca1e0bad18cca`. Backend работает в `erpnext_frappe_network`, чтение ERPNext успешно.

- UI сделки показывает 0 строк, но сохраняет документы снабжения и перемещения и остаток к оплате 96 900 ₽.
- В Bitrix24 сохранились 8 нативных строк на 96 900 ₽. Их количества, цены и состав совпадают с корзиной связанного заказа 1298. Заказ создан 08.07.2026, изменён 04.09.2026; `payed=N`, `deducted=N`; количества нативных резервов равны нулю. `sale.shipment.list` по заказу вернул пустой список.
- В ERPNext не найден ни один Sales Order и Delivery Note с `b24_deal_id=37176`, включая отменённые документы. Файл ручных строк сделки отсутствует. Поиск в Deleted Document и Version для Sales Order по данным, содержащим 37176, не дал результатов. Это не доказывает, что план никогда не существовал.
- Заявка `MAT-MR-2026-00011` создана 28.07.2026; все 6 товарных позиций и их количества совпадают с нативными строками. Последнее изменение — 31.08.2026. В UI виден комментарий о возврате Shelly с Дунайского и отсутствии ожидаемой поставки Add-on/Pro 1. Комментарий не устанавливает, отменялся ли состав сделки.

- Проводки `MAT-STE-2026-00108` (29.07, Shelly → транзит) и `MAT-STE-2026-00236` (19.08, транзит → Максидом Дунайский 64) проведены и привязаны к 37176. Их нельзя повторять при восстановлении плана.
- Заказы поставщикам `PUR-ORD-2026-00035` и `PUR-ORD-2026-00036` также сохранились: крепления × 2, Add-on × 2 и Pro 1 × 1.

## История изменения источника

Коммит `f1c705ea121e3d8cb457d3c7add132ad67280b39` от 30.07.2026 (`fix: keep deal composition in core only`) удалил из `DealProductsTab.tsx` отображение нативных товарных строк при отсутствии плана ERPNext и из `api-deal.ts` перенос старого состава перед изменением/реализацией. Текущий `deal-products-data-loader.ts` читает рабочий состав из ERPNext, дополняя его историей реализаций; оба источника для этой сделки пусты.

Этот переход объясняет механизм невидимости сохранившихся нативных строк. Точная дата появления симптома в production и существование отдельного Sales Order до него пока не установлены. Наличие заявки и перемещения подтверждает прежнюю работу с товарами, но само по себе не доказывает наличие Sales Order: старый интерфейс мог работать с нативным составом.

## Границы восстановления

1. Подтвердить актуальность полного сохранённого состава; сделать снимок исходных строк, связанных документов и полей сделки в закрытом постоянном хранилище сервера.
2. Повторно проверить отсутствие плана и реализаций и отсутствие изменений исходных строк с момента проверки. При расхождении остановиться.
3. Создать только черновик плана ERPNext с точными количествами и ценами. Реальную услугу «Выезд инженера» перенести на существующий ID 9814001, сохранив 3 300 ₽: старый ID 9814 теперь используется для служебной свёртки и не должен поглотить настоящую услугу.
4. Прочитать сохранённый план через штатную функцию приложения, проверить все 8 строк и итог 96 900 ₽. Только после этого заменить нативные строки служебной свёрткой той же суммы.
5. Не перепроводить складские документы, не менять остатки, заявки, перемещения, закупочные цены и состояние оплаты. Проверить интерфейс и сохранность связей документов после восстановления.

Массовый перенос других сделок и возвращение автоматического чтения нативного состава не входят в этот инцидент. Отдельный открытый риск: добавление товара/свёртка в старой сделке без плана может заменить единственный сохранившийся нативный состав. Для 37176 план теперь восстановлен; общая защита других старых сделок ещё не реализована.

Сценарий по умолчанию выполняет только проверки. `--apply` требует неизменного релиза и состава, сохраняет резервную копию в `B24_STATE_DIR/recoveries/deal-37176-20260929` и разрешает ERP-клиенту единственную запись: создание черновика Sales Order этой сделки. Любое обновление каталога, создание служебных полей или складских документов блокируется. Повторный запуск при существующем плане останавливается, а не создаёт дубликат. После частичного сбоя проверять созданный документ и снимок вручную; не удалять исходный снимок ради повторного запуска.
