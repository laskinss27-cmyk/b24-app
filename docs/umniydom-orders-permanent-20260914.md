- Очередь: `/srv/b24-state/umniydom-orders/orders.sqlite`.

Обычный запуск после плановой остановки выполняется через ту же конфигурацию:

```sh
docker compose --project-directory /opt/b24-orders -f /opt/b24-orders/compose.yaml -f /opt/b24-orders/worker.production.yaml --profile worker up -d --no-deps worker
```

При остановке для обслуживания сначала остановить `b24-orders-monitor.timer`,
затем worker; очередь сохранять. После запуска worker вернуть таймер и выполнить
одну проверку `systemctl start b24-orders-monitor.service`. Не восстанавливать
старую SQLite поверх новых заказов и не очищать журнал ради повторной отправки.
При неизвестном результате записи CRM требуется ручная сверка, а не слепой повтор.

## Контроль ошибок и резервирование

`b24-orders-monitor.timer` включён, проверяет каждую минуту: доступность receiver
и worker, задержку очереди от 5 минут, истёкшую аренду задания, техническую ручную
сверку, свежесть проверенной внешней копии до 30 часов и состояние backup timer.
Две последовательные проверки подтверждают проблему. В chat3092 отправляется
уведомление при изменении проблемы и восстановлении; стабильное состояние
не создаёт повторов. Неоднозначный клиент разбирается штатным сообщением заказа.

Отчёт: `/opt/b24-orders/monitor-state.json`, системный журнал:
`journalctl -u b24-orders-monitor.service`. Неизвестный результат отправки
технического уведомления блокирует автоматический повтор до сверки его маркера
`orders-monitor:…` в чате. Сообщения не содержат контактов покупателей.

Контроль расположен на том же сервере: полное падение сервера требует внешнего
наблюдения. При недоступном Битриксе техническое уведомление туда также не сможет
дойти; локальный отчёт сохраняется. Отдельный внешний канал не подключён.

`b24-orders-backup.timer` работает ежедневно в 03:35 UTC / 06:35 МСК с небольшим
случайным сдвигом. Копия после проверки: Битрикс Диск **109488**, 4 записи;
архив `/root/core-backups/orders/orders-20260914T172959Z-55553643.tar.gz`.
Восстановление и целостность проверены. Актуальный отчёт —
`/opt/b24-orders/last-backup.json`.

## Следующий шаг на стороне сайта

На стороне b24-app дополнительное включение worker уже не требуется. Когда
пользователь решит открыть отправку, на стороне сайта нужно включить production
доставку с существующими endpoint, sourceId и общим токеном, запустить постоянный
процесс доставки и проверить один заказ из фактической браузерной формы.
Перед включением проверить отсутствие посторонних накопленных заданий.
CRM-вебхук на сайт не передавать: сайту нужен только токен приёмника заказов.

Дальнейший контроль: квитанция accepted на сайте, done в b24-app, ссылка CRM и
одно уведомление в общем чате. Не создавать новый sourceId при развёртывании
сайта и не пересоздавать его SQLite-очередь.
