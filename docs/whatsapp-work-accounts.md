# Рабочий WhatsApp в «Сообщениях» (MSG-15)

## Принятое поведение

По просьбе владельца 09.10.2026 готовим рабочую интеграцию; рабочий QR он отсканирует позже. Личный аккаунт локального пилота MSG-07, его ключи и история **не переносятся**. Полный старый архив и отдельный импорт пользователь отклонил. Вкладка: сделка → Сообщения → WhatsApp → Аккаунты и привязки → название менеджера → Подключить аккаунт по QR. На телефоне: Связанные устройства → Привязка устройства.

- До восьми рабочих WhatsApp-подключений отдельно от восьми Telegram. Это связанное устройство через Baileys 7.0.0-rc14 (неофициальный протокол обычного WhatsApp), а не Cloud API. Обновления WhatsApp могут потребовать обновления интеграции или повторного QR. Отправки сообщений из CRM нет.
- После первого подключения собираются новые входящие и исходящие. Старые сообщения из присланных телефоном пакетов истории отсекаются по дате первого подключения. После перезапуска эта граница сохраняется. Доставка пропущенных событий зависит от WhatsApp; полнота за длительный простой не гарантируется, отдельного чтения старого архива нет.
- Личный диалог → доступный международный телефон → единственный CONTACT. Фоновый доступ CRM проверяется при подключении, автопривязка включается сразу. LID не выдаётся за телефон: соответствие берётся только из данных WhatsApp. Несколько контактов или отсутствие номера требуют ручного выбора. Первое сообщение ожидает привязки в зашифрованном буфере до 24 часов; связанная история не ограничена этим сроком.
- История принадлежит контакту, видна во всех его сделках и разделена по мессенджеру и аккаунту менеджера. Сохранённая пауза не снимается автоматически. Переименование действует по дате сообщений, права владельца не передаются.
- Группы связываются с контактом вручную; до этого тела групповых сообщений не сохраняются. Один постоянный сборщик на группу, автор каждого сообщения, без дублирования между менеджерами. При потере сборщика автоматического переключения на другого менеджера нет.
- Нормализованные PN/LID объединяются без потери сохранённой истории, с сохранением паузы, новых правок и удалений. Привязки разных клиентов не объединяются. Повтор события не отменяет правку и не восстанавливает удалённое сообщение. Одноразовые/исчезающие сообщения, статусы и каналы не сохраняются.
- Вложения до 25 МБ: фото/PDF/аудио/видео/стикеры поддерживаемых MIME, только по нажатию. В памяти сервера и браузера, без постоянного файла, без cache; закрытие/скрытие вкладки отменяет запрос и освобождает предпросмотр. Права CRM и наличие сообщения проверяются до и после загрузки. Истёкшая ссылка WhatsApp может быть недоступна; повторную загрузку старого файла с телефона не запрашиваем автоматически. Прочие форматы открываются в WhatsApp.
- Разрыв сети восстанавливается с задержкой; ответ 429 сохраняет 15-минутную паузу. Истинная потеря ранее работающей сессии (401/411 или новый QR вместо сохранённого входа) ставит одно уведомление в «Менеджеры Умный дом», chat3092, через OAuth владельца приложения. Ручное отключение и краткий сетевой сбой не создают такое уведомление. Неопределённый результат отправки не повторяется вслепую.

## Источники данных и совместимость

Прежний источник — локальный ограниченный снимок tools/whatsapp-pilot на 5201; он остаётся отдельным диагностическим пилотом. Новый — серверная SQLite в `${B24_STATE_DIR}/whatsapp/whatsapp.sqlite`, отдельный ключ AES-GCM, сессионные данные Baileys/Signal и исходные события в зашифрованных столбцах. Никаких файлов пилота, browser storage или tdata сервер не читает.

Переиспользован проверенный TelegramStore для владельцев, привязок к контакту, истории имён, сообщений, прав и очереди оповещений, **в отдельной базе**. Исторический префикс таблиц `telegram_*` здесь — внутренняя схема общего хранилища; Telegram DB не становится источником WhatsApp-сообщений. Новые `wa_*` таблицы хранят auth, дату начала, псевдонимы и исходные сообщения. Числовой ID истории — durable event ID; настоящий строковый WhatsApp key хранится в зашифрованном событии. Контроллеры `/api/whatsapp/*` отделены от `/api/telegram/*`.

OAuth CRM используется общий: registerTelegramRoutes возвращает тот же экземпляр TelegramCrmAccess, включая сериализацию ротации и общий ограничитель фоновых CRM-вызовов. Второго хранилища refresh token и гонки между независимыми экземплярами нет. В текущем приложении для WhatsApp требуется исправная серверная конфигурация Telegram/общего CRM-доступа. Все HTTP-маршруты требуют deals.view; аккаунтами управляет владелец/владелец приложения; чтение диалога дополнительно проверяет доступную сделку и её контакт. Сессии/ключи не возвращаются через API.

Структурные изменения Telegram минимальны: общий CRM getter, параметр марки мессенджера для оповещения и поддержка ключа группы с дефисом в общем store. Telegram HTTP schema прежняя. Существующие сообщения, связи, паузы, курсоры и ключи Telegram не мигрируются. Откат на прежний образ оставляет WhatsApp DB на диске; прежний backend её не читает, сбор WhatsApp останавливается. Данные и конфигурацию при откате не удалять.

## Серверная конфигурация и обслуживание

`${B24_STATE_DIR}/whatsapp/config.json` (0600): `key` — отдельные случайные 32 байта в hex; `proxy` — необязательный SOCKS5/SOCKS5h URL. Не менять ключ после подключения аккаунтов. Резервировать базу SQLite штатным online backup вместе с ключом в закрытом хранилище. Не помещать конфигурацию, QR, ключи и логины в Git/логи.

На действующем сервере используется существующий WARP SOCKS-контейнер. WebSocket и native fetch медиа/служебных пакетов идут через один SOCKS connector; глобальный системный proxy и globalThis.fetch не меняются. Undici 8 обёрнут штатным Dispatcher1Wrapper для совместимости с native fetch Node 24; прямое подключение Agent несовместимо. DNS назначения разрешает proxy, TLS проверяет сертификат. Предпросмотр ограничивает хосты WhatsApp, запрещает redirects и поддерживает отмену.

Зависимости закреплены lockfile. У libsignal 6.0.0 обнаружен вывод session record с ключами через console вне логгера Baileys. `signal-logging.ts` проверяет SHA исходных функций и заменяет только openSession/closeSession/removeOldSessions эквивалентными переходами без вывода ключей. Глобальный console не подменяется; при иной версии/содержимом WhatsApp не запускается до ревью. Проверяется регрессией. Не удалять этот guard при обновлении библиотеки.

## Проверки и ограничения приёмки

Обычные discovery suites включают `whatsapp/{whatsapp,routes,network}.test.ts`: durable auth/история, PN/LID/правки/удаления, буфер, группы, паузы, переименование, лимиты, восстановление, неверный аккаунт, уведомления, ACL CRM/сессий, shared OAuth, повторная media-проверка. Frontend namespace и временный preview входят в штатные тесты. `tools/telegram-pilot/contact-ui-test.mjs` проверяет общий экран обоих мессенджеров на 360/768/1280, QR WhatsApp, отдельные ленты/медиа и сохраняет Telegram-регрессии.

Реальный рабочий WhatsApp пока не подключён по решению пользователя. Нельзя считать доказанными серверную доставку рабочего аккаунта, работу восьми сессий и длительную стабильность до отдельной живой проверки после QR. Локальный личный пилот ранее подтвердил новые сообщения в обе стороны и сохранение после рестарта; это не заменяет приёмку нового серверного подключения.
