# Сохранение связей строк состава сделки

При редактировании или удалении позиции этапа `Sales Order.items` обновляется целиком. Каждая сохранившаяся строка должна передаваться с прежним дочерним `name` и `b24_line_key`. Если у старой строки ключ ещё не сохранён, используется её прежний `name`, как при чтении плана. Новая строка получает отдельный ключ.

До исправления `updateDealStageItem` и `removeDealStageItem` передавали только товар, количество и цену. ERPNext создавал новые дочерние записи и терял `b24_line_key`. Существующая реализация сохраняла правильный сегмент `line:<старый ключ>`, но интерфейс больше не мог сопоставить её с планом и показывал количество к повторной отгрузке. Складские проводки и сама реализация при этом сохранялись.

Источник данных и контракт сопоставления не меняются: план — `Sales Order`, история — `Delivery Note`, принадлежность строки — `b24_line_key` и `b24_deal_segment`. Нельзя исправлять расхождение общим сопоставлением только по товару: в сделке могут быть несколько строк одного товара или услуги с разными ценами и этапами.

Дополнительная защита от 01.10.2026 закрывает общие пути сохранения. Прежний `upsertDealPlan` выбирал дочернюю запись по очереди одинаковых productId; перестановка или удаление дубликата переносила ключ на чужой `name`. Строка без сохранённого ключа получала новый UUID вместо используемого при чтении прежнего `name`. Маршрут добавления товаров превращал весь состав в `Map(productId)` и выбрасывал повторяющиеся строки; чтение альтернативного КП также отбрасывало ключи каталожных позиций.

Теперь `prepareDealPlanLines` сначала резервирует явные ключи и подбирает прежний дочерний `name` только по идентичности строки. Совместимость запроса без ключа сохраняется для единственного однозначного кандидата; неоднозначные или повторяющиеся ключи отклоняются до записи. Новая явная строка не забирает дочернюю запись существующего дубликата. Ключи альтернативных КП сохраняются при чтении и выборе.

Накопительный реализованный состав защищён по каждой паре productId и `line:<ключ>` с учётом возвратов. Если реализованная строка исключена из запроса, но ещё есть в прежнем плане, сохраняется именно она с прежним ключом, дочерним `name`, ценой и скидкой. Другая строка того же товара не подменяет её, даже при достаточном суммарном количестве. Полный возврат допускает удаление строки. Если действующая реализация ссылается на уже отсутствующую идентичность, дальнейшее сохранение требует восстановления по истории и не угадывает связь по товару.

Добавление товаров использует массив всех прежних строк; Map нужен только для выбора строки, количество которой увеличивают. Новый этап накапливает количество в первой строке товара, как чтение таблицы и редактор этапов, сохраняя прежнюю базовую цену. Удаление позиции этапа вычитает её количество один раз, а не из каждого дубликата.

Редактирование количества этапа не может уменьшить его ниже действующей реализации этого сегмента; удалить реализованную позицию этапа можно после соответствующего возврата. Иначе прежний суммарный baseline сохранял товар в общем плане, но удалённая строка этапа больше не сопоставлялась со своей реализацией. Отказ сохраняет прежний состав; полный возврат и обычное удаление нереализованной позиции проверены штатными тестами.

Обновление этапа сохраняет идентификаторы всех строк, включая не относящиеся к изменяемому этапу. Удаление позиции сохраняет идентификаторы оставшихся строк и реализованный накопительный состав. Историческая строка, возвращённая в накопительный план из реализаций, использует прежнюю запись, если её можно однозначно определить.

Миграция схемы не нужна. Уже потерянные связи автоматически не угадываются. Для отдельной подтверждённой проблемы старый ключ восстанавливается только при однозначном совпадении истории `Version`, проведённой реализации и текущей строки плана. Восстановление меняет технический ключ, сохраняет резервную копию и проверяет неизменность бизнес-полей, проведённых документов и складских остатков. Подробные производственные данные восстановления сохраняются локально без отправки в публичный репозиторий.

Регрессии в штатном `B/erp/operations.test.ts`: жизненный цикл этапа сохраняет `name`/ключ; изменение и удаление этапа не теряют связь уже проданных одинаковых строк с разными ценами; прежний `name` старой строки остаётся её ключом. Полные наборы после изменения: 384 backend, 179 frontend, 6 release tooling; typecheck и сборка проходят.

Новые регрессии входят в тот же штатный набор: перестановка реализованных дубликатов и сохранение старой строки без ключа; пропуск реализованного дубликата; новая явная строка перед прежней строкой без ключа; отказ при неоднозначных и повторяющихся ключах; удаление полностью возвращённого дубликата; однократное вычитание количества этапа; отказ при уже повреждённой связи. `B/deal-manual.test.ts` проверяет HTTP-добавление в рабочий состав и альтернативное КП, добавление того же товара в этап и выбор переставленных строк альтернативы. Пять сценариев сохранения воспроизвели дефект до исправления.

Общий поиск исторических расхождений выполняется без записи: сопоставляются активные `Delivery Note` с текущими ключами плана, включая строки с полным возвратом, если товар остаётся в плане. Для найденных связей применяется описанная выше проверка Version и отдельное восстановление с резервной копией. Это проверка сохранности идентичности, а не переоценка товаров, изменение состава, перепроведение документов или складская операция. Производственные аудиты и резервные копии остаются в закрытом хранилище сервера.
