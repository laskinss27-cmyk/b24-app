## Денежная оценка (INV-04)

База — **закупочная цена**. Для старой инвентаризации без сохранённой закупки пользователь выбрал: **«Зафиксировать цену при первом расчёте»**.

Новые результаты уже включают `purchase` из расчёта и сохраняются с ним при отправке. Для старых сохранённых результатов без цены `/api/inventory/list` теперь фиксирует найденную закупку в строках `result.lines` хранилища Б24 `ctv_inv` и добавляет `purchaseFixedAt`. Ответ с новой оценкой возвращается только после успешной записи. Последующие открытия используют сохранённую цену; каталог не переоценивает этот результат.

Источник закупки сохранён: `Standard Buying`, затем `Item.valuation_rate`. Ранее сохранённая числовая цена, включая нулевую, не меняется. Если цена отсутствует или некорректна, строка остаётся без оценки, а не получает выдуманный ноль. Она может быть зафиксирована при следующем чтении, когда источник её предоставит. При недоступном ERP уже оценённые результаты остаются доступными без переоценки.

Ранее чтение добавляло текущую цену только в ответ. Новая совместимость — однократное дополнение старых результатов в том же хранилище; массовой миграции и восстановления цены на историческую дату нет. Количества, статусы, документы и существующие цены сохраняются. Осознанное повторное открытие и отправка нового результата остаются отдельным действием пользователя; это не автоматическая переоценка сохранённого отчёта.

Чтение старого результата с отсутствующей ценой теперь может вызвать `entity.item.update`. Перед записью используется общий замок по ID инвентаризации и повторное чтение по `FILTER.ID`, чтобы не затереть параллельные подсчёты и другие точки. При ошибке записи запрос завершается ошибкой без выдачи временного расчёта за зафиксированный. Как и существующие обновления инвентаризации, замок действует в одном backend-процессе; внешние прямые записи в Б24 им не защищены.

Регрессии в `B/routes/inventory-price-snapshot.test.ts`: изменение каталога после первого расчёта; сохранение остальных полей; два одновременных первых чтения после обновления подсчёта; ошибка записи; ноль / отсутствующая цена; отсутствие повторных запросов и записей для оценённого результата. Проверка денежных итогов `F/inventory-money.test.ts` сохранена.

## Продажи во время подсчёта (INV-06)

Пользователь выбрал простой процесс: сотрудники сами учитывают проданное во время подсчёта. Корректность факта относительно учётного снимка проверяется ими до отправки результата; нельзя повторно учитывать продажу, уже отражённую в подсчитанном количестве.

Не требуется возвращать исторические автоматическую проверку свежести черновиков, полный предварительный анализ нехваток и отдельный подтверждённый пересчёт (`4f48446`, `592610b`). Это намеренно снятое требование, а не обязательная к восстановлению регрессия или временный обход. Автоматическую корректировку факта по продажам не добавляем.

Остаются замороженные учётные количества и отправленный результат (INV-01), раздельные документы и продолжение частичного проведения (INV-02), подтверждение сохранения и отказ устаревшим/недопустимым записям (INV-05), доступ и собственные проверки ERP. Отмена INV-06 не разрешает отключать эти защиты или переписывать проведённые документы. Миграция не нужна.
